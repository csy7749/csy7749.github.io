游戏AI-GOAP（5）：GOAP+GAS 融合架构与设计方向

Created2026-08-10|Updated2026-08-13|游戏AIGOAP
|Post Views:

GOAP+GAS 整合系列走到了最后一篇。第 4 篇讨论了”为什么整合”和”怎么共享基础设施”——用 Attribute 替代 WorldKey、用 GAS Ability 替代 GOAP 的 Effect 和 Sensor、用监听能力替代 Goal。这篇是面向落地的：把两套框架的组件摊开做对照，理清融合后的职责边界，然后给出一个可执行的设计方向和架构总览。

GOAP 组件回顾

在讨论融合之前，先快速回顾 GOAP 的核心组件在 crashkonijn 框架中的形态[^1]。如果你读过第 1、2 篇，这一节可以当速查表用。

Goal（目标）

Goal 代表 Agent 期望达成的结果，是 Planner 的出发点。

属性 说明
Conditions 基于 WorldKey 的一组标准，全部满足即视为目标达成。例如”保命”目标的条件可能是 IsHealthHigh + IsInSafeZone
BaseCost 目标的基础代价，用于多目标优先级排序

Goal 类无状态——它只向 Planner 提供”什么算达成”的标准，Planner 用它来决定最合适的 Action 序列。

Action（动作）

Action 是 Agent 可执行的离散步骤，由四个部分构成：

Action 的生命周期通过 IActionRunState 接口控制：

方法 职责
Update(agent, context) 每帧更新动作状态
ShouldStop(agent) 返回 true 则停止
ShouldPerform(agent) 返回 true 则继续执行
IsCompleted(agent) 检查是否完成
MayResolve(agent) 条件完成判定，用于可中断动作
IsRunning() 当前运行状态查询

通过实现这个接口，开发者可以定义自定义的动作运行状态——启动、暂停、恢复、中断——适配复杂的异步行为（比如”移动到目标”这个动作需要多帧完成，中途可能被打断）。

Action 还支持 Enable() / Disable(disabler) 的开关机制，运行时可以动态禁用某些动作而不需要修改配置。

AgentBehaviour 与 GoapActionProvider

这两个组件的职责分离是 crashkonijn 架构中设计精妙的地方：

  • GoapActionProvider（决策侧）：根据当前目标和世界状态决定要执行哪个 Action，管理 Goal 的切换和优先级。它不知道 Action 怎么执行——只知道一个 IActionReceiver 接口。
  • AgentBehaviour（执行侧）：从 Provider 拿到 Action 后负责驱动执行——移动、播放动画、等待完成。它不知道为什么要执行这个 Action——只知道一个 IActionProvider 接口。

这种决策与执行分离的设计让两端可以独立测试：你可以用 Mock 的 Provider 测试 AgentBehaviour 的行为执行是否正确，也可以用 Mock 的 Receiver 测试 Provider 的决策逻辑。

Sensor（传感器）

Sensor 把游戏世界翻译成 GOAP 能读的状态，提供两种数据：

类型 存储 示例
WorldKey int 值 AppleCount = 3、IsHungry = 1
TargetKey Vector3 位置 AppleTree = (12, 0, 8)

按作用域分两层：

作用域 说明 示例
Global 所有同类 Agent 共享 IsDaytimeSensor、WeatherSensor
Local 单个 Agent 独有 ClosestAppleSensor、OwnHealthSensor

MultiSensor 允许在单个类中组合多个 Sensor，减少重复的感知代码。Sensor 还支持定时器，可以按固定间隔更新（比如每 2 秒扫描一次最近的资源点），而不是每帧更新。

这些在第 2 篇中有详细展开，这里不再赘述。

GAS 组件速览

GAS（Gameplay Ability System）是 Epic 在 UE 中设计的技能框架，其核心思想在 Unity 中同样适用[^2]：

组件 职责
Tag（标签） 状态标识：饥饿、眩晕、战斗中。轻量、可叠加、可继承
Attribute（属性） 数值属性：生命值、饱腹度、体力。支持 Min/Max 钳制
AttributeSet 属性的集合，定义一组关联属性的计算规则
Modifier（修改器） 临时修改属性值：+20% 攻击力，持续 5 秒
GameplayEffect 效果的载体：伤害、治疗、Buff、Debuff。可以瞬时也可以持续
Ability 可执行的能力：近战攻击、翻滚、喝药。有冷却、消耗、触发条件
Trigger（触发器） 事件驱动：当属性变化或标签变化时自动触发 Effect
Cue（表现） 视觉/听觉表现层：特效、音效、屏幕震动

组件对照：GOAP ↔ GAS

把两套框架的组件放在一起对照，融合点就很清楚了：

概念 GOAP 侧 GAS 侧 融合策略
世界状态 WorldKey（int 值） Attribute（float 值） 统一为 Attribute：Hunger 不再用 int 的 0/1，而是 float 的 0~100
位置目标 TargetKey（Vector3） — GOAP 独有，保留
状态标识 WorldKey（bool） Tag 统一为 Tag：IsHungry 不再是一个 WorldKey，而是 饱腹度 < 30% 时通过 Trigger 添加的 Tag
效果 Action.Effects GameplayEffect 统一为 GameplayEffect：GOAP 的 Effect 不再直接改 WorldKey，而是通过 GAS Effect 修改 Attribute
动作 Action Ability 统一为 Ability：GOAP 的 Action 变成 GAS Ability，用 Tag 做前置条件
传感器 Sensor Trigger 用 Trigger 替代 Sensor：属性变化时自动触发事件，替代主动轮询
目标 Goal 监听能力 Goal 变监听能力：目标是”当条件满足时自动激活的能力”
表现 — Cue GAS 独有，GOAP 侧复用

融合后的核心原则：GOAP 做规划，GAS 做执行。GOAP 不再直接操作世界状态——它通过 GAS 的能力系统来感知和改变世界。

设计方向

属性驱动标签系统

这个方向是整个融合的核心想法——用属性和标签替代 GOAP 原生的 WorldKey+Sensor 体系：

举例：人类 A 有 饱腹度 属性：

  • 当 饱腹度 < 30% → 触发 Effect B → 给自身添加 Tag 饥饿
  • 当 饱腹度 >= 30% → 触发 Effect C → 移除 Tag 饥饿
  • Planner 通过检查 Tag（而不是 WorldKey）来判断是否需要执行”找食物”计划

这样做的好处：

  • 声明式：不需要每帧跑 Sensor 轮询，属性变化自动传播
  • 可组合：多个 Effect 可以同时操作不同的 Tag
  • 可追溯：Tag 的添加和移除都有明确的触发源，调试时一目了然

抽出状态与标签为独立模块

GOAP 和 GAS 都不直接拥有 Attribute 和 Tag——它们通过引用访问一个共享的状态模块：

这样做的优势：

  • GOAP 和 GAS 各自独立演化，互不耦合
  • 状态模块可以单独测试
  • 未来换掉 GOAP 或 GAS 中的任何一方，状态层不受影响

与 NodeCanvas 结合

如果项目使用 NodeCanvas 做行为树，GAS 的 Tag、Attribute、Ability、Effect 可以直接作为行为树节点的判断条件和执行动作——相当于用行为树做更高层的编排，GOAP 做中层的规划，GAS 做底层的执行。

与 Timeline 结合

Timeline 可以用来编排 GAS Ability 的时间轴表现（技能前摇、打击帧、后摇、特效同步），GOAP 在规划阶段不需要关心这些表现细节。

架构总览

融合后的完整 Agent 架构：

各层职责：

  • GOAPPlanner：从 Goal 出发，用 A* 搜索找出最佳 Action 序列
  • GASAbilitySystem：执行具体的 Ability，管理 Attribute 和 Tag 的变更
  • 共享状态层：Attribute + Tag，GOAP 和 GAS 通过引用读写
  • Debugger：可视化规划过程，辅助调试（第 3 篇讨论过）

回顾

这个系列的 5 篇文章串起来是一条从理论到落地的路径：

篇 主题 核心问题
(1) 入门 GOAP 是什么、反向链接搜索 “GOAP 怎么工作的？”
(2) 框架深入 crashkonijn 的架构设计 “工程化的 GOAP 长什么样？”
(3) 可视化与多目标 调试工具和多目标处理 “怎么看到 Planner 在想什么？”
(4) GOAP+GAS 整合 两套系统的融合设计 “GOAP 和 GAS 能一起用吗？”
(5) 本文 融合架构与设计方向 “怎么落地？架构怎么画？”

GOAP 给了 AI 灵活性和不可预测性，GAS 给了 AI 可配置性和可维护性。融合之后的愿景是：用 GOAP 做”想要什么”，用 GAS 做”能做什么”，用共享的属性/标签层做”世界是什么样的”。

[^2]: BandoWare/GameplayTags — Unity 的 GameplayTags 实现
