Unity AssetBundle加载框架：从版本清单到引用卸载

Created2026-08-18|Updated2026-08-18|Unity资源管理
|Post Views:

AssetBundle 只是 Unity 提供的资源归档与加载能力，不是完整的资源框架。真正可用于项目的系统，还要解决版本、清单、寻址、下载、缓存、依赖、并发、引用和卸载。本文参考 YooAsset 与 CatAsset 的公开设计，把这些职责整理为一套与具体框架无关的工程模型。

本文面向已经使用过 AssetBundle.LoadFromFileAsync、LoadAssetAsync 的 Unity 开发者。重点不是再写一个 API 调用示例，而是解释：一个 AB 加载框架为什么需要这些模块，它们如何协作，以及资源为什么经常“能加载，却卸载不干净”。

一、先给结论：资源框架管理的不是文件，而是生命周期

一次业务加载表面上只有一行：

框架内部至少要完成：

因此，框架的核心目标不是“封装 LoadAssetAsync”，而是保证三个闭环：

  1. 正确性闭环：同一个地址总能定位到当前版本的正确内容，依赖按序加载，错误明确暴露。
  2. 性能闭环：重复请求只执行一次底层工作，下载与加载受控并发，缓存可复用。
  3. 生命周期闭环：谁持有、谁释放，依赖引用可追踪，资源最终能在安全点回收。

二、Unity 原生 AssetBundle 到底负责什么

Unity 原生层提供四类能力：

能力 典型 API 说明
加载 Bundle LoadFromFileAsync、LoadFromMemoryAsync、LoadFromStreamAsync 把一个 AB 文件交给 Unity
加载 Asset LoadAssetAsync<T>、LoadAllAssetsAsync 从已经加载的 Bundle 读取对象
查询构建依赖 AssetBundleManifest.GetAllDependencies 得到 Bundle 级依赖关系
卸载 Bundle Unload、UnloadAsync 释放 Bundle 数据，可选择是否销毁已加载对象

它不会自动替项目完成：

  • 逻辑地址到资源路径、Bundle 名的映射；
  • 本地版本与远端版本比较；
  • CDN 下载、断点续传、校验与损坏修复；
  • 内置文件、缓存文件、远端文件的优先级选择；
  • 相同加载请求合并；
  • Asset、实例、场景和 Bundle 的引用计数；
  • 包体分组、灰度、回滚与缓存清理；
  • 加载耗时、引用链和泄漏诊断。

Unity 官方文档还明确了两个约束：依赖 Bundle 必须先于主 Bundle 加载；仍被其他 Bundle 使用的依赖不能提前卸载，否则可能出现未定义行为或序列化错误。

所以“项目里有一个 Dictionary<string, AssetBundle>”还不能称为资源框架。它只解决了已加载 Bundle 的去重缓存。

三、通用的九层资源架构

一套可维护的 AB 框架可以拆成九层：

3.1 Business API：让业务只表达意图

业务层应该关心“我要哪个资源、何时释放”，不应该知道 Bundle 名、缓存路径和 CDN 地址：

这里返回的是 AssetLease<T>，而不是裸 T。裸对象无法回答“这次使用何时结束”，框架也就无法建立可靠引用关系。

句柄或 Lease 必须具备三个语义：

  • 每次业务加载得到独立持有权；
  • 多个 Lease 可以共享同一次底层加载结果；
  • Dispose / Release 幂等，但超量释放、无效访问应留下明确诊断。

YooAsset 的 AssetHandle 与 CatAsset 的 AssetHandler<T> 都体现了这一思路。CatAsset 还支持把句柄绑定到 GameObject 或 Scene 生命周期，减少业务忘记释放的概率。CatAsset 使用教程

3.2 Package 与 PlayMode：把运行环境变成显式策略

资源包 Package 是一组可以独立版本化、更新、加载和清理的内容边界。常见拆分包括：

  • Base：首包必需资源；
  • Game：核心玩法；
  • DLC：可选内容；
  • Raw：Lua、DLL、配置、视频等原生文件；
  • Mod：用户或外部工程提供的内容。

运行模式决定文件从哪里来，但不应改变业务加载接口：

模式 主要来源 典型用途
Editor Simulate AssetDatabase 或虚拟文件系统 不构建 AB 的快速开发
Offline 安装包内置目录 单机、不可热更资源
Host 内置 + 沙盒缓存 + CDN 商业项目热更新
Web 浏览器/小游戏文件系统 WebGL、小游戏平台
Custom 项目注入的文件系统 MOD、私有存储、特殊平台

编辑器直读不是加载失败后的隐式兜底，而是一种显式运行模式。否则编辑器永远成功、真机却失败，错误会被推迟到最昂贵的验证阶段。

YooAsset 3.x 把加载、下载和清理收敛到 ResourcePackage，并通过不同文件系统参数组合运行模式；这比在每个加载函数里判断 UNITY_EDITOR、本地路径和远端 URL 更容易扩展。

把静态清单和运行时数据混在一起，会带来两个问题：

  1. 版本切换时难以判断哪些字段来自构建，哪些字段被运行时修改；
  2. 测试、回滚和并发读取都更容易出现隐式状态污染。

CatAsset 的 CatAssetManifest 与 BundleRuntimeInfo / AssetRuntimeInfo 就采用了这种静态与运行时分离。CatAsset Runtime 总结

3.4 Address Resolver：地址稳定，物理布局可变

业务地址 ui/login 不应等于 Asset 路径或 Bundle 文件名。地址层负责：

稳定逻辑地址带来三项价值：

  • 资源移动、改包策略时不修改业务代码；
  • 可以按语言、画质、渠道选择变体；
  • 可以按标签计算预下载范围。

定位失败、类型不匹配、地址冲突都应直接返回结构化错误，不能静默转到 Resources 或 AssetDatabase。

3.5 File Provider：先确保文件可信，再交给 Unity

文件层回答“这个 Bundle 的可读字节在哪里”：

缓存键应基于内容身份，例如 package + hash，而不是只用逻辑文件名。否则新旧版本同名文件容易相互覆盖。

下载完成不等于文件可用。只有校验通过并原子提交后，缓存索引才能标记为 Ready。失败时保留明确错误，不能把半文件当作成功缓存。

3.6 Operation Scheduler：异步不是“到处开协程”

资源系统至少存在下载、解压、Bundle 加载、Asset 加载、场景加载、卸载六类异步操作。调度层统一处理：

  • 同键任务合并；
  • 优先级；
  • 各类型并发限制；
  • 依赖等待；
  • 调用方取消；
  • 进度聚合；
  • 超时与重试策略；
  • 主线程回调。

两个界面同时请求 ui/common_atlas 时，正确行为是“一次底层加载、两个独立 Lease”，而不是两个 LoadFromFileAsync。

取消也需要分层：调用方取消自己的等待，不应直接取消仍被其他订阅者需要的共享任务。只有所有订阅者都离开，并且底层阶段允许取消时，调度器才取消真实操作。

CatAsset 的任务系统把加载、卸载、更新建模为 Task，并显式处理依赖等待、取消、同目标合并、频率限制和优先级。这是值得独立吸收的设计，而不是某个加载 API 的附属实现。CatAsset Runtime 总结

3.7 Bundle 与 Asset Provider：分开两级缓存

Bundle 缓存与 Asset 缓存解决的是不同问题：

层级 Key Value 主要引用来源
Bundle bundleId AssetBundle Asset Provider、依赖 Bundle
Asset ResourceKey + Type UnityEngine.Object 业务 Lease、实例、场景

加载一个 Asset 的顺序应为：

  1. 从 Manifest 得到依赖 Bundle 的拓扑顺序；
  2. 并行确保无相互依赖的文件就绪；
  3. 按依赖顺序加载 Bundle；
  4. 加载主 Asset；
  5. 建立 Asset 到 Bundle 的强引用；
  6. 返回业务 Lease。

Bundle 级依赖只说明“哪个文件依赖哪个文件”。如果项目需要更早回收纹理、材质、音频等对象，还要进一步维护 Asset 级依赖。CatAsset 的特色正是精细的 Asset 级依赖管理；YooAsset 更突出 Package、Bundle 与 Handle 组成的通用商业化交付链路。

四、三条必须画清楚的主流程

4.1 启动与更新流

需要注意：

  • “发现新版本”与“激活新版本”是两步；
  • 下载未完成时，当前有效 Manifest 不能被破坏；
  • Manifest 激活应原子化，失败后仍可使用旧版本；
  • 强更、可选下载、边玩边下是产品策略，不应硬编码在文件加载器中。

YooAsset 支持先请求包版本，再加载指定版本 Manifest，并可按标签或资源对象创建下载器。YooAsset ResourcePackage API CatAsset 则支持按资源组检查和执行更新，适合把更新边界直接对应业务内容组。CatAsset 使用教程

4.2 按需加载流

状态提交要放在末尾。任何阶段失败，都应撤销本次尚未对外发布的临时引用，并返回带阶段信息的错误：

4.3 释放与回收流

不要在每次 Release 后立即执行全局回收。频繁加载/卸载同一资源会产生抖动，Resources.UnloadUnusedAssets 本身也可能造成明显卡顿。更合理的策略是：

  • Lease 归零只改变可回收状态；
  • 场景切换、加载界面或内存水位超标时统一回收；
  • 高频资源保留短暂冷却时间；
  • 紧急回收和普通回收采用不同预算。

五、引用计数不能只数 Bundle

5.1 四种不同的“引用”

至少要区分：

  1. 业务引用：调用 LoadAsync 得到的 Lease；
  2. 依赖引用：Asset A 使用材质 B，A 存活时 B 必须存活；
  3. 实例引用：Prefab 实例仍在场景中；
  4. 场景引用：Additive Scene 仍然加载。

如果只统计 Bundle 被加载了几次，框架无法判断 Bundle 内某个对象是否仍被实例、材质或场景使用。

5.2 引用沿依赖图传播

假设：

角色的业务引用从 0 -> 1 时，才给材质和 AnimatorController 各增加一次依赖引用；角色从 1 -> 0 时再撤销。角色从 1 -> 2 不应再次给整条依赖链加一遍引用。

这条规则能避免共享依赖计数被成倍放大，也让引用图具备可解释性。CatAsset 的公开教程明确采用了这一传播方式。CatAsset 使用教程

5.3 Prefab Asset 与实例不是同一生命周期

加载 Prefab 后立刻释放句柄，再把实例留在场景中，是常见泄漏或丢引用来源。框架可以提供两种明确方案：

  • InstantiateAsync 返回 InstanceLease，销毁实例时自动释放底层 Asset Lease；
  • 业务自己持有 Asset Lease，保证它覆盖所有实例的生命周期。

不要让 LoadAsync<GameObject> 同时隐式承担“加载 Prefab”和“管理所有实例”的双重语义。

六、正确理解 AssetBundle.Unload(bool)

6.1 Unload(false) 不是通用安全卸载

Unity 官方说明：调用 Unload(false) 会释放 Bundle 的追踪结构与缓冲，但已加载对象仍然存在；以后重新加载同一个 Bundle，旧对象不会重新关联，可能出现重复对象。

它适合少量明确场景，却不适合作为资源框架的默认“省内存技巧”。如果框架失去了对象与 Bundle 的关联，就更难判断何时真正回收。

6.2 Unload(true) 需要完整生命周期证明

调用 Unload(true) 会销毁从该 Bundle 加载的对象。如果仍有 UI、材质、Prefab 实例或其他 Bundle 依赖这些对象，结果就是 Missing 引用或序列化问题。

七、构建系统决定运行时上限

加载框架无法修复糟糕的打包结果。构建阶段至少要产出：

  • 稳定的 Asset 地址表；
  • Bundle 与 Asset 依赖图；
  • hash、size、CRC、加密等校验信息；
  • 标签、资源组和内置/远端分类；
  • 循环依赖、重复依赖和冗余分析报告；
  • 可与上一版本比较的增量数据。

Bundle 划分要在两个极端之间取平衡：

极端 后果
包过大 任一小改动导致大下载；加载一个对象可能长期占住大量内容
包过碎 Bundle 头、序列化缓冲、文件 IO、调度和依赖数量上升

更可操作的规则是“生命周期相近、更新频率相近、加载场景相近的资源放在一起”，再通过构建报告验证共享依赖是否被重复打包。

YooAsset 支持内置管线与 SBP、标签分包、分布式构建和自定义打包策略。YooAsset 官方仓库 CatAsset 基于 SBP，提供目录规则、资源组、补丁构建、循环依赖与冗余分析。CatAsset 官方仓库

补丁构建也有代价：CatAsset 的方案会让补丁包与正式包共存，以更小下载量换取磁盘冗余和更复杂的 Manifest 合并。它适合资源量巨大、版本日构建压力高的项目，不应默认成为所有项目的唯一构建方式。CatAsset 补丁构建

八、YooAsset 与 CatAsset 放进同一张架构图

两者都不是“只封装 AB API”，但设计着力点不同：

维度 YooAsset CatAsset 通用结论
顶层边界 ResourcePackage CatAssetManager + 资源组 先定义可独立版本化的内容边界
运行模式 Editor、Offline、Host、Web、Custom Editor、单机、可更新 来源策略必须与业务 API 解耦
更新模型 包版本、Manifest、标签/对象下载器 版本检查、资源组更新器 更新策略建立在 Manifest 差异之上
文件抽象 内置/缓存等文件系统 自动寻址到读写区、内置或远端 文件就绪是 Bundle 加载的前置阶段
异步调度 AsyncOperation 体系 TaskSystem：合并、取消、优先级、限频 同键请求必须共享底层工作
生命周期 Handle 引用计数与分析器 Handler、Asset 级依赖、对象/场景绑定 裸对象返回不足以管理生命周期
原生文件 RawFile 内置/外置原生资源与转换器 AB 与原生文件可以共享版本和下载层
构建特点 标签分包、分布式构建、可换管线 SBP、目录规则、补丁包、冗余分析 构建元数据决定运行时能力

如果直接采用成熟框架：

  • 商业化热更新、多包、多平台、边玩边下和完整交付链路，优先研究 YooAsset；
  • 想深入研究 Asset 级依赖、任务调度、补丁构建和生命周期绑定，可重点阅读 CatAsset；
  • 自研时不要复制类名和 API 表面，要复用职责划分、状态机与不变量。

九、框架必须守住的不变量

下面这些比具体 API 更重要：

  1. 同一 Manifest 版本中，一个逻辑地址只解析到一个确定资源。
  2. Bundle 交给 Unity 前，文件必须存在且校验通过。
  3. 依赖先于使用者加载，晚于使用者卸载。
  4. 同键并发请求共享底层操作，但持有权独立。
  5. 静态 Manifest 不被运行时行为修改。
  6. 引用从 0 -> 1 与 1 -> 0 时才向依赖图传播。
  7. 失败包含阶段、资源键、Bundle、来源和原始异常。
  8. 取消一个调用方不能破坏其他调用方的共享加载。
  9. 新 Manifest 未完整验证并原子激活前，旧版本仍然有效。
  10. 任何被业务使用的对象，都能追溯到仍存活的 Lease、实例或场景所有者。

只要其中一条无法证明，系统就会以某种形式表现为资源错版、重复下载、偶现 Missing、内存泄漏或无法复现的加载失败。

十、落地检查表

构建期

  • 资源地址唯一，地址与物理路径解耦
  • 生成 Asset/Bundle 依赖图和内容 hash
  • 检查循环依赖、共享依赖冗余和超大/超碎 Bundle
  • 标签、资源组、内置/远端分类可由报告复核
  • Manifest 可做版本比较、回滚和兼容性校验

启动与更新

  • 运行模式显式配置，没有失败后的隐式 Editor/Resources 兜底
  • 新 Manifest 下载、验证、激活分阶段执行
  • 文件先写临时路径，校验后原子提交
  • 强更、可选下载、边玩边下由策略层决定
  • 旧版本在新版本激活前始终可用

加载与卸载

  • 相同 Asset/Bundle 请求能够合并
  • 下载、Bundle 加载、Asset 加载分别限制并发
  • 调用方获得独立 Handle/Lease，释放幂等
  • Prefab 实例和 Additive Scene 有明确所有者
  • 依赖引用按 0 -> 1 / 1 -> 0 传播
  • 回收发生在可控安全点，不在每次 Release 后全局扫描

诊断

  • 能查看当前版本、缓存来源和文件校验状态
  • 能查看进行中的下载/加载任务、优先级和订阅者
  • 能查看 Asset/Bundle 引用计数与上下游依赖
  • 错误日志包含阶段、地址、包、Bundle、来源和异常
  • 能在真机上抓取资源快照并定位未释放所有者

十一、结语

AssetBundle 加载框架可以压缩成一句话：用 Manifest 管正确版本，用调度器管异步工作，用 Handle 管生命周期，用依赖图证明何时可以卸载。

YooAsset 展示了完整商业化资源交付系统如何围绕 Package、文件系统、Manifest、Downloader 和 Handle 组织；CatAsset 则把任务合并、Asset 级依赖、生命周期绑定和补丁构建讲得很透。把二者放在一起看，最值得借鉴的不是某个 API，而是它们都把“文件存在”“对象可用”“业务仍持有”视为三个不同阶段，并为每个阶段建立了独立状态与责任边界。
