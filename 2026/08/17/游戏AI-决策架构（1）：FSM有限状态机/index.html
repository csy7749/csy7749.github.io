游戏AI-决策架构（1）：FSM 有限状态机

Created2026-08-17|Updated2026-08-18|游戏AI决策架构
|Post Views:

FSM（Finite State Machine，有限状态机）把角色行为表达为有限个状态，以及状态之间带条件的迁移。它不负责生成长期计划，但很适合把巡逻、追击、攻击、撤退这类边界明确的行为组织成一个稳定、可观察的执行闭环。

本文假设读者熟悉 C# 接口、委托和集合。示例使用 .NET 8，可直接放进控制台项目运行；接入 Unity 时，把 Tick 放到组件更新入口，并把输出动作替换为注入的移动、技能和动画服务即可。

一、FSM 真正在管理什么

一个 FSM 至少包含四部分；这种“状态对象 + 迁移规则”的拆分也对应状态模式在游戏逻辑中的典型用法[^1]：

  • State：当前行为模式，例如 Patrol、Chase、Attack。
  • Transition：从源状态到目标状态的有向边。
  • Condition：迁移成立的条件，例如“看见敌人且距离不超过攻击范围”。
  • State Machine：保存当前状态，检查迁移，按顺序调用退出与进入逻辑。

这里最重要的不是状态框，而是箭头。FSM 的维护成本通常来自“哪些状态能切到哪些状态，以及每条边为什么成立”。状态越多、互相可达关系越密，迁移数量越接近平方增长，状态图就会比状态实现本身更难理解。

四、迁移规则放在哪里

常见做法有两种。

状态内部发起切换

在一种常见写法中，ChaseState.Update 发现距离足够近，于是直接调用 ChangeState(Attack)。代码短，但状态既要执行追击，又要知道其他状态和迁移规则，依赖会逐渐扩散。

状态机集中管理迁移

示例中的状态不知道目标状态，迁移表统一描述条件。这样更容易输出状态图、检查优先级和做数据驱动配置，代价是需要额外维护迁移集合。

工程上可以按变化来源拆分：

  • 只与当前动作完成有关的局部结果，由状态返回，例如“攻击动作完成”。
  • 影响多个状态的规则放在迁移层，例如“低血量时撤退”。
  • 感知层只更新 GuardContext，不直接调用 ChangeState。

最后一条很重要。否则视觉、听觉、伤害系统都能从外部强切状态，状态机就失去了唯一入口，切换顺序和日志也会变得不可追踪。

五、全局迁移与优先级

示例用 Source = null 表达从任意状态生效的迁移。这适合死亡、眩晕、撤退等高优先级规则，但必须定义冲突处理方式。

这里采用“列表中第一条成立的迁移获胜”。它很直观，也意味着列表顺序属于业务规则，不能把迁移存进无序集合。另一种做法是给迁移显式配置优先级，再按优先级排序；无论选哪一种，都要让冲突结果确定且可打印。

同一帧只执行一次迁移也更容易推理。如果允许连续迁移，就可能出现 Patrol -> Chase -> Attack -> Flee 在一个 Tick 内全部发生，所有状态都只调用 Enter/Exit 而没有真正执行。确实需要连续求稳态时，应把它设计成显式算法，并检测迁移环，而不是让循环悄悄发生。

六、FSM 什么时候开始失控

“状态多”不是唯一判断标准。真正危险的信号是：

  • 多个状态重复同一组进入、退出或感知逻辑。
  • 同一条规则需要复制到大量源状态。
  • 新增一个状态时，必须修改许多旧状态。
  • 状态名开始同时编码两个维度，例如 ArmedChasing、UnarmedChasing、ArmedFleeing。
  • 状态图已经无法在一张屏幕里解释清楚。

前两类问题通常指向 HFSM：把 Chase、Attack、Search 放进 Combat 父状态，共享战斗逻辑和撤退迁移。状态名同时编码多个独立维度时，则可能应该使用两个正交状态机，例如一个管理移动、一个管理武器，而不是继续增加组合状态。

七、FSM 的适用边界

FSM 很适合：

  • 敌人的小型行为闭环
  • 技能施法阶段
  • Boss 的明确阶段切换
  • 交互物、机关、任务节点和 UI 流程

《Programming Game AI by Example》也采用“状态对象 + 统一状态接口 + Agent 持有当前状态”的方式组织游戏 Agent 行为，是这类工程实现的经典参考[^2]。

FSM 不擅长：

  • 根据多个连续因素权衡当前最优行为
  • 动态生成长动作链
  • 大量层级共享和高频优先级中断

这些问题分别更接近 Utility AI、GOAP/HTN、HFSM/行为树的职责。状态机可以继续作为执行器，不必因为引入了高层决策系统就被删除。

八、自查清单

  • 每个状态是否只有一个清晰职责？
  • Enter / Update / Exit 的调用顺序是否固定？
  • 迁移冲突是否有确定的优先级规则？
  • 感知系统是否只更新上下文，而不是从外部强切状态？
  • 任意状态迁移是否集中管理并可记录原因？
  • 重复规则增多时，问题应该用 HFSM、正交状态机还是拆服务解决？
