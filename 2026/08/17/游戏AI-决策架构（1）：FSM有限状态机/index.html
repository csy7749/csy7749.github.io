游戏AI-决策架构（1）：FSM 有限状态机

Created2026-08-17|Updated2026-08-17|游戏AI决策架构
|Post Views:

FSM（Finite State Machine，有限状态机）把角色行为表达为有限个状态，以及状态之间带条件的迁移。它不负责生成长期计划，但很适合把巡逻、追击、攻击、撤退这类边界明确的行为组织成一个稳定、可观察的执行闭环。

本文假设读者熟悉 C# 接口、委托和集合。示例使用 .NET 8，可直接放进控制台项目运行；接入 Unity 时，把 Tick 放到组件更新入口，并把输出动作替换为注入的移动、技能和动画服务即可。

一、FSM 真正在管理什么

一个 FSM 至少包含四部分；这种“状态对象 + 迁移规则”的拆分也对应状态模式在游戏逻辑中的典型用法[^1]：

  • State：当前行为模式，例如 Patrol、Chase、Attack。
  • Transition：从源状态到目标状态的有向边。
  • Condition：迁移成立的条件，例如“看见敌人且距离不超过攻击范围”。
  • State Machine：保存当前状态，检查迁移，按顺序调用退出与进入逻辑。

守卫 NPC 可以画成下面这张状态图：

Patrol --发现敌人--> Chase --进入射程--> Attack
   ^                    ^                   |
   |                    +----离开射程-------+
   +------丢失敌人------+

任意状态 --低血量--> Flee --恢复安全--> Patrol
```text

这里最重要的不是状态框，而是箭头。FSM 的维护成本通常来自“哪些状态能切到哪些状态，以及每条边为什么成立”。状态越多、互相可达关系越密，迁移数量越接近平方增长，状态图就会比状态实现本身更难理解。

## 二、进入、更新、退出的边界

状态通常有三个生命周期方法：

```text
Enter  只执行一次：启动导航、播放起始动画、订阅事件
Update 持续执行：推进移动、瞄准、攻击或等待
Exit   只执行一次：停止旧动作、释放占用、取消订阅
```text

迁移时应保持固定顺序：

```text
检查迁移条件 -> Exit(旧状态) -> 切换当前状态 -> Enter(新状态) -> Update(新状态)
```text

如果先进入新状态再退出旧状态，旧状态的清理逻辑可能把新状态刚启动的导航或动画一起停止。顺序是状态机的契约，不能留给每个状态自行决定。

## 三、一个可运行的守卫 FSM

下面的实现把状态行为和迁移规则分开：状态只执行动作，`Transition` 只描述切换条件。迁移列表的顺序就是优先级，因此“低血量撤退”放在最前面，能覆盖普通战斗迁移。

```csharp
using System;
using System.Collections.Generic;
using System.Linq;

public enum GuardState
{
    Patrol,
    Chase,
    Attack,
    Flee
}

public sealed record GuardContext(
    bool EnemyVisible,
    float DistanceToEnemy,
    bool LowHealth);

public interface IState
{
    void Enter();
    void Update(GuardContext context);
    void Exit();
}

public sealed class ConsoleState : IState
{
    private readonly string _name;

    public ConsoleState(string name)
    {
        _name = name;
    }

    public void Enter() => Console.WriteLine($"Enter {_name}");

    public void Update(GuardContext context)
    {
        Console.WriteLine($"Update {_name}, distance={context.DistanceToEnemy}");
    }

    public void Exit() => Console.WriteLine($"Exit {_name}");
}

public sealed record Transition(
    GuardState? Source,
    GuardState Target,
    Func<GuardContext, bool> Condition)
{
    public bool Applies(GuardState current, GuardContext context)
    {
        return (Source is null || Source == current) && Condition(context);
    }
}

public sealed class StateMachine
{
    private readonly IReadOnlyDictionary<GuardState, IState> _states;
    private readonly IReadOnlyList<Transition> _transitions;
    private GuardState _current;

    public StateMachine(
        IReadOnlyDictionary<GuardState, IState> states,
        IReadOnlyList<Transition> transitions,
        GuardState initialState)
    {
        _states = states;
        _transitions = transitions;
        _current = initialState;
        _states[_current].Enter();
    }

    public void Tick(GuardContext context)
    {
        var transition = _transitions.FirstOrDefault(
            item => item.Applies(_current, context));

        if (transition is not null && transition.Target != _current)
        {
            ChangeState(transition.Target);
        }

        _states[_current].Update(context);
    }

    private void ChangeState(GuardState target)
    {
        Console.WriteLine($"Transition: {_current} -> {target}");
        _states[_current].Exit();
        _current = target;
        _states[_current].Enter();
    }
}

public static class Program
{
    private const float AttackRange = 2.0f;

    public static void Main()
    {
        var states = CreateStates();
        var transitions = CreateTransitions();
        var machine = new StateMachine(states, transitions, GuardState.Patrol);

        var frames = new[]
        {
            new GuardContext(false, 10.0f, false),
            new GuardContext(true, 8.0f, false),
            new GuardContext(true, 1.5f, false),
            new GuardContext(true, 1.5f, true),
            new GuardContext(false, 10.0f, false)
        };

        foreach (var frame in frames)
        {
            machine.Tick(frame);
        }
    }

    private static IReadOnlyDictionary<GuardState, IState> CreateStates()
    {
        return new Dictionary<GuardState, IState>
        {
            [GuardState.Patrol] = new ConsoleState("Patrol"),
            [GuardState.Chase] = new ConsoleState("Chase"),
            [GuardState.Attack] = new ConsoleState("Attack"),
            [GuardState.Flee] = new ConsoleState("Flee")
        };
    }

    private static IReadOnlyList<Transition> CreateTransitions()
    {
        return new List<Transition>
        {
            new(null, GuardState.Flee, context => context.LowHealth),
            new(GuardState.Flee, GuardState.Patrol, context => !context.LowHealth),
            new(GuardState.Patrol, GuardState.Chase, context => context.EnemyVisible),
            new(GuardState.Chase, GuardState.Patrol, context => !context.EnemyVisible),
            new(GuardState.Chase, GuardState.Attack, IsInAttackRange),
            new(GuardState.Attack, GuardState.Chase, IsOutsideAttackRange)
        };
    }

    private static bool IsInAttackRange(GuardContext context)
    {
        return context.EnemyVisible && context.DistanceToEnemy <= AttackRange;
    }

    private static bool IsOutsideAttackRange(GuardContext context)
    {
        return !context.EnemyVisible || context.DistanceToEnemy > AttackRange;
    }
}
```text

运行时能看到完整的生命周期顺序：

```text
Enter Patrol
Update Patrol, distance=10
Transition: Patrol -> Chase
Exit Patrol
Enter Chase
Update Chase, distance=8
Transition: Chase -> Attack
Exit Chase
Enter Attack
Update Attack, distance=1.5
Transition: Attack -> Flee
Exit Attack
Enter Flee
Update Flee, distance=1.5
Transition: Flee -> Patrol
Exit Flee
Enter Patrol
Update Patrol, distance=10
```text

## 四、迁移规则放在哪里

常见做法有两种。

### 状态内部发起切换

在一种常见写法中，`ChaseState.Update` 发现距离足够近，于是直接调用 `ChangeState(Attack)`。代码短，但状态既要执行追击，又要知道其他状态和迁移规则，依赖会逐渐扩散。

### 状态机集中管理迁移

示例中的状态不知道目标状态，迁移表统一描述条件。这样更容易输出状态图、检查优先级和做数据驱动配置，代价是需要额外维护迁移集合。

工程上可以按变化来源拆分：

- 只与当前动作完成有关的局部结果，由状态返回，例如“攻击动作完成”。
- 影响多个状态的规则放在迁移层，例如“低血量时撤退”。
- 感知层只更新 `GuardContext`，不直接调用 `ChangeState`。

最后一条很重要。否则视觉、听觉、伤害系统都能从外部强切状态，状态机就失去了唯一入口，切换顺序和日志也会变得不可追踪。

## 五、全局迁移与优先级

示例用 `Source = null` 表达从任意状态生效的迁移。这适合死亡、眩晕、撤退等高优先级规则，但必须定义冲突处理方式。

这里采用“列表中第一条成立的迁移获胜”。它很直观，也意味着列表顺序属于业务规则，不能把迁移存进无序集合。另一种做法是给迁移显式配置优先级，再按优先级排序；无论选哪一种，都要让冲突结果确定且可打印。

同一帧只执行一次迁移也更容易推理。如果允许连续迁移，就可能出现 `Patrol -> Chase -> Attack -> Flee` 在一个 Tick 内全部发生，所有状态都只调用 `Enter/Exit` 而没有真正执行。确实需要连续求稳态时，应把它设计成显式算法，并检测迁移环，而不是让循环悄悄发生。

## 六、FSM 什么时候开始失控

“状态多”不是唯一判断标准。真正危险的信号是：

- 多个状态重复同一组进入、退出或感知逻辑。
- 同一条规则需要复制到大量源状态。
- 新增一个状态时，必须修改许多旧状态。
- 状态名开始同时编码两个维度，例如 `ArmedChasing`、`UnarmedChasing`、`ArmedFleeing`。
- 状态图已经无法在一张屏幕里解释清楚。

前两类问题通常指向 HFSM：把 `Chase`、`Attack`、`Search` 放进 `Combat` 父状态，共享战斗逻辑和撤退迁移。状态名同时编码多个独立维度时，则可能应该使用两个正交状态机，例如一个管理移动、一个管理武器，而不是继续增加组合状态。

## 七、FSM 的适用边界

FSM 很适合：

- 敌人的小型行为闭环
- 技能施法阶段
- Boss 的明确阶段切换
- 交互物、机关、任务节点和 UI 流程

《Programming Game AI by Example》也采用“状态对象 + 统一状态接口 + Agent 持有当前状态”的方式组织游戏 Agent 行为，是这类工程实现的经典参考[^2]。

FSM 不擅长：

- 根据多个连续因素权衡当前最优行为
- 动态生成长动作链
- 大量层级共享和高频优先级中断

这些问题分别更接近 Utility AI、GOAP/HTN、HFSM/行为树的职责。状态机可以继续作为执行器，不必因为引入了高层决策系统就被删除。

## 八、自查清单

- 每个状态是否只有一个清晰职责？
- `Enter / Update / Exit` 的调用顺序是否固定？
- 迁移冲突是否有确定的优先级规则？
- 感知系统是否只更新上下文，而不是从外部强切状态？
- 任意状态迁移是否集中管理并可记录原因？
- 重复规则增多时，问题应该用 HFSM、正交状态机还是拆服务解决？
