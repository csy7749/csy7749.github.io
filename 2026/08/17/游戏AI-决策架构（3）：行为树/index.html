游戏AI-决策架构（3）：行为树

Created2026-08-17|Updated2026-08-17|游戏AI决策架构
|Post Views:

行为树（Behavior Tree）把 AI 行为组织成可组合节点，并用 Success、Failure、Running 三种结果驱动控制流。它特别适合持续重新评估威胁、按优先级选择分支，以及把复杂战斗逻辑拆成可复用子树。

本文假设读者理解基本的树结构和 C# 接口。示例使用 .NET 8，实现一棵响应式守卫行为树；重点不是可视化编辑器，而是编辑器背后必须稳定成立的 Tick、中断和状态语义。

一、行为树和状态机看问题的角度不同

FSM 首先问：

我当前处于哪个状态？什么条件会让我切到另一个状态？
```text

行为树首先问：

```text
从根节点开始，这一帧哪条分支能够执行？执行到哪里还没结束？
```text

同一个守卫逻辑可以写成：

```text
Priority Selector
├── Sequence: 撤退
│   ├── Condition: 低血量
│   └── Action: 逃离
├── Sequence: 战斗
│   ├── Condition: 看见敌人
│   └── Selector
│       ├── Sequence: 攻击
│       │   ├── Condition: 位于攻击距离
│       │   └── Action: 攻击
│       └── Action: 追击
└── Action: 巡逻
```text

根节点从高到低检查分支。低血量时先撤退；否则看见敌人就攻击或追击；前两条都不适用时巡逻。优先级直接体现在树的排列顺序中，不需要画出每个动作到其他动作的迁移箭头。

## 二、三个返回状态是行为树的协议

每个节点 Tick 后必须返回一种状态：

| 状态 | 含义 | 例子 |
| :--- | :--- | :--- |
| `Success` | 节点已经成功完成 | 已经抵达目标点 |
| `Failure` | 当前条件下无法完成 | 没有看见敌人 |
| `Running` | 节点尚未结束，需要继续 Tick | 正在移动或播放技能 |

其中，`Failure` 不是程序异常，而是正常控制流。条件节点返回失败，父节点就可以尝试其他分支。真正的异常，例如导航服务没有初始化，不应该伪装成 `Failure`；它应明确抛错或写入错误日志，否则树只会悄悄换一条分支，根因很难发现。

行为树在游戏与机器人系统中常用同一组三值状态和组合节点语义。Colledanchise 与 Ögren 对这种模块化控制结构、反应性和组合方式做了系统整理[^1]。

## 三、Selector 与 Sequence

### Selector：找到第一个可用分支

Selector 从左到右 Tick 子节点：

```text
遇到 Failure -> 尝试下一个
遇到 Success -> 立即返回 Success
遇到 Running -> 立即返回 Running
全部 Failure -> 返回 Failure
```text

它表达“或者”：撤退不可用就尝试战斗，战斗不可用就巡逻。

### Sequence：按顺序完成全部步骤

Sequence 从左到右 Tick 子节点：

```text
遇到 Success -> 继续下一个
遇到 Failure -> 立即返回 Failure
遇到 Running -> 立即返回 Running
全部 Success -> 返回 Success
```text

它表达“并且按顺序”：先确认看见敌人，再执行追击或攻击。

Selector 和 Sequence 都不是业务动作。它们只编排子节点的执行顺序，因此可以反复组合，形成更大的战术子树。

## 四、一个可运行的响应式行为树

下面实现四类最小节点：条件、动作、Sequence、Selector。组合节点每次 Tick 都从第一个子节点重新检查，因此高优先级条件变化后能立即抢占低优先级分支。

```csharp
using System;
using System.Collections.Generic;

public enum NodeStatus
{
    Success,
    Failure,
    Running
}

public sealed record GuardContext(
    bool EnemyVisible,
    float DistanceToEnemy,
    bool LowHealth);

public interface INode
{
    NodeStatus Tick(GuardContext context);
}

public sealed class ConditionNode : INode
{
    private readonly Func<GuardContext, bool> _condition;

    public ConditionNode(Func<GuardContext, bool> condition)
    {
        _condition = condition;
    }

    public NodeStatus Tick(GuardContext context)
    {
        return _condition(context) ? NodeStatus.Success : NodeStatus.Failure;
    }
}

public sealed class ActionNode : INode
{
    private readonly Func<GuardContext, NodeStatus> _action;

    public ActionNode(Func<GuardContext, NodeStatus> action)
    {
        _action = action;
    }

    public NodeStatus Tick(GuardContext context) => _action(context);
}

public sealed class SequenceNode : INode
{
    private readonly IReadOnlyList<INode> _children;

    public SequenceNode(IReadOnlyList<INode> children)
    {
        _children = children;
    }

    public NodeStatus Tick(GuardContext context)
    {
        foreach (var child in _children)
        {
            var status = child.Tick(context);
            if (status != NodeStatus.Success)
            {
                return status;
            }
        }

        return NodeStatus.Success;
    }
}

public sealed class SelectorNode : INode
{
    private readonly IReadOnlyList<INode> _children;

    public SelectorNode(IReadOnlyList<INode> children)
    {
        _children = children;
    }

    public NodeStatus Tick(GuardContext context)
    {
        foreach (var child in _children)
        {
            var status = child.Tick(context);
            if (status != NodeStatus.Failure)
            {
                return status;
            }
        }

        return NodeStatus.Failure;
    }
}

public static class Program
{
    private const float AttackRange = 2.0f;

    public static void Main()
    {
        var tree = CreateTree();
        RunFrame(tree, new GuardContext(false, 10.0f, false));
        RunFrame(tree, new GuardContext(true, 8.0f, false));
        RunFrame(tree, new GuardContext(true, 1.5f, false));
        RunFrame(tree, new GuardContext(true, 1.5f, true));
    }

    private static INode CreateTree()
    {
        var flee = new SequenceNode(new INode[]
        {
            new ConditionNode(context => context.LowHealth),
            new ActionNode(Flee)
        });

        var engage = new SequenceNode(new INode[]
        {
            new ConditionNode(context => context.EnemyVisible),
            new SelectorNode(new INode[] { CreateAttack(), new ActionNode(Chase) })
        });

        return new SelectorNode(new INode[]
        {
            flee,
            engage,
            new ActionNode(Patrol)
        });
    }

    private static INode CreateAttack()
    {
        return new SequenceNode(new INode[]
        {
            new ConditionNode(context => context.DistanceToEnemy <= AttackRange),
            new ActionNode(Attack)
        });
    }

    private static void RunFrame(INode tree, GuardContext context)
    {
        var result = tree.Tick(context);
        Console.WriteLine($"Tree result: {result}");
    }

    private static NodeStatus Flee(GuardContext context)
    {
        Console.WriteLine("Flee");
        return NodeStatus.Running;
    }

    private static NodeStatus Chase(GuardContext context)
    {
        Console.WriteLine($"Chase, distance={context.DistanceToEnemy}");
        return NodeStatus.Running;
    }

    private static NodeStatus Attack(GuardContext context)
    {
        Console.WriteLine("Attack");
        return NodeStatus.Success;
    }

    private static NodeStatus Patrol(GuardContext context)
    {
        Console.WriteLine("Patrol");
        return NodeStatus.Running;
    }
}
```text

输出对应四种上下文：

```text
Patrol
Tree result: Running
Chase, distance=8
Tree result: Running
Attack
Tree result: Success
Flee
Tree result: Running
```text

第四帧中，即使上一帧正在攻击，根 Selector 也会重新检查第一条撤退分支。低血量条件成立后，撤退立即获得执行权。这就是响应式行为树的核心价值。

## 五、Running 节点必须有中断协议

示例中的动作没有持有资源，只打印结果。真实项目的 `Chase` 可能启动寻路，`Attack` 可能锁定朝向、占用技能槽并等待动画事件。高优先级分支抢占时，旧动作不能只是“不再被 Tick”，还需要收到明确的 `Abort`：

```text
Chase.Abort()
  -> CancelPathRequest()
  -> ReleaseMovementLock()
  -> ClearTemporaryTarget()
```text

完整节点协议通常至少包含：

```text
OnEnter   第一次被激活
OnTick    继续推进
OnExit    正常以 Success 或 Failure 结束
OnAbort   被其他分支抢占
```text

不区分正常结束和中断，会出现残留导航、技能重复回调、动画锁没有释放等问题。行为树编辑器能画出节点，但不能替代这套运行时契约。

## 六、响应式节点与记忆型节点

示例中的 Sequence 和 Selector 每帧都从第一个子节点开始，属于响应式实现。它的优点是条件变化能立刻生效，缺点是前面的成功节点也会重复执行。

另一类实现会记住上次返回 `Running` 的子节点，下次直接从那里继续：

```text
Memory Sequence
Tick 1: Child 0 Success, Child 1 Running -> 记住索引 1
Tick 2: 直接 Tick Child 1
```text

记忆型节点适合线性任务，例如“走到门口 -> 开门 -> 进入房间”，但它不会自动重查前置条件。若走路过程中门被锁上，任务可能仍沿旧路径执行。

工程上常见组合是：

- 根部用响应式 Selector，持续检查死亡、眩晕、撤退等高优先级条件。
- 战术分支用响应式 Sequence，确保目标和距离仍然有效。
- 动作内部用记忆状态推进异步操作。
- 明确配置哪些条件变化会触发 Abort。

BehaviorTree.CPP 的基础文档也强调节点状态与异步动作的停止语义，尤其要求长时间运行的动作能够被安全中止[^2]。

## 七、Decorator、Service 与 Blackboard

最小行为树有四类节点就能工作，工程框架通常还会增加三组能力。

### Decorator

Decorator 包裹一个子节点，改变它的执行条件或返回结果：

- `Inverter`：交换 Success 和 Failure
- `Repeat`：重复执行
- `Cooldown`：冷却期间直接失败
- `Timeout`：超过时限后中止

Decorator 适合表达通用控制规则，不应该塞入具体战斗业务。

### Service

Service 在某个分支活跃时周期更新数据，例如刷新最近掩体或敌人距离。它可以减少全树每帧重复计算，但要避免让 Service 直接触发动作；它仍然应该只更新决策所需的事实。

### Blackboard

Blackboard 是树与感知、动作之间共享的数据面。适合保存：

- 当前目标与最后已知位置
- 自身血量、弹药和技能冷却
- 是否看见敌人、是否存在可用掩体
- 当前命令和小队信息

不适合保存为了“让树走到某条线”而制造的控制标记，例如 `ShouldRunSecondAttackBranch`。这类字段会把控制流从树结构藏进数据，调试时既看不懂树，也看不懂 Blackboard。

## 八、事件驱动不是静默跳过 Tick

大型行为树如果每帧从根遍历所有条件，会产生重复计算。优化方向包括：

- 降低整棵树的 Tick 频率
- 缓存昂贵感知结果
- 只让活跃分支更新 Service
- 条件依赖的 Blackboard Key 变化时触发重新评估

Unreal Engine 的行为树实现采用事件驱动思路，并通过 Blackboard Observer 触发条件变化后的分支重评估，以减少无意义的逐帧检查[^3]。

这里不能把“事件驱动”实现成条件变化后静默修改当前节点。事件应该请求树在统一入口重新仲裁，并输出中断原因；否则优化会破坏原本确定的优先级语义。

## 九、行为树什么时候比 HFSM 更合适

行为树更适合：

- 行为由大量条件分支和优先级组成
- 需要持续检查高优先级中断
- 子行为希望复用为独立子树
- 策划或设计师需要可视化编排
- 动作天然以 Success、Failure、Running 汇报结果

HFSM 更适合：

- 行为存在稳定的模式与子模式
- 状态生命周期比条件组合更重要
- 切换关系明确且数量可控
- 需要保持父状态上下文和历史子状态

两者可以组合。高层 HFSM 管理 `Peace / Combat / Dead` 模式，`Combat` 内部运行一棵战斗行为树；也可以由行为树的动作节点启动一个技能状态机。组合时要规定唯一的所有者，避免两个系统都认为自己有权中断同一个动作。

## 十、调试信息至少要包含什么

一棵可维护的行为树至少能显示：

- 本次 Tick 经过的节点路径
- 每个节点返回的状态
- 当前 Running 节点
- Blackboard 关键值
- 哪个条件触发了中断
- 被 Abort 的节点和清理结果

典型日志可以是：

```text
Root/Combat/Attack: Running
Blackboard.LowHealth: false -> true
Abort: Root/Combat/Attack
Select: Root/Flee
Root/Flee: Running
```text

只高亮当前节点而不记录选择原因，复杂树仍然难以定位问题。

## 十一、自查清单

- 每个节点是否严格遵守 Success、Failure、Running 语义？
- 高优先级条件变化后，树是否会重新仲裁？
- Running 动作被抢占时，是否执行明确的 Abort 清理？
- 响应式与记忆型节点是否被区分，而不是混用同一个名字？
- Blackboard 是否保存事实，而不是隐藏控制流？
- 昂贵感知是否缓存或事件化，同时保留可追踪的中断入口？
- 行为树、状态机、技能和移动系统之间是否只有一个动作所有者？
