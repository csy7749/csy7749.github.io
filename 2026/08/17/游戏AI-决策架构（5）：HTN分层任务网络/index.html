游戏AI-决策架构（5）：HTN 分层任务网络

Created2026-08-17|Updated2026-08-18|游戏AI决策架构
|Post Views:

HTN（Hierarchical Task Network，分层任务网络）从高层任务出发，根据当前世界状态选择 Method，逐层拆解 Compound Task，最终生成可执行的 Primitive Task 序列。它适合步骤较长、领域套路明确，同时又需要根据局势选择不同执行方案的游戏 AI。

本文假设读者熟悉 C# 继承、委托、不可变记录和集合。示例使用 .NET 8，实现一个支持 Method 回溯、规划期状态效果和完整展开轨迹的总序 HTN Planner，可以直接放进控制台项目运行。

一、HTN 解决什么问题

守卫 NPC 接到 DefendArea 任务后，可能面对不同情况：

FSM 可以为每一步建立状态，行为树可以把所有分支画出来，GOAP 可以在动作状态空间中搜索。HTN 采用另一种思路：把设计者已经知道的领域套路写成任务分解规则。

规划器根据世界状态选择一条可用 Method，再继续展开其中的复合任务。Game AI Pro 的 HTN 示例正是通过 Task、Method、Operator 与规划期效果解释这种领域驱动的计划生成方式[^1]。

二、四个核心概念

Compound Task

复合任务表示一个高层意图，不能直接执行，例如：

  • DefendArea
  • EngageEnemy
  • GatherResources
  • CapturePoint

它持有一组候选 Method，规划器要根据条件选择分解方式。

Method

Method 是复合任务的一种拆解方案，由两部分组成：

  • Condition：该方案何时可用。
  • Subtasks：选中后展开成哪些子任务。

Method 的排列顺序通常也是领域策略：先尝试更具体、更理想的方案，失败后回溯到其他方案。

Primitive Task

原子任务是规划器不再继续拆解的最小任务。它通常包含：

  • 执行前提
  • 规划期效果
  • 运行时 Operator 或执行器标识

例如，MoveToEnemy 是一个 Primitive Task，但它并不意味着 Planner 自己控制角色移动。Planner 只输出任务，Executor 再调用 NavMesh 或移动系统。

六、Method 顺序就是领域策略

当多个 Method 条件同时成立，排在前面的方案获胜。这种顺序让设计结果可控，但也意味着调整顺序会直接改变行为。

条件应该尽量表达方案的适用前提，不要把全部可行性都塞进 Method Condition。Primitive Task 仍要验证自己的前提，因为子任务执行所需条件可能由前面任务的效果产生。

生产框架应记录：

  • 哪些 Method 条件不成立
  • 哪个子任务导致 Method 失败
  • 回溯后尝试了哪个 Method
  • 最终为什么没有计划

Guerrilla Games 对 Decima HTN 的介绍专门展示了回溯流程可视化，因为仅显示最终计划无法解释规划器为何跳过某条分解路径[^2]。

七、规划成功不等于执行成功

Planner 使用的是抽象预测状态，真实世界可能在执行期间变化：

  • 角色接近敌人时，敌人已经离开。
  • 药品在执行前被其他系统消耗。
  • 目标死亡或导航路径失效。
  • 角色被眩晕，当前任务无法继续。

因此 Executor 需要在每个 Primitive Task 执行前重新验证条件，并明确报告：

不要让 Primitive Task 的规划期 Effect 直接修改真实 World State。预测效果只服务于 Planner，真实状态只能由实际动作结果更新。

八、什么时候触发重规划

每帧重新展开完整 HTN 通常没有必要。常见触发点包括：

  • 当前 Primitive Task 前提失效
  • 当前任务执行失败
  • 根目标或高层命令改变
  • 关键世界状态发生结构性变化
  • 当前计划完成

重规划需要预算。大量 Agent 同时失败时，可以进入 Planner 队列，按优先级或时间片处理。但预算规则必须显式：队列等待、超时和无计划状态都要可观察，不能让 Agent 静默停住。

核心模型 Task + Method Action + Precondition + Effect + Cost
计划来源 领域知识分解 状态空间搜索

HTN 适合“这类问题已有可靠套路，但要根据局势选择套路”；GOAP 适合“给出动作能力，让系统寻找达成目标的路径”。两者都需要世界状态和动作执行器，但计划生成机制不同。

十一、领域建模的常见坑

Method 条件过宽

多个 Method 总是同时成立，行为完全依赖列表顺序，条件失去解释力。

Method 条件过窄

真实可行方案被提前排除，Planner 经常返回无计划。

Primitive Task 粒度不一致

一部分任务是“完成整场战斗”，另一部分任务是“转身 10 度”，Planner 很难在同一层组合和预测。

Effect 与真实动作不一致

规划认为 MoveToEnemy 必然进入射程，但实际导航可能被阻挡。Effect 是预期结果，不是成功保证，Executor 仍要验证。

递归分解没有终止条件

Compound Task 通过 Method 再次展开自身，却没有让状态更接近终止条件，会造成无限递归。框架应记录展开栈并明确报告循环。

Planner 接管表现细节

HTN 应规划“治疗”或“移动到掩体”，不应规划每个动画状态和粒子效果。表现细节交给执行层。

十二、适用场景与边界

HTN 适合：

  • SLG 中的集结、行军、占点和防守。
  • RPG 中的任务链、生活行为和剧情角色流程。
  • 小队指挥、角色分工和协同战术。
  • 采集、制作、运输、建设等长链行为。
  • 需要动态选择方案，同时保持设计可控性的 AI。

Guerrilla Games 的 Killzone 2 多人 Bot 架构使用 HTN Planner，并把 Commander、Squad 与单兵 AI 结合用于动态战术行为[^3]。

HTN 不适合：

  • 只有少量明确状态的小型敌人。
  • 主要问题是当前技能评分，而不是多步任务。
  • 团队无法维护 Domain、Method 和调试工具。
  • 世界变化速度远高于计划执行速度，计划持续失效。
  • 希望动作自由组合，不愿预先提供任务分解结构。

十三、调试工具应该显示什么

至少显示：

  • 当前根任务和输入 World State
  • Compound Task 的 Method 尝试顺序
  • 每个 Method 的条件结果
  • Primitive Task 前提和规划期 Effect
  • 当前展开栈、失败点和回溯路径
  • 最终计划与执行进度
  • 计划失效和重规划原因

Decima 的 HTN 资料展示了把回溯流程生成并可视化的实现方向，说明 HTN 调试不仅需要看结果，还要看 Planner 如何得到结果[^2]。

十四、自查清单

  • Compound Task、Method、Primitive Task 的职责是否明确？
  • Method 顺序是否代表清晰的领域策略？
  • Primitive Task 是否声明前提和规划期效果？
  • Planner 是否在预测状态上应用效果，而不修改真实世界？
  • 子任务失败后是否会回溯尝试其他 Method？
  • Executor 是否在运行前重新验证任务前提？
  • 计划失败、中断和重规划是否有明确状态？
  • 日志能否还原 Method 选择、失败点和回溯路径？
  • Domain 中是否存在无终止条件的递归分解？
