Unity UGUI架构（3）：MVC与MVVM对比

Created2026-08-17|Updated2026-08-17|UnityUGUI
|Post Views:

MVC 与 MVVM 没有“旧架构”和“新架构”的胜负关系。MVC 强调显式协调，MVVM 强调界面状态映射与持续绑定。本文用同一个 UGUI 背包界面比较两者的数据流、依赖、测试、性能与团队成本，并给出可直接用于项目评审的选型方法。

本文假设读者已经了解 MVC 与 MVVM 的基本角色。重点不是重复定义，而是回答三个工程问题：它们真正差在哪里、什么场景下差异会产生价值、项目应该如何选择。

一、先给结论

不要因为 MVVM 自动化程度更高就默认它更先进。自动绑定节省的是重复同步代码，付出的是基础设施、生命周期、调试链路和学习成本。

二、两者解决的问题并不完全相同

MVC 的中心是一次交互流程，MVVM 的中心是一份可观察的界面状态。这一差异可以从 MVC 与 Presentation Model 的 GUI 架构演进中得到更完整的背景，也决定了两者各自擅长的复杂度。

三、同一个操作的数据流对比

仍以“点击按钮，把背包数量从 0 增加到 1”为例。

MVC

每一步都是显式方法调用。开发者可以沿 Controller 断点观察完整路径。uGUI 基于 MonoBehaviour 与可配置事件回调的工作方式，使这种显式协调很容易接入现有 Prefab（参见 uGUI 迁移说明）。

MVVM

链路更长，但当 Quantity 同时影响数量文本、上限提示、按钮交互态和颜色时，ViewModel 可以统一表达这些派生状态，Binding 自动更新对应控件。示例中的 PropertyChanged 采用 .NET 的标准 INotifyPropertyChanged 契约，但具体 Binder 仍是 UGUI 项目自行实现的基础设施。

四、核心差异表

维度 MVC MVVM
主要抽象 用户操作与协调流程 可观察的界面状态
View 更新方式 Controller 显式调用 Binding 响应属性变化
输入处理 View 事件交给 Controller Binding 触发 ViewModel 命令
View 状态转换 Controller 或 View Formatter 集中在 ViewModel
调用链 短、显式 长、部分由绑定系统驱动
样板代码 多个手写刷新方法 多个属性通知与绑定声明
基础设施 少 多，需要 Binding/Command/Lifecycle
单元测试重点 Model 规则、Controller 协调 Model 规则、ViewModel 状态输出
多字段联动 容易让 Controller 膨胀 ViewModel 更自然
简单页面成本 低 较高
大量同类页面 重复协调代码增多 Binder 成熟后复用更强
高频更新风险 手动全量刷新 通知风暴、装箱与订阅开销
常见失控点 Fat Controller God ViewModel、隐式绑定

五、优缺点不是孤立的

MVC 的“显式”既是优点也是成本

显式调用让调试简单，但每个新字段都要补一条刷新路径。页面小时这是可控性，页面大时就是重复劳动。

MVVM 的“自动”既是优点也是成本

属性变化自动传播能减少漏刷，但一次更新经过更多中间层。没有绑定追踪和生命周期规范时，自动化会变成隐式行为。

MVC 更怕横向扩张

当同一状态影响多个页面时，Controller 之间容易形成点对点通知。此时应先引入共享状态服务，而不是让 Controller 互相引用。

MVVM 更怕纵向堆叠

为了完整自动绑定，项目可能继续增加基类、命令、转换器、验证器、反射、代码生成和容器。如果每一层都没有解决真实重复，复杂度会超过页面本身。

六、按项目场景选择

原型、Game Jam、独立游戏

优先 MVC，甚至只使用明确分层的 Presenter/Controller 即可。此阶段需求变化快，最重要的是让业务规则离开 View，而不是先搭完整绑定系统。

中小型商业项目

菜单、设置、结算、商店等页面可以使用 MVC。对字段联动明显的养成或背包页面，可以局部使用 ViewModel，不需要全项目强制统一成 MVVM。

长线运营项目

活动、任务、邮件、商城和礼包页面结构相似，字段多且状态来源复杂。稳定的 MVVM 绑定、通用组件和生成工具能产生复用价值，但前提是团队愿意维护工具链。

重 UI 的模拟经营、卡牌、SLG

这类项目通常有大量表格、筛选、资源联动、红点、倒计时和服务器状态。MVVM 更适合表达派生 UI 状态，业务规则仍应留在领域服务，不要全部放进 ViewModel。

动作、射击游戏的战斗 HUD

不应只按“项目很大”选择 MVVM。血量、准星、弹药和目标标记可能高频变化，手写 Presenter/MVC 更新有时更直接、更容易控制频率。低频菜单与高频 HUD 可以采用不同方案。

Unity 编辑器工具

如果使用传统 UGUI 做运行时工具面板，复杂表单适合 MVVM；如果项目使用 UI Toolkit，应单独评估其原生数据绑定能力，不能把 UI Toolkit 的结论直接套到 UGUI（参见 Unity UI 系统对比）。

一个数据变化是否会影响多个控件？ +1
是否有大量结构相似的表单或列表页？ +1

团队是否已有可调试的绑定和生命周期设施？ +1
UI 数据是否以低频离散变化为主？ +1

再看下面的反向条件：

问题 是则 MVC +1
页面是否只有少量按钮和文本？ +1
操作流程是否比持续状态同步更复杂？ +1
是否需要严格控制每次刷新时机？ +1
团队是否缺少绑定框架维护经验？ +1
是否处于快速验证或频繁推翻阶段？ +1

分数不是自动决策器。它的作用是把争论从“喜欢哪种架构”转成“项目正在承受哪种复杂度”。

八、按页面而不是按项目一刀切

同一个项目完全可以这样组合：

模块 推荐方式 原因
登录、暂停、确认弹窗 MVC 交互少，流程明确
角色养成、装备对比 MVVM 派生属性和联动字段多
战斗 HUD Presenter/MVC 高频数据，需要精确刷新控制
商城与活动页 MVVM 同类页面多，绑定可复用
剧情对话 状态机 + View 核心复杂度在流程，不在数据绑定
通用列表 Item 轻量 Binder 重复渲染多，适合抽取绑定

架构边界可以按功能模块划分，但同一模块内部必须保持一致。一个页面同时存在 Controller 手动刷新、View 自己读 Model、Binder 自动刷新三条路径，会制造多事实源和重复更新。

十、测试策略对比

MVC 应重点测试什么

  • Model 是否正确执行领域规则。
  • Controller 收到操作后是否调用正确用例。
  • Model 变化后是否让 View 渲染正确参数。
  • Dispose 后是否不再响应事件。

MVVM 应重点测试什么

  • Model 状态能否映射成正确的 ViewModel 属性。
  • 派生属性是否一起变化。
  • 命令是否满足可执行条件并调用正确用例。
  • 属性未变化时是否避免重复通知。
  • Bind/Unbind 后控件和属性事件是否保持对称。

MVC 测试更偏交互协作，MVVM 测试更偏状态映射。两者都不能用 UI 架构测试替代真正的业务规则测试。

十一、性能对比

架构名称本身不会决定帧率，具体更新策略才会。

MVC 的性能风险

  • Controller 为方便而每次全量刷新页面。
  • 多个 Model 事件在一帧内触发重复 Render。
  • View 刷新导致不必要的 Layout Rebuild。

MVVM 的性能风险

  • 高频属性产生通知风暴。
  • 通用绑定使用反射、字符串和装箱。
  • 集合变化后全量重建列表。
  • 响应式链产生闭包和临时对象。

两者都应遵循相同原则：值未变化不通知、按变化粒度刷新、列表差量更新、高频 HUD 专门处理，并通过 Profiler 验证而不是凭架构名称判断。

十二、迁移路径

从杂乱 View 脚本迁移到 MVC

从 MVC 逐步迁移到 MVVM

不需要一次改写所有页面。优先选择联动最多、最容易漏刷、测试价值最高的页面验证收益。

十三、选型时最容易犯的错误

把 MVVM 当成 MVC 的升级版

MVC 的显式协调在小页面和高频 HUD 中仍然有优势。升级架构必须由具体痛点驱动。

只比较代码行数

MVVM 的基础设施通常比单页 MVC 多，但在大量页面中可能摊薄。应该比较整个功能生命周期内的修改范围、漏刷概率和调试时间。

把第三方框架能力等同于 MVVM

响应式属性、依赖注入和代码生成只是实现手段。即使使用成熟框架，ViewModel 引用 GameObject、业务规则散落在 View 中，职责仍然是混乱的。

为统一而统一

全项目只能选一种 UI 架构并不是工程目标。真正需要统一的是依赖方向、数据所有权、生命周期和错误暴露方式。

十四、站在主程视角如何选型

主程选择 UI 架构，不是在评审会上挑一个概念更完整的模式，而是在为未来几年的交付成本和故障成本负责。真正要回答的是：团队能否稳定执行这套规则，需求变化时修改范围是否可控，线上问题能否快速定位。

14.1 主程首先评估的不是模式，而是项目约束

约束 要确认的问题 对选型的影响
产品生命周期 是三个月原型，还是三年以上长线运营？ 生命周期越长，MVVM 基础设施越可能回本
UI 内容占比 核心工作量在战斗玩法，还是养成、活动和运营页面？ 重 UI 项目更容易获得 MVVM 收益
页面重复度 是否持续生产结构相似的列表、表单和详情页？ 重复越多，通用 Binder 价值越高
团队经验 多数开发者能否解释绑定方向和订阅生命周期？ 经验不足时，MVC 的显式链路风险更低
工具所有权 谁维护绑定框架、代码生成和调试面板？ 没有长期 Owner 时，不应依赖复杂 MVVM 基建
存量代码 已有 UGUI 页面采用什么依赖方向？ 改造成本必须进入版本计划，不能只算新代码收益
性能特征 主要是低频页面，还是高频 HUD 与大列表？ 高频场景更需要显式、专门的刷新策略
测试目标 更关心操作流程，还是大量页面状态组合？ 状态组合测试多时，ViewModel 更有价值

这张表决定的是架构投资能否回收。只比较示例代码行数，无法替主程做项目级判断。

14.2 什么情况下主程会选择 MVC

如果项目满足下面多数条件，我会把 MVC 作为 UGUI 的默认方案：

  • 团队规模较小，UI 开发者需要同时承担玩法或系统开发。
  • 当前目标是快速形成稳定版本，而不是建设通用 UI 平台。
  • 页面以设置、结算、弹窗和有限交互为主。
  • 战斗 HUD 更新频率高，需要精确控制刷新时机。
  • 存量项目已经使用显式事件与 Presenter/Controller。
  • 团队没有专人维护绑定、生成和调试工具。

选择 MVC 的主要原因不是它“简单”，而是它的失败模式更容易暴露：Controller 过大、刷新遗漏、事件未注销都能通过代码评审、调用链和 Profiler 定位。对交付压力大的项目，可观察的问题通常比隐藏在绑定基础设施里的问题更容易管理。

14.3 什么情况下主程会选择 MVVM

当项目满足下面多数条件时，投入 MVVM 更合理：

  • 游戏长期运营，未来会持续增加活动、商城、养成和任务页面。
  • 同一业务状态需要驱动大量文本、显隐、交互态和错误态。
  • 页面模板重复度高，通用 Text、Button、List Binder 可以反复复用。
  • 团队已有稳定的领域服务，ViewModel 不需要承担业务补丁。
  • 自动化测试需要覆盖大量 UI 状态组合。
  • 有明确的基础设施 Owner，能维护绑定错误、性能采样和代码生成。
  • 团队愿意先在一个真实复杂页面验证，再逐步推广。

选择 MVVM 的原因是把持续增长的“状态同步成本”集中治理，而不是追求自动化本身。当一项余额变化要影响十几个控件、多个页面又有相似结构时，ViewModel 和 Binder 能把修改范围从多处事件回调收敛到状态映射与通用绑定。

主程批准 MVVM 前，至少应要求基础设施具备：

  1. 强类型或可生成的绑定，避免字符串静默失效。
  2. 重复 Bind、空目标和无效属性的明确错误。
  3. 统一的页面、ViewModel 与 Model 生命周期规则。
  4. 属性变化和命令调用的调试追踪能力。
  5. 列表差量更新、高频属性降频和 GC 预算。
  6. 不加载场景即可运行的 ViewModel 测试模板。

缺少这些条件时，MVVM 的理论收益很可能被调试和维护成本抵消。

14.6 一句话决策

如果团队当前最缺的是可控交付和透明调试，选 MVC；如果项目已经被大规模 UI 状态同步拖慢，并且团队有能力长期维护绑定基础设施，选 MVVM。

十五、最终判断标准

选择 MVC，当项目更需要：

  • 短而透明的调用链。
  • 低基础设施成本。
  • 精确控制刷新时机。
  • 快速建立业务与 View 的边界。

选择 MVVM，当项目更需要：

  • 集中表达复杂 UI 状态。
  • 自动同步大量联动字段。
  • 复用通用绑定与表单组件。
  • 脱离 Prefab 测试页面状态。

最终标准不是哪种模式更流行，而是新增一个业务字段时，需要修改多少旧代码、经过多少隐式链路，以及出错后能否快速定位。MVC 用显式协调换取透明度，MVVM 用绑定基础设施换取状态同步效率。选择能够覆盖当前复杂度的最小方案，就是更稳妥的架构。

自查清单

  • 当前主要复杂度是交互流程，还是界面状态联动？
  • 团队是否已有可观察、可报错的绑定基础设施？
  • 高频 HUD 是否与低频菜单采用了不同更新策略？
  • 同一页面是否只有一条状态刷新路径？
  • ViewModel 或 Controller 是否正在承载本应属于业务服务的规则？
  • 选择方案后，事件与对象生命周期是否有统一规范？
  • 是否用一个真实复杂页面验证过收益，而不是只看演示代码？
