游戏AI-决策架构（6）：AI 决策比较——特点、场景与选型

Created2026-08-17|Updated2026-08-17|游戏AI决策架构
|Post Views:

FSM、HFSM、行为树、Utility AI、GOAP、HTN 经常被放在一起比较，但它们并不完全处于同一层。本文按“解决什么问题、输出什么结果、适合什么场景”重新对齐六种方案，并给出面向实际项目的选型与组合方式。

本文假设读者已经了解游戏 AI 中的感知、移动和动作执行概念。重点不是重复每种算法的完整实现，而是建立一套能用于项目判断的比较坐标。

一、先区分：执行控制、即时选择与多步规划

很多选型争论没有结果，是因为大家比较的并不是同一个问题。

感知层
  收集血量、距离、目标、危险度、资源等事实
        |
        v
决策与规划层
  Utility AI：当前哪个候选行为最值得做
  GOAP：哪些动作可以组成一条达成目标的路径
  HTN：高层任务应该按哪种方法逐层拆解
        |
        v
执行控制层
  FSM：当前处于哪个明确状态
  HFSM：当前处于哪条层级状态路径
  行为树：当前哪条优先级分支可以继续执行
        |
        v
动作能力层
  寻路、技能、动画、交互、Smart Object
```text

这不是强制分层。行为树可以承担轻量决策，FSM 也可以直接根据条件选择动作。但当系统变复杂后，把“选什么”“怎么安排步骤”“如何执行”分开，通常更容易调试和扩展。

## 二、一张表看懂六种方案

| 方案 | 核心问题 | 主要输出 | 核心特点 | 典型场景 | 主要限制 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| FSM | 当前处于什么状态 | 单个状态 | 简单、确定、生命周期清晰 | 小怪、机关、技能阶段 | 状态与迁移容易膨胀 |
| HFSM | 状态如何分层并复用 | 激活状态路径 | 父子层级、共享迁移、模式清晰 | Boss 阶段、战斗/和平模式 | 跨层语义和调试成本更高 |
| 行为树 | 当前哪条分支可执行 | Running 节点与执行路径 | 组合式、响应式、易可视化 | 战斗 AI、Boss 技能、战术行为 | 大树、Blackboard 和中断容易失控 |
| Utility AI | 当前哪个候选最有价值 | 候选及效用分数 | 连续评分、动态权衡、行为自然 | 技能选择、目标选择、生存需求 | 曲线调参与行为震荡 |
| GOAP | 如何动态组合动作达成目标 | 动作计划 | 前提/效果、状态空间搜索、涌现性 | 沙盒 NPC、生存模拟、动态战术 | 建模、搜索和重规划成本高 |
| HTN | 已知领域任务如何逐层拆解 | 原子任务序列 | 领域知识驱动、结构可控、可解释 | 长任务链、SLG、RPG、队伍策略 | Method 设计成本高、动态性受域约束 |

如果只记一组关键词：

```text
FSM     = 明确状态
HFSM    = 层级模式
行为树   = 条件控制流
Utility = 当前评分
GOAP    = 动态找路
HTN     = 按套路拆任务
```text

## 三、FSM：最小、确定的行为闭环

FSM 用有限状态和显式迁移描述行为。角色同一时间通常处于一个状态，切换时执行固定的 `Exit -> Enter` 生命周期。状态模式在游戏开发中的价值，正是把分散的布尔条件收束成互斥、可命名的行为模式[^1]。

### 核心特点

- 当前状态唯一，行为容易观察。
- 迁移条件显式，运行结果确定。
- `Enter / Update / Exit` 生命周期清楚。
- 实现成本低，不依赖复杂工具。
- 状态少、迁移稀疏时，调试效率很高。

### 适合使用

- 塔防或动作游戏中的普通小怪：巡逻、追击、攻击、死亡。
- 技能施法流程：前摇、释放、后摇、冷却。
- 门、机关、宝箱、生产建筑等交互对象。
- Boss 的少量固定阶段。
- UI、任务节点和关卡流程。

### 不适合使用

- 一个行为需要同时考虑很多连续因素。
- 状态之间几乎都能互相迁移。
- 多个状态重复死亡、撤退、受控等规则。
- 需要运行时动态生成一串动作。

FSM 的问题通常不是“状态达到某个数量”，而是新增一个状态时必须修改多少旧迁移。如果每次扩展都要触碰大量已有状态，结构就已经开始变脆。

## 四、HFSM：为状态增加模式与层级

HFSM 在 FSM 上增加父子状态。`Chase` 和 `Attack` 可以归入 `Combat`，共享战斗模式的进入、退出、更新和迁移。层级状态思想来自 Statecharts，它通过层级和扩展语义缓解平铺状态图的复杂度[^2]。

### 核心特点

- 当前状态是一条 `Root -> Parent -> Leaf` 激活路径。
- 父状态承载共享生命周期和共享迁移。
- 可以表达和平、战斗、受控、死亡等稳定模式。
- 子状态切换时可以保持父状态持续激活。
- 默认子状态和历史状态能恢复局部流程。

### 适合使用

- Boss 的阶段内还有攻击、移动、施法等子状态。
- 角色存在地面、空中、游泳等大模式。
- 战斗模式中的多个状态共享目标锁定和威胁更新。
- 技能或动画存在稳定的层级阶段。
- 普通 FSM 已出现大量重复迁移，但行为仍然以状态为中心。

### 不适合使用

- 行为主要由大量优先级条件分支构成。
- 多个维度需要并行变化，例如移动状态和武器状态。
- 层级只是为了整理文件，没有共享行为或迁移。
- 父层和子层都在争夺同一个动作控制权。

HFSM 的风险是把一张复杂平面图变成一棵更难追踪的深树。跨层迁移必须记录完整的退出路径、最近公共祖先和进入路径，否则问题会藏在父状态中。

## 五、行为树：面向优先级与持续响应的控制流

行为树通过 Selector、Sequence、Decorator、Condition、Action 等节点组合行为，并用 `Success / Failure / Running` 驱动树的执行。其优势在于模块化和反应性：高优先级条件变化后，树可以中断当前低优先级分支并重新选择[^3]。

### 核心特点

- 分支顺序可以直接表达优先级。
- 子树和通用节点容易复用。
- 条件与动作分离，适合可视化编辑。
- 能持续检查死亡、眩晕、撤退等高优先级中断。
- 适合把战斗行为组织成可读的层级控制流。

### 适合使用

- 射击或动作游戏中的战术敌人。
- Boss 技能选择、连招条件和阶段内行为。
- 搜索、追击、找掩体、攻击之间的响应式切换。
- 需要策划使用可视化工具配置的 NPC。
- 行为能够自然汇报成功、失败和运行中状态。

### 不适合使用

- 需要在大量候选之间进行连续数值权衡。
- 需要动态搜索没有预先写在树里的动作链。
- 长期计划会被硬编码成很深的 Sequence。
- 团队没有定义 Running、Abort 和 Blackboard 规范。

行为树真正的工程难点不是画节点，而是中断。一个 `Running` 的追击节点被撤退分支抢占后，必须取消寻路并释放动作资源；只停止 Tick 会留下脏状态。

## 六、Utility AI：用分数表达倾向和权衡

Utility AI 为每个候选行为计算效用分数，再选择当前分数最高的行为。血量、距离、弹药、敌人数量等输入通常先归一化，再经过响应曲线和权重组合。Utility Theory 在游戏 AI 中常用于把硬阈值决策改造成连续的行为偏好[^4]。

### 核心特点

- 多个连续变量可以共同参与决策。
- 输出不仅有选择结果，还有可解释的候选分数。
- 通过响应曲线表达“越来越想做某件事”。
- 增加候选行为时，不必修改所有已有候选。
- 容易产生比固定条件链更柔和的行为变化。

### 适合使用

- 攻击、治疗、撤退、找掩体之间的选择。
- 技能选择和攻击目标选择。
- 生存游戏中的饥饿、口渴、睡眠、安全需求。
- 模拟经营中的工作、休息、社交等活动选择。
- RTS 或小队 AI 中选择当前最合适的任务执行者。

### 不适合使用

- 行为必须严格按固定步骤执行。
- 需要生成多步计划，而不是只选当前候选。
- 输入和曲线缺乏明确业务含义。
- 没有分数可视化和回放工具。

Utility AI 最常见的问题是震荡：攻击分数和撤退分数在临界值附近反复超越。迟滞、最短执行时间、冷却、切换惩罚和降频评估都应该属于显式决策规则，而不是藏在动作内部。

## 七、GOAP：在状态空间中动态组合动作

GOAP 把动作描述成前提条件、效果和代价，再搜索一条从当前世界状态到目标状态的动作序列。它不要求开发者预先写死完整流程，而是让动作根据当前条件重新组合。F.E.A.R. 对 GOAP 的应用展示了“规划器生成动作计划，执行器负责移动、动画和 Smart Object”的分层方式[^5]。

### 核心特点

- 以目标状态为驱动，而不是以固定流程为驱动。
- 动作通过前提和效果松耦合。
- 同一个目标可以根据资源和环境产生不同计划。
- 动作库扩展后，已有目标可能自动获得新的达成方式。
- 能产生设计者没有逐条编排的行为组合。

### 适合使用

- 沙盒世界中的自主 NPC。
- 生存模拟中的采集、制作、补给和战斗。
- 动作资源和环境条件经常变化的任务。
- 需要多种路径达成同一目标的战术 AI。
- Smart Object 丰富、交互方式多的场景。

### 不适合使用

- 行为流程短而固定，FSM 或行为树已经足够。
- 世界状态难以抽象成稳定的规划事实。
- 动作前提、效果和代价无法被可靠维护。
- 大量 Agent 高频重规划，但没有预算和调度机制。
- 设计要求结果严格按预定脚本执行。

GOAP 找到的是抽象动作链，不是完整表现。`MoveToCover` 仍然需要寻路，`AttackEnemy` 仍然需要技能或状态机执行。规划模型和真实世界不一致时，执行前验证、动作失败和重规划路径必须明确暴露。

## 八、HTN：用领域知识拆解长任务

HTN（Hierarchical Task Network）从高层任务开始，通过满足条件的 Method 把复合任务逐层拆成子任务，直到得到可执行的 Primitive Task。它把“这类任务通常应该怎么做”的领域知识写进分解结构，因此比自由搜索更可控、更容易解释[^6]。

### 核心特点

- 任务天然具有从战略到动作的层级。
- 同一个复合任务可以提供多种条件化 Method。
- 计划结果由领域知识约束，可控性强。
- 展开过程和失败位置容易记录。
- 对长任务链和团队流程表达能力较好。

### 适合使用

- SLG 中的集结、行军、攻城和防守。
- RPG 中的任务链、生活行为和剧情角色流程。
- 小队协同与战术任务分配。
- 采集、生产、运输、建设等长链行为。
- 希望 AI 有适应性，但仍要遵循设计套路的项目。

### 不适合使用

- 行为只需要在少量状态之间切换。
- 团队无法投入成本维护 Task 和 Method 域模型。
- 世界变化极快，长计划频繁失效。
- 期望系统自由发现领域设计之外的新动作组合。

HTN 的质量取决于 Method。条件写得过宽会出现多个分解同时可用，条件写得过窄又会导致没有计划；Primitive Task 粒度不一致，则会把规划细节和动作执行重新混在一起。

## 九、按游戏场景选择

| 游戏场景 | 首选方案 | 常见组合 | 原因 |
| :--- | :--- | :--- | :--- |
| 塔防普通怪、简单野怪 | FSM | FSM + NavMesh | 行为少、状态边界明确 |
| 多阶段 Boss | HFSM | HFSM + 行为树 | 阶段稳定，阶段内分支较多 |
| 射击游戏战斗敌人 | 行为树 | 行为树 + Utility AI | 需要高频响应、掩体和技能选择 |
| 技能很多的战斗单位 | Utility AI | Utility AI + FSM | 先评分选技能，再执行技能阶段 |
| 生活模拟角色 | Utility AI | Utility AI + 行为树 | 多需求动态权衡，动作需要持续执行 |
| 沙盒生存 NPC | GOAP | Utility AI + GOAP + HFSM | 选目标、生成动作链、稳定执行 |
| SLG 队伍或生产流程 | HTN | HTN + 行为树 | 长链任务有明确领域结构 |
| 剧情和任务角色 | HTN 或 HFSM | HTN + FSM | 流程可控、步骤可解释 |
| 机关、交互物、技能流程 | FSM | FSM + 事件系统 | 不需要引入复杂规划 |

“首选”表示最先验证的最小方案，不代表最终架构。先用最低复杂度建立可玩的行为闭环，再根据重复关系和变化压力升级，比一开始搭完整 AI 平台更可靠。

## 十、一个实用的选型流程

可以按下面的顺序判断：

```text
1. 行为是否只有少量明确模式？
   是 -> FSM
   否 -> 继续

2. 多个状态是否存在稳定的父子模式和共享迁移？
   是 -> HFSM
   否 -> 继续

3. 问题是否主要是大量条件分支、优先级和持续中断？
   是 -> 行为树
   否 -> 继续

4. 问题是否主要是多个连续因素下“现在选哪个”？
   是 -> Utility AI
   否 -> 继续

5. 系统是否需要动态组合动作来达成目标？
   是 -> GOAP
   否 -> 继续

6. 系统是否需要按领域套路拆解可控的长任务？
   是 -> HTN
```text

如果同时回答多个“是”，通常意味着需要组合，而不是继续寻找一个包办所有职责的方案。

## 十一、常见的混合架构

一个复杂 NPC 可以采用下面的分层：

```text
Sensor / Blackboard
    提供事实
        |
        v
Utility AI
    选择当前目标：战斗、治疗、补给、逃跑
        |
        v
GOAP 或 HTN
    生成达成目标的动作序列
        |
        v
行为树或 HFSM
    处理中断、重试和动作执行流程
        |
        v
FSM / Ability / Movement / Animation
    完成具体技能和移动
```text

并不是每层都必须存在：

- 普通小怪可能只有 FSM。
- Boss 可能是 HFSM + 行为树。
- 生存 NPC 可能是 Utility AI + GOAP + 动作状态机。
- SLG 队伍可能是 HTN + 行为树 + 寻路系统。

组合架构必须明确所有权。例如 Utility AI 选择“撤退”后，由谁能取消撤退、谁负责释放寻路、谁报告完成，都要有唯一入口。多个系统同时切换行为，比单个系统复杂更危险。

## 十二、选型时最容易犯的错误

### 只按行为数量选

十个状态未必复杂，四个互相强耦合的状态也可能很难维护。应该看迁移密度、共享规则和变化范围。

### 把行为树当自动规划器

行为树只会执行设计者写进树里的控制流。它可以做轻量选择，但不会自动发现树外的新动作链。

### 把 Utility AI 当执行器

Utility AI 选出高分动作后，动作仍然需要生命周期、中断和完成结果。评分系统不应该直接接管动画和移动细节。

### 把 GOAP 或 HTN 接到表现层

Planner 应操作抽象动作，不应该为每个动画片段建立规划事实。规划粒度过细会扩大搜索空间，也让计划与表现资源强耦合。

### 一开始就组合全部方案

每增加一层，就增加状态同步、失败传播、调试工具和所有权规则。没有明确问题时不应引入对应系统。

## 十三、最终判断标准

选型时可以用五个维度复核：

| 维度 | 要问的问题 |
| :--- | :--- |
| 行为规模 | 行为和关系是否已经超出简单状态图？ |
| 动态性 | 行为链需要运行时生成，还是预先编排即可？ |
| 可控性 | 设计是否要求结果严格遵循领域流程？ |
| 响应性 | 当前动作是否需要被高优先级条件频繁中断？ |
| 可调试性 | 团队能否看到状态、分数、计划或节点路径？ |

没有绝对最强的 AI 决策方案。FSM 的简单、HFSM 的层级、行为树的响应、Utility AI 的权衡、GOAP 的动态组合、HTN 的可控分解，分别对应不同的设计压力。先判断系统真正需要回答的问题，再选择最小可用结构，最后才考虑组合。

## 自查清单

- 当前问题属于执行控制、即时选择还是多步规划？
- 是否正在用复杂系统解决一个简单状态切换问题？
- 决策输出能否交给独立执行器，而不是直接操作表现层？
- 行为切换、中断、失败和重规划是否有唯一入口？
- 团队能否查看 FSM 状态、Utility 分数、GOAP 计划、HTN 展开或行为树路径？
- 混合架构中每一层是否解决了一个无法由更低成本方案解决的问题？
