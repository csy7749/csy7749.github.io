Unity UGUI架构（1）：MVC模式

Created2026-08-17|Updated2026-08-17|UnityUGUI
|Post Views:

MVC 在 Unity UGUI 中的价值，不是把脚本机械地分成三个文件，而是把界面显示、业务状态和用户操作分开。本文从一次按钮点击的完整数据流出发，说明 Model、View、Controller 的职责、依赖方向、优缺点，以及它真正适合的项目规模。

本文假设读者熟悉 Unity、MonoBehaviour、Button 和 Text 等基本 UGUI 组件。文中的 MVC 指面向客户端界面的工程化变体，不要求照搬 Web MVC 的请求/响应模型。

一、UGUI 为什么需要 MVC

一个小型界面通常会从下面这种脚本开始：

它在功能很少时没有问题，但一段代码同时承担了五件事：

  • 接收按钮事件。
  • 修改业务数据。
  • 刷新界面。
  • 持久化数据。
  • 播放表现效果。

当数量还会被背包系统、网络同步或奖励结算修改时，界面脚本就不再是数据的唯一入口。此时容易出现“数据已经变了但文本没刷新”“关闭界面后监听仍然存在”“测试业务规则必须启动场景”等问题。

MVC 的目标是建立一个明确的数据闭环：

重点不是类名，而是状态只能由业务入口修改，界面只渲染结果。

二、三个角色在 Unity 中分别负责什么

Model：业务状态与规则

Model 保存真正影响游戏结果的数据，并维护这些数据的约束。例如背包数量不能小于 0，也不能超过堆叠上限。

Model 不应该引用 Button、Text、Prefab 或具体场景对象。否则它无法脱离界面运行，也难以用于自动测试、服务器逻辑或存档恢复。

View：UGUI 组件与表现

View 持有序列化的 UGUI 引用，负责：

  • 把数据显示到 Text、Image、Slider 等控件。
  • 把点击、拖拽、输入等操作转换为语义化事件。
  • 播放界面动画、音效和选中态。
  • 在正确的生命周期注册与注销 UGUI 监听。

View 不负责判断“能否购买”“道具是否达到上限”。这些属于业务规则。

Controller：协调一次交互

Controller 接收 View 的操作事件，调用 Model，再把 Model 的变化交给 View。它是协调者，不应该重新保存一份与 Model 重复的业务状态。

在 Unity 项目中，Controller 可以是普通 C# 类，也可以是 MonoBehaviour。只要不依赖帧循环、协程和场景生命周期，优先使用普通 C# 类，更容易测试和复用。

三、依赖方向比文件夹名称更重要

推荐采用偏 Passive View 的依赖方向。这里强调 View 被动渲染、协调者组织输入与状态更新，属于经典 GUI 架构职责演进在客户端中的一种工程化落地（参见 GUI Architectures）：

Controller 依赖接口，而不是直接查找场景对象。具体实现由界面入口组装。这样 Model 与 Controller 可以脱离 Unity 场景测试，View 也不会知道数据来自本地、服务器还是缓存。

四、一个最小可用的 MVC 示例

下面用“点击按钮增加背包数量”展示完整闭环。

4.1 Model

Model 主动暴露状态变化事件。这样变化不论来自按钮、奖励还是网络同步，都能沿同一条刷新路径传播。

4.2 View

View 把 Button.onClick 转换成 AddClicked，让 Controller 不依赖具体控件。uGUI 元素基于 MonoBehaviour，事件回调既可以在 Inspector 配置，也可以在运行时注册；工程中应选择一种清晰、可追踪的绑定方式，避免同一操作被重复注册（参见 Unity 的 uGUI 迁移说明）。对于 Inspector 中持久化的 UnityEvent，还要注意它会持有目标对象引用，监听关系必须纳入对象生命周期检查（参见 UnityEvents 文档）。

4.3 Controller

Controller 没有自行计算上限，也没有直接修改 Text。业务规则归 Model，显示归 View，Controller 只组织调用顺序。

4.4 界面入口负责组装

InventoryPanelEntry 是组合入口。具体对象在边界处创建，业务类内部不创建自己的依赖。实际项目可以把 Model 换成玩家数据服务注入，而不是每次打开界面都创建新数据。

五、MVC 的优点

职责容易理解

Model 管数据，View 管显示，Controller 管交互。对刚开始治理 UGUI 代码的团队，这套划分比自动绑定和响应式流更直观。

数据流显式

按钮触发哪个 Controller、Controller 调用哪个 Model、Model 更新后刷新哪个 View，都能通过调用链和断点观察。出现问题时不必先理解一套绑定引擎。

对小中型界面成本可控

界面字段不多、交互路径明确时，手写几条事件和刷新方法就能建立稳定边界，不需要引入命令系统、属性通知、绑定生成器和复杂生命周期管理。

业务逻辑可测试

只要 Model 与 Controller 不依赖 MonoBehaviour，就能用普通 C# 测试规则与协调流程。View 可以通过接口替身验证是否收到正确渲染参数。

与 UGUI 的使用方式自然贴合

UGUI 本身以组件和事件为中心。MVC 可以直接利用 Button、Toggle、InputField 的事件，不要求改变 Prefab 和 Inspector 的主要工作方式。

六、MVC 的缺点

Controller 容易膨胀

当所有按钮回调、请求、校验、页面跳转和刷新都堆进一个 Controller，它会变成新的“万能脚本”。解决方式不是继续拆出更多 Controller 名称，而是把业务用例下沉到服务，把显示格式提取为独立转换器，并按子区域拆分界面协调职责。

手动刷新容易遗漏

Model 新增字段后，开发者必须明确调用对应的 View 更新方法。状态来源很多时，某一条变化路径可能漏掉刷新。

Controller 与 View API 可能高度耦合

如果 View 暴露 SetName、SetPrice、SetIcon、SetCount 等大量细粒度方法，Controller 会被迫了解界面细节。可以用不可变的 ViewState 一次性渲染，减少调用数量和半更新状态。

多页面共享状态时协调成本上升

同一玩家数据同时影响顶部资源栏、背包、商店和任务提示时，点对点 Controller 刷新会形成网状关系。此时需要统一状态服务或事件流，而不是让 Controller 互相调用。

容易产生 MVC 名义下的不同实现

有的团队让 View 直接读 Model，有的让 Controller 负责所有刷新，有的把 Controller 挂在每个 Prefab 上。如果依赖规则没有写清楚，同样叫 MVC 的模块仍然无法组合。

七、适合 MVC 的项目场景

场景 适合程度 原因
原型、独立游戏、小团队项目 高 结构明确，基础设施成本低
设置、暂停、结算等表单型页面 高 操作路径有限，字段变化清晰
商店、背包的中等复杂度页面 中高 业务规则可下沉，手动刷新仍可管理
高频实时 HUD 中 可用，但必须避免每帧全量刷新
大型活动系统、复杂数据面板 中低 状态来源与联动字段多，手动刷新成本高
大量通用控件和动态表单 低 重复绑定代码多，MVVM 或声明式方案更合适

MVC 特别适合从“所有代码都写在 View”向工程化 UI 迈出的第一步。只要交互路径仍然能被清晰列出，它通常已经足够。

八、不建议继续使用 MVC 的信号

  • 一个 Model 字段变化需要手动通知多个页面。
  • Controller 大量代码只是在把字段转换成文本、颜色和显隐状态。
  • 同类列表项反复编写相同的监听与刷新代码。
  • UI 状态远多于业务状态，例如加载中、错误、权限、选中、分页和筛选同时存在。
  • 自动化测试更关心“某状态应该显示什么”，而不是“某方法是否被调用”。

这些信号说明问题已从“协调几个操作”转向“持续维护一份界面状态映射”，MVVM 会更值得考虑。

九、常见错误

View 直接修改 Model

Button 回调中直接写 model.Quantity++ 会绕开 Controller，也可能绕开校验、日志和事务边界。View 应发出用户意图，不应决定业务结果。

Model 持有 GameObject

Model 一旦引用场景对象，就会被 Unity 生命周期和场景切换绑住。需要驱动表现时，应发布领域事件或返回结果，由上层协调。

Controller 保存第二份状态

Controller 中再维护一个 currentQuantity，会产生两个事实来源。业务数据只应由 Model 持有；临时 UI 状态如果确实存在，也要明确它不属于领域数据。

只注册不注销

动态创建和销毁的界面如果没有对称注销监听，旧 View 仍可能收到事件。绑定与解绑应由同一对象、同一生命周期负责。

十、工程落地建议

一个中小项目可以从下面的目录开始：

落地时守住四条规则：

  1. Model 不依赖 Unity UI。
  2. View 不包含业务判断。
  3. Controller 不复制业务状态。
  4. 事件注册与注销必须成对出现。

MVC 不是为了增加文件数量，而是为了让一次变化只有一条可追踪路径。对大多数中小型 UGUI 页面，只要把职责和依赖方向守住，它就是低成本、可测试、容易调试的方案。

自查清单

  • Model 能否脱离场景独立测试？
  • View 是否只把输入转换为事件，并根据参数渲染？
  • Controller 是否只协调，不复制状态和业务规则？
  • 同一个数据变化是否只有一个事实来源？
  • 所有 UGUI 与 Model 事件是否成对注销？
  • Controller 增长时，是否按业务用例与界面区域拆分？
