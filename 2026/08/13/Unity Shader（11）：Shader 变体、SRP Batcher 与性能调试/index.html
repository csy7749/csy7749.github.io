Unity Shader（11）：Shader 变体、SRP Batcher 与性能调试

Created2026-08-13|Updated2026-08-17|UnityShader
|Post Views:

写完 Shader 只是第一步。能不能跑得快、包体不大、出了问题能定位，才是把 Shader 用好的关键。这一讲收官，讲三件事：Shader 变体（keyword 如何膨胀包体）、SRP Batcher（现代 Unity 的批量渲染优化）、以及 Frame Debugger 和常见报错排查。学完这篇，整个系列就闭环了。

一、Shader 变体与 keyword

1.1 什么是变体

同一个 Shader，经常需要”开关某些功能”。比如”要不要自发光””要不要法线贴图”。Unity 用 keyword 实现，每个 keyword 组合编译出一份独立的 GPU 程序，这就是变体（Variant）。

#pragma multi_compile _ ENABLE_EMISSION
#pragma multi_compile _ RED GREEN BLUE
```text

- 第一行：1 个开关，2 种可能（无 / ENABLE_EMISSION）。
- 第二行：4 种可能（无 / RED / GREEN / BLUE）。

两行叠加就是 `2 × 4 = 8` 个变体。每多一个 keyword，变体数量成倍增长。

### 1.2 shader_feature vs multi_compile

| 指令 | 行为 | 适用 |
| :--- | :--- | :--- |
| `multi_compile` | 编译所有变体，包体全带 | 运行时可能动态切换、全局 keyword |
| `shader_feature` | 只保留"材质用到"的变体 | 每个材质静态决定的功能 |

**默认能用 `shader_feature` 就别用 `multi_compile`**。`shader_feature` 会剔除未被任何材质引用的变体，大幅减小包体。只有"需要在运行时全局切换、或通过 C# 动态启用"的 keyword 才用 `multi_compile`。

### 1.3 变体为什么是性能杀手

- **包体**：变体越多，Shader 资源越大，安装包越大。
- **内存**：变体被加载进 GPU 内存，每个变体都占一份。
- **编译时间**：变体爆炸会让 Shader 导入/构建变慢。

排查工具：项目设置里的 **Shader Variant 统计**，以及 `Project Settings → Graphics → Shader Stripping`（URP 的剥离选项）。合理控制变体，是移动端项目的必修课。

## 二、SRP Batcher：现代批量渲染

### 2.1 它解决什么问题

传统渲染里，切换一个材质就要重新绑定一堆参数，产生 CPU 开销。**SRP Batcher** 把"材质数据"组织成持续的常量缓冲，让大量使用**不同材质但相同 Shader** 的物体能连续、低开销地提交。

```text
传统：物体 → 逐个绑定参数 → Draw Call（每个都打断批处理）
SRP Batcher：物体 → 复用同一套缓冲 → 连续 Draw Call
```text

### 2.2 兼容条件

Shader 要兼容 SRP Batcher，需要满足：

- 材质相关属性放在 `CBUFFER_START(UnityPerMaterial) ... CBUFFER_END` 里（第 4 讲讲过的写法）。
- 用 `TEXTURE2D / SAMPLER` 宏声明纹理。
- 不依赖 Built-in 老式的属性排列方式。

在 Shader 的 Inspector 面板底部，会直接显示：

```text
SRP Batcher: Compatible   ← 兼容
SRP Batcher: Not compatible  ← 不兼容
```text

URP 下新建的 Lit/Unlit 模板、Shader Graph 默认都兼容；自己手写时注意上面的 CBUFFER 规则即可。

### 2.3 收益与注意

- SRP Batcher 不是"合批成一次 Draw Call"，而是"让多次 Draw Call 之间的切换开销变低"。它和静态合批（Static Batching）、GPU Instancing 是不同层面的优化。
- 对"大量不同材质、相同 Shader"的场景收益最大；对"很多相同材质"的场景，GPU Instancing 可能更合适。

## 三、Frame Debugger：逐 Draw Call 拆解渲染

Shader 出问题，第一反应不应该是"猜"，而是打开 **Frame Debugger**：

```text
Window → Analysis → Frame Debugger → Enable
```text

它把一帧的渲染按顺序列出来，你能看到：

- 每个 **Draw Call** 画了什么、用的哪个 Shader 的哪个 Pass
- 每个 Pass 的渲染状态（Blend、Cull、ZWrite 等）
- 透明物体、后处理、阴影各自在什么时机执行
- 每一步的渲染结果截图

典型排查场景：

| 现象 | 看什么 |
| :--- | :--- |
| 物体没画出来 | 有没有对应的 Draw Call、Pass 是否执行 |
| 半透明乱序 | Transparent 阶段的 Draw Call 顺序 |
| 后处理无效 | Renderer Feature 的 Pass 有没有插入 |
| Draw Call 太多 | 逐条看能不能合批/合并材质 |

## 四、移动端性能要点

| 优化点 | 做法 |
| :--- | :--- |
| 精度 | 颜色用 `half`/`fixed`，位置/世界坐标用 `float` |
| 纹理采样 | 减少采样次数，合并贴图（图集/通道打包） |
| Overdraw | 减少透明叠层，注意粒子和大面积透明 |
| 变体 | 用 `shader_feature` + Shader Stripping 控制 |
| 复杂度 | 避免片元里的昂贵运算（多噪声、多次采样） |
| Alpha Test | 能不用就不用，`clip` 在部分移动 GPU 上较贵 |

核心原则：**移动端的瓶颈常在带宽和片元着色器**，优先减少采样次数和 Overdraw。

## 五、常见报错与排查

| 报错/现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| 材质变粉红 | Shader 编译失败 | 看 Console 的 shader error，逐个修 |
| `unrecognized identifier` | 变量/宏未定义 | 检查拼写、是否 `#include` 了对应头文件 |
| `redefinition` | 变量重复定义 | 删除重复声明，或检查头文件重复引入 |
| URP 项目报 `UnityCG.cginc` 找不到 | 用了 Built-in 头文件 | 换成 URP 的 `Core.hlsl` 等 |
| 半透明物体排序错乱 | Queue/排序问题 | 检查 `Queue="Transparent"`、物体层级 |
| 采样结果全黑/全白 | UV 或采样器/属性名不对 | 检查 UV、`TRANSFORM_TEX`、Blit 属性名 |

排错心法：**先看报错行号 → 再看 Frame Debugger → 最后才改代码**，不要盲改。

## 六、自查清单

- [ ] 能解释 keyword 如何让变体数量成倍增长
- [ ] 知道 `shader_feature` 与 `multi_compile` 的区别，以及默认该选谁
- [ ] 知道 SRP Batcher 优化的是"切换开销"而非"合批次数"
- [ ] 能写出让 Shader 兼容 SRP Batcher 的 CBUFFER 写法
- [ ] 会用 Frame Debugger 定位 Draw Call / Pass / 状态问题
- [ ] 能列出移动端 Shader 优化的主要手段
- [ ] 遇到粉色材质知道先去看 shader 编译报错
