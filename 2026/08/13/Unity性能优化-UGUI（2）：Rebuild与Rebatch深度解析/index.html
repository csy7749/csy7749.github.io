Unity性能优化-UGUI（2）：Rebuild 与 Rebatch 深度解析

Created2026-08-13|Updated2026-08-13|Unity性能优化
|Post Views:

上一篇建立了 UGUI 的底层地基：Canvas 是渲染单元，CanvasRenderer 持有网格，脏标记触发重建，CanvasUpdateRegistry 统一调度。这一篇往深里走两步——Rebuild 到底怎么”重造网格”，Rebatch 又凭什么决定哪些元素能合进同一个 DrawCall。读完你会明白 Frame Debugger 里每一条红色高亮到底在告诉你什么。

一、两个动作，两种成本模型

先回顾边界：Rebuild 是点成本（单个元素重造网格），Rebatch 是面成本（整个 Canvas 重新合批）。

两者遵循一个铁律：Rebuild 必然触发 Rebatch，但 Rebatch 不一定由 Rebuild 引起。

  • 你改了 Image 的颜色 → Rebuild 这个 Image（顶点颜色重算）→ 必然 Rebatch 整个 Canvas
  • 你只调整了元素在 Hierarchy 里的兄弟顺序 → 没有 Rebuild，但渲染深度变了 → 单独触发 Rebatch

理解这个铁律，才能读懂 Profiler 里的两个指标：Canvas.SendWillRenderCanvases（包含 Rebuild）和 Canvas.BuildBatch（就是 Rebatch）。

二、Rebuild 的内部：从 UpdateGeometry 到 OnPopulateMesh

2.1 完整调用链

OnPopulateMesh 是唯一的”生产点”，所有元素重建的差异都体现在这里。

2.2 三种典型网格的成本差异

元素 OnPopulateMesh 的工作 顶点量级
Image（Simple） 生成 1 个 quad 4 顶点 + 6 索引
Image（Sliced 九宫格） 按 border 生成 9 个格子的顶点 最多 16 顶点
Image（Filled 填充） 按 fillAmount 动态生成 可变
Text（纯文本） 逐字形生成 quad 每字约 4 顶点
Text（带 Outline/Shadow） 原网格 + 多方向复制 顶点数 ×4 或 ×8
Text（富文本） 加粗/斜体再复制网格 顶点数显著膨胀

这就是为什么那些优化建议会成立：

  • 避免富文本：<b> 加粗是通过把原网格偏移复制一份实现的，顶点直接翻倍。
  • 避免 Best Fit：每次 Rebuild 都要重新采样多个字号找最佳大小，计算量远高于固定字号。
  • Text 比 Image 慢：逐字形生成 vs 固定 quad。

2.3 一个被低估的细节：Text 的网格缓存

旧版 Text 组件内部通过 TextGenerator 缓存了文本布局结果，只有当文本、字号、对齐等参数变化时才真正重新生成字形网格。这意味着：

  • 改位置（rectTransform.position）不触发文本重排版——只是把已有网格平移
  • 改文本内容/字号/颜色才触发重排版

理解这个差异，能帮你判断”到底哪里在真正重建”。

三、Rebuild 之外的布局重建：LayoutRebuilder

Rebuild 不只是图形重建，还有一条并行的布局重建线。

3.1 布局重建的对象

当元素的尺寸会影响别人时（比如 ContentSizeFitter 根据子内容撑大自己，LayoutGroup 根据子元素排列），走的是布局重建队列，核心是 LayoutRebuilder。

3.2 布局重建的代价：递归

LayoutGroup 要计算”每个子元素放哪里”，就必须先知道”每个子元素有多大”。而子元素如果自己也有 ContentSizeFitter 或嵌套 LayoutGroup，又要往下递归。所以：

  • 嵌套 LayoutGroup 的代价随深度指数增长（每层都要先算完所有子层）
  • 布局重建往往在 Layout 阶段完成，比 PreRender 的图形重建更早、更”牵一发动全身”

四、Rebatch：合批的完整判定规则

Rebuild 解决”每个元素长什么样”，Rebatch 解决”这些元素怎么打包成最少的 DrawCall”。

4.1 合批发生在哪

Rebatch 发生在引擎的 C++ 层（Profiler 里叫 Canvas.BuildBatch），它做的事是：

  1. 收集当前 Canvas 下所有 CanvasRenderer
  2. 按渲染深度排序（不是 Hierarchy 顺序！）
  3. 从头到尾扫描，把相邻且可合并的元素并进同一个 Batch
  4. 遇到不可合并的元素就开新 Batch

4.2 可合并的充要条件

两个相邻元素要合进同一个 Batch，必须同时满足：

  1. 同一个 Canvas（跨 Canvas 永不合并）
  2. 材质实例相同（material 是同一个实例，而非”长得一样”）
  3. 主纹理相同（mainTexture 同一张）
  4. Shader 相同

任何一条不满足，合批立即中断，开启新 Batch。

4.3 为什么图集是”最有效的优化”

没有图集时，10 个 Image 各用各的 Sprite，就是 10 张不同的纹理、10 个不同的材质实例，即使都是默认 UI 材质也会因为纹理不同而中断合批 → 10 个 DrawCall。

打进同一个 Sprite Atlas 后，这 10 个 Sprite 共享同一张大图（一个纹理）+ 同一个 Atlas 材质实例。材质相同、纹理相同，理论上这 10 个 Image 可以合进 1 个 DrawCall。

4.4 合批的”顺序敏感”特性

合批是按深度排序后扫描相邻元素，所以两个本可合并的元素，如果中间插了一个材质不同的元素，就都被拆散：

这就是”把同材质元素连续排列”的底层原因——合批看的是渲染深度的相邻性，不是逻辑分组。

4.5 渲染深度从哪来

元素的渲染深度主要取决于：

  • Canvas 的 sortingOrder
  • 同一 Canvas 内的 sibling index（Hierarchy 里的先后）
  • 特殊属性（如 Text 会强制更深的深度）

所以当你用 Frame Debugger 看到合批顺序”和 Hierarchy 不一样”时，通常是因为深度排序的结果，而非 bug。

五、Mask 与 RectMask2D：合批的天敌与救星

5.1 Mask 为什么贵

Mask 依赖**模板缓冲（Stencil Buffer）**实现裁剪：

  1. 先渲染 mask 形状，往 stencil buffer 写入标记
  2. 再渲染被遮罩内容，每个像素做 stencil test
  3. 最后恢复 stencil buffer

这个流程会带来额外的 2 个 DrawCall（甚至更多，视实现而定），并且 stencil 操作会强制打断合批。

5.2 RectMask2D 为什么省

RectMask2D 不碰 stencil，而是用一个矩形裁剪区域（clip rect），在 CanvasRenderer 层面直接裁剪。它不增加 DrawCall，对合批的破坏也远小于 Mask。

规则：只要裁剪区域是矩形，一律 RectMask2D。只有需要圆形、异形裁剪时才考虑 Mask。

5.3 一个常被忽略的坑

RectMask2D 虽然省，但一个元素同时被多个 RectMask2D 裁剪时，CanvasRenderer 需要维护多个 clip rect，合批也会受影响。所以滚动列表里，Item 内部尽量不要再嵌套 RectMask2D。

六、用 Profiler 精确定位 Rebuild / Rebatch

机制讲完了，现在上工具。核心就两个指标：

6.1 Canvas.SendWillRenderCanvases

这是 Canvas.willRenderCanvases 事件的总耗时，代表这一帧所有 Canvas 的 Rebuild 总开销。

  • 它很高（> 10ms）→ 有大量元素在重建 → 检查是否在每帧无脑改 Text/Image
  • 它很低，但帧率仍差 → 瓶颈在别处（GPU、脚本逻辑），别急着优化 UI

6.2 Canvas.BuildBatch

这是 Rebatch 的耗时。

  • 它很高 → 某个 Canvas 下顶点太多 / 元素太多 → 拆分 Canvas、减少单 Canvas 规模
  • 它很低 → 合批本身不慢，问题在 Rebuild 或其它

6.3 UI Details 模块的黄金指标

在 Profiler 里开启 UI 和 UI Details 模块，关注三个数：

指标 含义 健康值参考
Batches 这一帧的合批次数 越低越好，UI 场景一般 < 30
Vertices 这一帧的顶点总数 越低越好，越复杂越高
SetPass Calls Shader 切换次数 接近 Batches 数

小技巧：Profiler.BeginSample("MyUIRebuild") 可以自定义采样区间，把”某段 UI 操作的开销”从大锅里单独拎出来看。

七、用 Frame Debugger 逐帧拆合批

Frame Debugger（Window → Analysis → Frame Debugger）是诊断合批的终极武器。点击 Enable 后：

  1. 左侧列表 = 这一帧的 DrawCall 序列，每个条目就是一次渲染提交
  2. 红色高亮 = 合批被打断的位置
  3. 点击红色条目，右侧会显示打断原因——通常是 “Material X is different” 或 “Texture Y is different”

八、一个完整的诊断实战

症状：某背包界面 Batches 高达 210。

排查：

  1. Profiler 开 UI Details：Batches: 210，Vertices: 38,000
  2. 开 Frame Debugger，发现大量红色高亮，逐个点开：
    • 60% 的打断原因：”different texture” → 物品图标没打图集
    • 30% 的打断原因：”different material” → 数字文本（Text）穿插在图标（Image）之间
    • 10% 是 Mask 组件

对应修复：

  1. 把所有物品图标打进一个 Sprite Atlas → 图标纹理统一
  2. 重排层级：把纯图标层和纯文本层分开排列，减少 Text/Image 交替
  3. Mask 全部换成 RectMask2D

结果：Batches 从 210 降到 26，Vertices 从 38,000 降到 21,000。

九、本篇小结

这一篇把两个动作拆到了可诊断的粒度：

  • Rebuild 是 OnPopulateMesh 的调用，不同 Graphic 的网格成本差异巨大，富文本、描边、Best Fit 是重灾区。
  • Rebatch 是 Canvas.BuildBatch 的排序合并，判定只看”材质实例 + 主纹理 + Shader”是否相同，且对渲染深度的相邻性敏感。
  • 图集之所以神，是因为它同时统一了纹理和材质，直接把合批判定里的两个变量消灭了。
  • Profiler 看总量，Frame Debugger 看细节，二者配合才能从”UI 卡”走到”哪里卡”。
