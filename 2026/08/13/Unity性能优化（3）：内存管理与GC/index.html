Unity性能优化（3）：内存管理与 GC

Created2026-08-13|Updated2026-08-17|Unity性能优化
|Post Views:

内存问题是最”阴险”的性能杀手：代码逻辑完全正确，没有报错，也没有明显的慢函数，但帧率却每隔几秒规律性地掉一下。这种规律性卡顿十有八九是 GC 在作祟。本文从 Unity 的内存模型讲起，拆解托管内存与原生内存的边界、值类型的分配位置、GC 的工作原理，再逐个击破七类隐形分配，最后给出内存泄漏的排查方法和一个完整实战案例。

一、先建立内存地图：托管 vs 原生

Unity 的内存分两个世界，混在一起看会完全迷失方向。

1.1 托管内存（Managed）

这是 C# 代码直接接触的内存，由 GC（垃圾回收器） 管理。你在 C# 里 new 出来的对象，绝大多数都住在这里。

var list = new List<int>();        // 托管内存：List 对象本身
var text = "hello" + "world";      // 托管内存：string 对象
var enemy = new Enemy();           // 托管内存：MonoBehaviour 的 C# 壳
```text

### 1.2 原生内存（Native）

这是 Unity 引擎内部使用的内存，由**引擎自己管理**，GC 看不见也管不着。纹理、网格、音频、Shader、动画数据都住在这里。

```csharp
var tex = Resources.Load<Texture2D>("hero");  // 原生内存：真正的像素数据
var mesh = GetComponent<MeshFilter>().mesh;   // 原生内存：顶点/三角形数据
```text

### 1.3 最容易踩的坑：一个对象两份内存

关键认知：**很多 C# 对象只是"壳"，真正的数据在原生内存**。

`Texture2D` 就是典型——C# 侧只有一个轻量的引用壳（托管内存，几十字节），但它的像素数据在原生内存（可能几十 MB）。所以：

- Profiler 里 `Managed Memory` 很低 ≠ 内存占用低
- 卸载一个 `Texture2D`，C# 壳被 GC 回收了，但原生像素数据可能还占着

正确释放纹理要显式销毁：

```csharp
// 只置空引用不够，原生数据还在
tex = null;                      // ❌ 原生内存不释放
Destroy(tex);                    // ✅ 显式销毁原生资源
Resources.UnloadUnusedAssets();  // 配合清理无引用的资源
```text

## 二、值类型到底分配在哪：栈还是堆

这个问题答案不是"struct 在栈、class 在堆"这么简单，要**看值类型的存放位置**。

### 2.1 三种情况

```csharp
public class Player {
    public int hp;              // ① 类字段：分配在堆上（随 Player 对象）
    public Vector3 position;    // ① 类字段：也在堆上
}

void Update() {
    int localHp = 100;          // ② 局部变量：分配在栈上（方法返回即消失）
    Vector3 localPos = Vector3.zero; // ② 局部变量：栈上
}

object boxed = 100;             // ③ 装箱：值类型被复制进堆上的一个 box
```text

### 2.2 为什么"struct 在栈上"会误导人

一个 `struct` 只要成为类的字段，就跟着类对象住在堆上。真正决定"栈还是堆"的是**存放位置**，不是类型本身。

理解这一点，才能明白 struct 优化的适用边界：**小而短命的值类型用 struct 能省堆分配；但把 struct 塞进长期存活的 class 里，它照样在堆上，省不了多少。**

### 2.3 装箱：隐藏的堆分配

当值类型被当作 `object` 或接口使用时，会触发装箱——把值复制进堆上的一个新对象：

```csharp
int count = 10;
object obj = count;              // ❌ 装箱：堆分配一个 int box
Debug.Log(count);                // ❌ Debug.Log(object) 会装箱
ArrayList list = new ArrayList();
list.Add(count);                 // ❌ ArrayList.Add(object) 装箱
```text

`ArrayList` 和 `Hashtable` 是装箱重灾区，现代代码应一律用泛型 `List<T>` 和 `Dictionary<TKey,TValue>`。

## 三、GC 的真相：Unity 用的是哪种 GC

### 3.1 Boehm GC：保守式、非分代

Unity 的 Mono 和 IL2CPP 后端，默认都使用 **Boehm GC**。它有两个关键特性，直接影响你的优化策略：

1. **非分代**：不像 .NET 的 Gen0/Gen1/Gen2 三代模型，Boehm 每次回收都要**扫描整个托管堆**。这意味着——对象越多，单次 GC 越慢，无论对象是刚分配的还是活了很久的。

2. **保守式**：它"看不清"栈和寄存器里的精确类型，只能猜。这偶尔会导致"该回收的没回收"（轻微的内存滞留），但不会导致崩溃。

### 3.2 核心结论：让对象"少而短命"

既然每次 GC 都是全堆扫描，优化的核心就非常明确：

- **减少分配**：从源头不让垃圾产生
- **缩短存活时间**：让临时对象尽早变成垃圾，别跨帧驻留
- **控制总量**：长期存活的对象越少，每次扫描越快

### 3.3 一句话判断 GC 是否在作祟

规律性卡顿（比如每 5 秒掉一次）→ 打开 Profiler，看 CPU Usage 里是否每隔一段出现一个 `GC.Collect` 尖峰。是的话，你的问题就是分配过多。

## 四、分配热点排查：GC.Alloc 列怎么读

打开 Profiler（`Window → Analysis → Profiler`），切到 CPU Usage 模块，看每一帧的 **GC Alloc** 列——它直接告诉你这一帧的脚本分配了多少字节托管内存。

排查流程：

```text
帧率规律性卡顿
  ↓
Profiler 里看到周期性 GC.Collect 尖峰
  ↓
找到 GC.Alloc 高的帧
  ↓
展开脚本方法，找到分配量最大的那一行
  ↓
对照本文第五节的七类隐形分配逐一排除
```text

> 经验值参考：**每帧 GC.Alloc 应控制在几 KB 以内**。如果一帧分配超过 100KB，且每帧都如此，移动端几乎必然卡顿。以下数值是我在典型中端设备上观察到的量级，具体以你项目的 Profiler 实测为准。

## 五、七类隐形分配，逐个击破

### 5.1 字符串拼接

```csharp
// ❌ 每次 + 都分配新 string，三个 + 就是三次分配
void Update() {
    string s = "HP: " + hp + " / " + maxHp;
    label.text = s;
}

// ✅ 用 StringBuilder 缓存 + Clear 复用
private readonly StringBuilder sb = new StringBuilder(64);

void Update() {
    sb.Clear();
    sb.Append("HP: ").Append(hp).Append(" / ").Append(maxHp);
    label.text = sb.ToString();  // ToString 本身仍分配一次
}
```text

更彻底的零分配做法，是配合 TextMeshPro 的格式化方法（见 UGUI 篇）：

```csharp
tmpText.SetText("HP: {0} / {1}", hp, maxHp);  // 参数直接进顶点，不拼字符串
```text

### 5.2 LINQ

LINQ 的每个操作符都会分配枚举器对象，链越长分配越多：

```csharp
// ❌ 每帧三个分配：Where 的委托 + 枚举器 + ToList 的结果
void Update() {
    var visible = enemies.Where(e => e.IsVisible).ToList();
}

// ✅ 换成 for + if，零分配
void Update() {
    visibleList.Clear();
    for (int i = 0; i < enemies.Count; i++) {
        if (enemies[i].IsVisible) {
            visibleList.Add(enemies[i]);
        }
    }
}
```text

**结论**：LINQ 适合初始化阶段、一次性执行的代码；高频路径（Update、循环内）一律用 `for`/`foreach` + `if`。

### 5.3 闭包捕获

匿名方法和 Lambda 若捕获了外部变量，会分配一个闭包对象：

```csharp
// ❌ 每次点击分配一个闭包对象（捕获了 count）
button.onClick.AddListener(() => { count++; });

// ✅ 用成员方法，无捕获
button.onClick.AddListener(IncrementCount);

void IncrementCount() { count++; }
```text

### 5.4 协程的 new WaitForSeconds

```csharp
// ❌ 每次 yield 都 new 一个 WaitForSeconds
IEnumerator Loop() {
    while (true) {
        yield return new WaitForSeconds(1f);   // 分配
        Tick();
    }
}

// ✅ 缓存复用一个实例
private static readonly WaitForSeconds WaitOneSecond = new WaitForSeconds(1f);

IEnumerator Loop() {
    while (true) {
        yield return WaitOneSecond;            // 零分配
        Tick();
    }
}
```text

同理缓存 `WaitForEndOfFrame`、`WaitForFixedUpdate`。

### 5.5 返回数组/集合的 API

Unity 有一批 API 默认返回新分配的数组，高频调用会产生大量垃圾：

```csharp
// ❌ 每帧分配一个新数组
var cols = Physics.OverlapSphere(pos, radius);
var children = GetComponentsInChildren<Transform>();
var allEnemies = FindObjectsOfType<Enemy>();

// ✅ 用 NonAlloc / 传入缓存的版本
private readonly Collider[] colsBuffer = new Collider[32];
private readonly List<Transform> childrenBuffer = new List<Transform>();

void Check() {
    int count = Physics.OverlapSphereNonAlloc(pos, radius, colsBuffer);  // 零分配
    childrenBuffer.Clear();
    GetComponentsInChildren(childrenBuffer);  // List 版本复用缓冲
}
```text

规律：**凡是带 `NonAlloc` 后缀，或接受 `List<T>` 参数的 API，都是零分配版本**，优先使用。

### 5.6 Debug.Log 残留

`Debug.Log` 在拼字符串、装箱参数时会分配，更重要的是它在**发布版里也不该存在**：

```csharp
// ❌ 每次拼字符串 + 装箱
Debug.Log("Enemy " + enemy.name + " hp = " + enemy.hp);

// ✅ 用条件编译，发布版直接剔除
[System.Diagnostics.Conditional("ENABLE_LOG")]
public static void Log(string msg) => Debug.Log(msg);
```text

或者项目里统一封装日志组件，发布时一键关闭。

### 5.7 装箱

第五节第 2.3 已讲过，这里再给一个高频场景：

```csharp
// ❌ 用 int 做 Dictionary 的 key 装箱（Dictionary<int,...> 不装箱，
//    但 object 或非泛型容器会装箱）
Hashtable ht = new Hashtable();
ht.Add(1, "a");                    // 装箱

// ✅ 泛型 Dictionary，零装箱
var dict = new Dictionary<int, string>();
dict.Add(1, "a");
```text

## 六、减少分配的设计模式

### 6.1 对象池

频繁创建/销毁的对象（子弹、粒子、UI Item、敌人）用池管理，从源头消除"new + 销毁"的分配。

Unity 2021+ 内置了 `ObjectPool<T>`：

```csharp
using UnityEngine.Pool;

public class BulletPool : MonoBehaviour {
    public Bullet bulletPrefab;

    private ObjectPool<Bullet> pool;

    void Awake() {
        pool = new ObjectPool<Bullet>(
            createFunc: () => Instantiate(bulletPrefab),
            actionOnGet: b => b.gameObject.SetActive(true),
            actionOnRelease: b => b.gameObject.SetActive(false),
            actionOnDestroy: b => Destroy(b.gameObject),
            collectionCheck: false,
            defaultCapacity: 20,
            maxSize: 100
        );
    }

    public Bullet Get() => pool.Get();
    public void Release(Bullet b) => pool.Release(b);
}
```text

### 6.2 NonAlloc 系列

覆盖物理查询、组件遍历、射线检测等高频 API：

```csharp
// 物理
Physics.OverlapSphereNonAlloc / OverlapBoxNonAlloc / RaycastNonAlloc
// 组件
GetComponentsInChildren(List<T>) / GetComponents(List<T>)
// 渲染
Mesh.GetVertices(List<Vector3>) / GetIndices(List<int>)
```text

### 6.3 缓存静态实例

把 `WaitForSeconds`、`Color`、`Vector3` 常量等不可变对象缓存成静态只读字段，全项目复用：

```csharp
private static readonly Color EnemyColor = new Color(1f, 0f, 0f);
private static readonly Vector3 Forward = Vector3.forward;
```text

### 6.4 struct 的正确姿势

用 struct 省分配的前提是：**小（建议 < 16 字节）、不可变、短命、不装箱**。

```csharp
// ✅ 好的 struct：小、只读、不会被装箱
public readonly struct PlayerInput {
    public readonly float horizontal;
    public readonly float vertical;
    public PlayerInput(float h, float v) { horizontal = h; vertical = v; }
}
```text

一旦 struct 含引用类型字段、被频繁装箱、或体积过大，收益就消失甚至变负。

## 七、GC 调优

### 7.1 Incremental GC：把长停顿切成碎片

Unity 2019.1 引入增量 GC，IL2CPP 后端自 2021.2 起默认开启。它的思想是：把一次大的全堆回收，**分摊到多帧**，每帧只做一小片，避免单帧卡顿 50ms。

```csharp
// 检查是否开启增量 GC
bool incremental = UnityEngine.Scripting.GarbageCollector.isIncremental;
```text

**注意事项**：
- 增量 GC 的**总耗时**比非增量略高（分摊有额外开销），但**单帧峰值**大幅下降，适合对帧率稳定要求高的项目
- 它只解决"单次停顿过长"，不解决"总分配过多"——治标不治本，源头仍是减少分配

### 7.2 手动 GC.Collect 的时机

在**可控的时机**主动触发 GC，把它挪到玩家无感知的时刻：

```csharp
// 场景切换、加载完成后、结算界面打开时
void OnSceneLoaded() {
    System.GC.Collect();
    Resources.UnloadUnusedAssets();
}
```text

不要在 Update 里手动 `GC.Collect()`——那等于自己制造卡顿。

### 7.3 IL2CPP 与 Mono 的差异

| 维度 | Mono | IL2CPP |
| :--- | :--- | :--- |
| GC 实现 | Boehm GC | Boehm GC（2021.2+ 支持增量） |
| 增量 GC | 支持 | 默认开启 |
| 代码体积 | 小 | 大（C++ 编译产物） |
| 运行性能 | 较慢 | 更快 |
| 内存占用 | 较低 | 略高（C++ 运行时） |

核心结论：**发布构建几乎都用 IL2CPP**，测试时也要在 IL2CPP 下测内存表现，Editor 里（通常 Mono）的数据只能做参考。

## 八、内存泄漏检测

### 8.1 用 Memory Profiler 抓泄漏

Unity 2022+ 的 Memory Profiler 包（Package Manager 安装 `com.unity.memoryprofiler`）支持快照对比：

```text
1. 进入场景 A，拍快照 1
2. 切到场景 B，再切回场景 A
3. 拍快照 2
4. 对比两张快照：场景 A 的资产本应释放，却还在 = 泄漏
```text

### 8.2 三大经典泄漏源

**① 静态引用**

```csharp
// ❌ 静态字段持有场景对象，场景切换后仍被引用，永不释放
public static List<Enemy> GlobalEnemies = new List<Enemy>();
```text

**② 事件未退订**

```csharp
// ❌ 订阅了事件但 OnDestroy 里不退订，发布者长期持有订阅者
void OnEnable() => GameEvents.OnPlayerDied += OnPlayerDied;

void OnDestroy() => GameEvents.OnPlayerDied -= OnPlayerDied;  // 这一行必须有
```text

**③ DontDestroyOnLoad 的双刃剑**

```csharp
// DontDestroyOnLoad 让对象跨场景存活，但也让它"永不释放"
// 只在真正需要全局存活的单例上使用，且要提供销毁接口
DontDestroyOnLoad(gameObject);
```text

## 九、实战案例：每 5 秒一次的规律卡顿

### 9.1 症状

战斗场景，帧率整体 50 FPS 左右，但每隔 5 秒稳定掉到 10 FPS 一瞬，然后恢复。逻辑代码无明显慢函数。

### 9.2 诊断

1. Profiler 开 CPU Usage，发现每隔 5 秒出现一个 `GC.Collect` 尖峰，耗时约 **50ms**
2. 看 GC.Alloc 列，战斗期间每帧分配约 **2MB**
3. 展开热点方法，锁定两个元凶：
   - `DamageNumber.Show()` 里用 LINQ 计算伤害数字排序
   - `UpdateHUD()` 里每帧字符串拼接血条文本

### 9.3 修复

```csharp
// 修复1：LINQ 换 for
// 旧：var sorted = damages.Where(d => d.active).OrderBy(d => d.value).ToList();
// 新：先收集进复用 List，再用 for 冒泡/选择排序，零分配

// 修复2：字符串拼接换 StringBuilder 缓存
private readonly StringBuilder hudSb = new StringBuilder(32);
void UpdateHUD() {
    hudSb.Clear();
    hudSb.Append(hp).Append('/').Append(maxHp);
    hpText.SetText(hudSb);
}

// 修复3：伤害数字用对象池 + TMP.SetText 格式化
```text

### 9.4 验证

| 指标 | 优化前 | 优化后 |
| :--- | :--- | :--- |
| GC.Alloc/帧 | 2MB | 2KB |
| GC.Collect 峰值 | 50ms / 每5秒 | 8ms / 每30秒 |
| 最低帧率 | 10 FPS | 48 FPS |

## 十、内存优化 Checklist

1. **[ ] 基线**：真机 Profiler，记录 GC.Alloc/帧 和 GC.Collect 频率
2. **[ ] 字符串**：高频路径无 `+` 拼接，改用 StringBuilder 缓存或 TMP.SetText
3. **[ ] LINQ**：Update/循环内无 LINQ，全部换成 for/foreach + if
4. **[ ] 闭包**：Lambda 无捕获外部变量，改用成员方法
5. **[ ] 协程**：WaitForSeconds 等已缓存为静态实例
6. **[ ] API**：物理查询、组件遍历已用 NonAlloc / List 复用版本
7. **[ ] 装箱**：无 ArrayList/Hashtable，值类型未被当 object 传
8. **[ ] 对象池**：频繁创建销毁的对象已池化
9. **[ ] 日志**：Debug.Log 已用条件编译或统一开关
10. **[ ] 泄漏**：静态引用、事件订阅、DontDestroyOnLoad 已审计
11. **[ ] 验证**：相同场景复测，GC.Alloc 与卡顿频率明显下降

## 十一、结语

内存优化的本质是**把 GC 变成"可预测"的东西**：要么从源头减少分配（让 GC 无事可做），要么把回收挪到可控时机（让 GC 在玩家无感知时干活）。记住三句话——**减少分配、缩短存活、控制总量**。真正的内存高手不是会写对象池，而是每写一行 `new` 之前，都下意识地问一句："这个对象非得现在分配吗？"
