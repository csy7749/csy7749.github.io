Unity性能优化（1）：CPU 与脚本优化

Created2026-08-13|Updated2026-08-17|Unity性能优化
|Post Views:

CPU 是游戏性能的”第一现场”——大多数卡顿，追到最后都落在主线程的某段脚本上。本文先帮你建立 CPU 性能模型、判断瓶颈归属，再逐个击破四个高频开销源：Update 模式、GameObject/Component 操作、物理动画、以及最后的杀手锏 Job System + Burst。每节都给”坏代码 → 好代码”的对照，配一个 1000 敌人寻路的完整实战案例。

一、CPU 性能模型：主线程到底在忙什么

Unity 的 CPU 侧由多条线程协作，理解它们的分工是优化的前提。

1.1 三条关键线程

线程 职责
主线程 你的脚本逻辑、物理、动画、以及向渲染线程提交渲染命令
渲染线程 把主线程提交的渲染命令整理后发给 GPU（多线程渲染模式下独立）
Job 线程池 Job System 的工作线程，数量约等于 CPU 核数 − 1

大多数游戏逻辑都挤在主线程上，所以”CPU 优化”约等于”主线程脚本优化”。

1.2 PlayerLoop：主线程的固定班次

主线程不是随意执行的，它按 PlayerLoop 的固定顺序逐段推进。骨架大致是：

PlayerLoop
├── EarlyUpdate（输入、粒子系统预更新）
├── FixedUpdate（物理步进，默认 50Hz）
├── Update（你的 Update 在这里，每帧一次）
├── PreLateUpdate / LateUpdate（AI、相机跟随）
├── PreRender（UGUI 重建、剔除）
└── Render（提交渲染）
```text

每个段都有"固定配额"，某一段超时，整帧就超时。所以优化的第一件事，永远是**搞清楚你的代码跑在哪个段、吃掉多少配额**。

## 二、先判断：到底是不是 CPU 瓶颈

别急着优化脚本，先确认瓶颈真的在 CPU。

### 2.1 两个关键信号

打开 Profiler 的 CPU Usage 模块：

- **`Gfx.WaitForPresent` 高**：CPU 和 GPU 都很快，但都在**等显示器刷新**（Vsync 空闲）。这不是瓶颈，反而说明你还有余量。
- **`Camera.Render` 或某段脚本高**：CPU 真的在忙，这才是要优化的对象。

### 2.2 判断口诀

```text
帧率低
  ├─ Profiler 里 CPU 段很高 → CPU bound → 优化脚本（本文）
  └─ Profiler 里 GPU 段很高 → GPU bound → 优化渲染（第2讲）
```text

确认是 CPU bound 后，再往下读。

## 三、Update 模式：隐形成本大户

### 3.1 空 Update 的真实代价

很多人以为空 Update 会被编译器优化掉，**在 IL2CPP 下不会**。每个 MonoBehaviour 的 `Update` 都通过 C++ 层的函数指针调用，即使方法体是空的，调用本身也有开销。

```csharp
// ❌ 1000 个挂着空 Update 的物体，每帧 1000 次无意义的 C++ 虚调用
void Update() { }
```text

**处理原则**：
- 不需要每帧更新的脚本，**删掉 Update**
- 需要低频更新的，用下面的降频策略

### 3.2 降频策略：自实现 Timer

不是所有逻辑都需要每帧跑。用计数器把"每帧"变成"每 N 帧"：

```csharp
public class AIBrain : MonoBehaviour {
    private const int TICK_INTERVAL = 10;  // 每 10 帧决策一次
    private int frameCounter;

    void Update() {
        frameCounter++;
        if (frameCounter < TICK_INTERVAL) return;
        frameCounter = 0;

        DecideAction();   // 原本每帧跑的重逻辑，现在 10 帧一次
    }
}
```text

更平滑的做法是**分帧**——把一批对象轮流处理，让每帧的负载恒定：

```csharp
// 1000 个敌人，每帧只处理 100 个，10 帧轮完一圈
void Update() {
    int batchSize = 100;
    for (int i = 0; i < batchSize; i++) {
        int idx = (currentOffset + i) % enemies.Count;
        enemies[idx].DecideAction();
    }
    currentOffset = (currentOffset + batchSize) % enemies.Count;
}
```text

### 3.3 何时用 FixedUpdate / LateUpdate

| 回调 | 用途 | 禁忌 |
| :--- | :--- | :--- |
| `Update` | 每帧逻辑 | 别放物理操作 |
| `FixedUpdate` | 物理相关（刚体施力） | 别放普通逻辑（它每帧可能跑 0 次或多次） |
| `LateUpdate` | 相机跟随、结果收集 | 别放本应早跑的 AI/输入 |

一个常见错误：在 `FixedUpdate` 里读 `Time.deltaTime`——它其实是固定步长，应该读 `Time.fixedDeltaTime`。同理，物理操作放 `Update` 里，在帧率波动时表现会不稳定。

## 四、GameObject 与 Component 操作

### 4.1 Find 的代价

```csharp
// ❌ GameObject.Find 遍历整个场景，O(n)，且每帧调用
var player = GameObject.Find("Player");
player.transform.position = target;

// ❌ 每帧 Transform.Find 也不该
var hp = transform.Find("HPText").GetComponent<Text>();

// ✅ Awake 里 Find + 缓存成员变量
private Transform playerTransform;

void Awake() {
    playerTransform = GameObject.Find("Player").transform;
    // 或更好：Inspector 直接拖引用 / 依赖注入
}
```text

规律：**Find 只能在初始化（Awake/Start）出现，且结果必须缓存。**

### 4.2 GetComponent：缓存是铁律

```csharp
// ❌ 每帧 GetComponent
void Update() {
    var rb = GetComponent<Rigidbody>();
    rb.AddForce(...);
}

// ✅ 启动时缓存
private Rigidbody rb;

void Awake() {
    rb = GetComponent<Rigidbody>();
}
```text

`GetComponent` 不是免费的——它要做类型查找。高频调用累积起来是一笔可观开销。

### 4.3 SendMessage / BroadcastMessage：反射陷阱

```csharp
// ❌ 反射调用，慢且无法重构安全
SendMessage("OnPlayerDied", damage);
BroadcastMessage("ApplyEffect", buff);

// ✅ 直接引用 / 接口 / 事件
player.TakeDamage(damage);
effectReceiver.ApplyEffect(buff);
EventBus.Raise(new PlayerDiedEvent(damage));
```text

`SendMessage` 和 `BroadcastMessage` 基于字符串反射查找方法，是历史遗留 API，性能差、易出错，新代码不要用。

### 4.4 Instantiate / Destroy 的位置

```csharp
// ❌ 战斗中频繁 Instantiate + Destroy（GC + 初始化双倍开销）
void Spawn() {
    Instantiate(enemyPrefab, pos, rot);   // 克隆 + Awake/OnEnable 全套初始化
}

// ✅ 用对象池复用（见第3讲对象池），或预热 + 复用
```text

`Instantiate` 的代价远高于"复制一份数据"——它要完整走一遍 `Awake`、`OnEnable`、组件初始化。`Destroy` 也是延迟销毁、产生 GC。高频创建销毁的对象，**对象池是唯一正解**。

## 五、物理与动画

### 5.1 物理设置

```csharp
// 修改固定步长：降低 FixedUpdate 频率可省 CPU，但会牺牲物理精度
Time.fixedDeltaTime = 0.02f;  // 默认 50Hz

// 帧率极低时物理可能"追帧"，必要时限制最大步长
Time.maximumDeltaTime = 0.1f;
```text

物理模拟是 CPU 大户，移动端可以适当把 `fixedDeltaTime` 调到 0.033（30Hz）以省开销。

### 5.2 碰撞体复杂度

| 碰撞体 | 代价 |
| :--- | :--- |
| Sphere / Capsule / Box | 低（解析几何，计算快） |
| Convex MeshCollider | 高（凸包检测） |
| 非凸 MeshCollider | 极高（三角面级检测，且不能挂 Rigidbody 动） |

规则：**能用简单碰撞体就不 MeshCollider；非要 Mesh，用多个简单碰撞体组合近似。**

### 5.3 Animator 的两个开关

```csharp
// Culling Mode：离开屏幕的 Animator 自动降级
animator.cullingMode = AnimatorCullingMode.CullUpdateTransforms;
// 完全不可见时跳过动画计算，但保留位置更新

// UpdateMode：不受时间缩放影响的动画
animator.updateMode = AnimatorUpdateMode.UnscaledTime;
```text

- `Cull Completely`：不可见时完全停更（最省，但要注意动画状态恢复）
- 减少 Animator 数量、合并 Layer，也能显著省 CPU

### 5.4 Playable API

传统 `Animation` 组件和 Animator Controller 有大量隐式开销。`PlayableGraph` 让动画播放更可控、更省：

```csharp
// Playable API 手动控制动画混合，绕过 AnimatorController 的隐式开销
var graph = PlayableGraph.Create("SimpleAnim");
var output = AnimationPlayableOutput.Create(graph, "Anim", animator);
var clipPlayable = AnimationClipPlayable.Create(graph, clip);
output.SetSourcePlayable(clipPlayable);
graph.Play();
```text

适合动画需求简单（单 clip、简单混合）的场景，可比 Animator Controller 省不少 CPU。

## 六、Job System + Burst：CPU 的杀手锏

### 6.1 何时值得上 Job

满足这些条件才上 Job：

- 数据量**大**（> 1000 个元素，太少反而被调度开销抵消）
- 计算**纯数据、相互独立**（各元素互不依赖）
- 不涉及 GameObject/Transform 的引用操作（Job 里碰不到托管对象）

典型场景：批量位置更新、寻路计算、粒子模拟、网格变形。

### 6.2 最小示例：并行移动 1000 个单位

```csharp
using Unity.Burst;
using Unity.Collections;
using Unity.Jobs;
using UnityEngine;

[BurstCompile]
public struct MoveJob : IJobParallelFor {
    public NativeArray<Vector3> positions;
    public float deltaTime;
    public float speed;

    public void Execute(int index) {
        positions[index] += new Vector3(0, 0, speed * deltaTime);
    }
}

public class JobDemo : MonoBehaviour {
    private NativeArray<Vector3> positions;
    private NativeArray<Vector3> result;

    void Start() {
        positions = new NativeArray<Vector3>(1000, Allocator.Persistent);
        result = new NativeArray<Vector3>(1000, Allocator.Persistent);
    }

    void Update() {
        var job = new MoveJob {
            positions = positions,
            deltaTime = Time.deltaTime,
            speed = 5f
        };
        JobHandle handle = job.Schedule(positions.Length, 64); // 每 64 个一批
        handle.Complete();  // 等所有批次完成
    }

    void OnDestroy() {
        positions.Dispose();  // NativeArray 必须手动释放
        result.Dispose();
    }
}
```text

### 6.3 Burst 的魔法与限制

`[BurstCompile]` 把这段 C# 编译成高度优化的 native 代码（SIMD 向量化），性能可提升数倍到数十倍。但它有严格限制：

- **不能 `new` 托管对象**（只能操作 blittable 类型）
- **不能调托管方法**（不能碰 `GameObject`、`Transform`、`List<T>`）
- **只能读写 `NativeContainer`**（`NativeArray`、`NativeList` 等）
- 需要 `using Unity.Collections`，且容器用完必须 `Dispose()`

> 经验：把"纯计算"从主线程剥离到 Job + Burst，是 CPU 优化里回报最高的手段之一，但工程复杂度也最高——先用前面五节的主线程优化"止血"，再对热点上 Job。

## 七、实战案例：1000 个敌人的 AI 寻路

### 7.1 症状

RTS 场景，1000 个敌人在场时，主线程 `AIBrain.Update` 每帧吃掉 45ms，帧率掉到 20 FPS。

### 7.2 诊断

1. Profiler 展开 `AIBrain.Update`，发现两个热点：
   - 每帧对每个敌人做一次 `GameObject.Find("Player")`（1000 次场景遍历）
   - 每个敌人每帧完整跑一遍寻路决策

### 7.3 修复

```csharp
// 修复1：Player 引用改成静态缓存
public static Transform PlayerTransform;   // 场景加载时赋值一次

// 修复2：寻路决策降频 + 分帧
void Update() {
    // 每 10 帧决策一次，且每帧只处理 100 个，轮转分摊
    if (frame++ % 10 != 0) return;
    for (int i = 0; i < 100; i++) {
        int idx = (offset + i) % enemies.Count;
        enemies[idx].DecideMoveDirection();  // 不再每帧全量决策
    }
    offset = (offset + 100) % enemies.Count;
}

// 修复3：把"寻路数值计算"从主线程搬到 Job + Burst
[BurstCompile]
struct PathComputeJob : IJobParallelFor { /* 纯数据寻路计算 */ }
```text

### 7.4 验证

| 指标 | 优化前 | 优化后 |
| :--- | :--- | :--- |
| AIBrain.Update | 45ms | 6ms |
| 帧率 | 20 FPS | 58 FPS |
| CPU 主线程占用 | 95% | 55% |

## 八、CPU 优化 Checklist

1. **[ ] 归属**：Profiler 确认是 CPU bound（非 GPU、非 WaitForPresent）
2. **[ ] 空 Update**：无逻辑的脚本已删掉 Update
3. **[ ] 降频**：低频逻辑已用 Timer/Interval 降低调用频率
4. **[ ] 分帧**：大批量对象已分帧轮转处理
5. **[ ] Find 缓存**：GameObject.Find / Transform.Find 只在初始化、结果已缓存
6. **[ ] GetComponent 缓存**：高频访问的组件已在 Awake 缓存
7. **[ ] 反射**：无 SendMessage / BroadcastMessage，改用接口/事件
8. **[ ] 对象池**：频繁 Instantiate/Destroy 的对象已池化
9. **[ ] 物理**：碰撞体已简化，fixedDeltaTime 已按平台调整
10. **[ ] 动画**：Animator CullingMode 已配置，简单动画用 Playable
11. **[ ] Job/Burst**：大数据纯计算热点已迁移到 Job System + Burst
12. **[ ] 验证**：复测 Profiler，主线程各段耗时明显下降

## 九、结语

CPU 优化有一条清晰的优先级链：**先消除无意义调用（空 Update、每帧 Find），再降低调用频率（降频、分帧），最后才上重型武器（Job + Burst）**。多数项目走到前两步就能解决 80% 的卡顿，第三类手段留给真正的计算密集热点。记住：主线程的每一毫秒，都是你写下的每行代码的账单。
