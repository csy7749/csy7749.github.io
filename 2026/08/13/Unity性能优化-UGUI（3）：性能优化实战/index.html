Unity性能优化-UGUI（3）：性能优化实战

Created2026-08-13|Updated2026-08-17|Unity性能优化
|Post Views:

前两篇讲清了 UGUI 的底层机制和诊断方法，这一篇落地到可执行的代码。你会拿到一套”拿来即用”的优化武器库：脏值检查、CanvasGroup 显隐、Layout 禁用、TextMeshPro 迁移、Raycast 批量关闭、对象池与循环列表，最后用一个排行榜实战案例串起全部技巧，并给出可直接打印贴在工位上的 Checklist。

一、优化策略总览

按”投入产出比”从高到低排序，这就是本文的行进路线：

优先级 策略 一句话理由
★★★★★ 脏值检查 消除 80% 的无效 Rebuild，代价几乎为零
★★★★★ 关闭 Raycast Target 一行代码，EventSystem 压力骤降
★★★★☆ CanvasGroup 代替 SetActive 频繁显隐零重建
★★★★☆ 打 Sprite Atlas 消灭合批的最大敌人：纹理不一致
★★★★☆ 禁用 Layout Group 掐掉指数级递归计算
★★★☆☆ TextMeshPro 迁移 文字渲染全面降本
★★★☆☆ 对象池 + 循环列表 海量列表的唯一正解

下面逐个展开，每个都给完整代码。

二、脏值检查：先把无意义的重建掐死

2.1 问题

void Update() {
    hpText.text = player.hp.ToString(); // 满血时每帧都在无意义重建
    scoreText.text = player.score.ToString();
}
```text

每帧两次字符串分配 + 两次 `SetVerticesDirty` → 每帧两次 Rebuild → 每帧两次 Rebatch。如果满血、分数不变，这些全是白干。

### 2.2 一个通用的脏值缓存

```csharp
// 通用脏值缓存：值不变就返回 false，不触发赋值
public struct DirtyValue<T> where T : System.IEquatable<T> {
    private T cached;
    private bool hasValue;

    public bool IsChanged(T newValue) {
        if (hasValue && cached.Equals(newValue)) return false;
        cached = newValue;
        hasValue = true;
        return true;
    }
}

public class HUD : MonoBehaviour {
    public TMP_Text hpText;
    public TMP_Text scoreText;
    private DirtyValue<int> hpCache = new DirtyValue<int>();
    private DirtyValue<int> scoreCache = new DirtyValue<int>();

    void Update() {
        if (hpCache.IsChanged(player.hp)) {
            hpText.SetText("{0}", player.hp);
        }
        if (scoreCache.IsChanged(player.score)) {
            scoreText.SetText("{0}", player.score);
        }
    }
}
```text

这个 `DirtyValue<T>` 可以复用到项目里任何"值变了才更新 UI"的场景。

## 三、CanvasGroup：频繁显隐的正确姿势

### 3.1 SetActive 的代价

`SetActive(false/true)` 会触发 Canvas 对 Dependencies 的全量重评估，进而 Rebuild + Rebatch。对于频繁切换的弹窗、Tab 页，这是持续的额外开销。

### 3.2 CanvasGroup.alpha 的零重建方案

```csharp
public class PopupPanel : MonoBehaviour {
    public CanvasGroup canvasGroup;

    public void Show() {
        canvasGroup.alpha = 1f;
        canvasGroup.interactable = true;
        canvasGroup.blocksRaycasts = true;
    }

    public void Hide() {
        canvasGroup.alpha = 0f;
        canvasGroup.interactable = false;   // 禁止交互
        canvasGroup.blocksRaycasts = false; // 同时关闭射线，双保险
    }
}
```text

三个属性配合使用，才能在"不可见"的同时"不可点、不挡射线"。只改 `alpha` 而不关 `blocksRaycasts`，元素虽然透明但依然会挡住后面的点击——这是常见翻车点。

> 注意：`CanvasGroup.alpha=0` 的元素仍在渲染管线里（Overdraw 仍在），所以它适合"频繁切换"，不适合"长期隐藏"。长期不用的界面还是应该 `SetActive(false)` 彻底移除。

## 四、Layout Group：初始化后立刻关掉

```csharp
public class AutoLayout : MonoBehaviour {
    public LayoutGroup layoutGroup;

    void Start() {
        // 先强制立即算一次布局，保证初始排列正确
        LayoutRebuilder.ForceRebuildLayoutImmediate(rectTransform);
        // 然后关闭自动布局，后续不再每帧递归计算
        layoutGroup.enabled = false;
    }

    // 如果运行时内容变了，手动触发一次即可
    public void Refresh() {
        layoutGroup.enabled = true;
        LayoutRebuilder.ForceRebuildLayoutImmediate(rectTransform);
        layoutGroup.enabled = false;
    }
}
```text

**底线**：无论如何，避免嵌套 Layout Group。`VerticalLayoutGroup` 里套 `HorizontalLayoutGroup` 的计算量会指数级放大，这是 UI 卡顿的经典元凶。

## 五、TextMeshPro 迁移：文字渲染的全面降本

### 5.1 为什么 TMP 更快

旧版 `Text` 用位图字体，每个字号一套纹理；TMP 用 SDF（Signed Distance Field），**一套字形图集通吃所有字号**，缩放不失真，且材质统一、顶点更省。

### 5.2 迁移时的性能要点

```csharp
// 旧版 Text：字符串拼接是 GC 重灾区
legacyText.text = "HP: " + hp + " / " + maxHp;  // 分配 3 个 string

// TMP 零分配写法：格式化参数直接进顶点，不拼字符串
tmpText.SetText("HP: {0} / {1}", hp, maxHp);

// 数字频繁变化时，用预分配的 char[] 甚至更快
private char[] buffer = new char[16];
void UpdateHP(int hp) {
    int len = hp.ToString(buffer); // 直接写入缓冲，零分配
    hpText.SetText(buffer, 0, len);
}
```text

### 5.3 TMP 的几个性能坑

- **TMP 的 `SetText(string)` 每次仍然会分配**——务必用 `SetText(string, params object[])` 或 `SetText(char[], ...)`
- **富文本 `<sprite>` 标签**会额外生成 Sprite 网格，高频场景慎用
- **`TMP_Text` 的 `autoSizeTextContainer`** 与 Best Fit 类似，每帧重算容器，尽量避免

## 六、Raycast Target：性价比最高的单行优化

每个 Image/Text 默认勾选 `Raycast Target`，导致 EventSystem 每次点击都要遍历 Canvas 下所有开启该选项的元素。**纯展示的元素全部该关掉。**

### 6.1 运行时批量关闭

```csharp
// 挂在一个界面根节点上，启动时批量关闭，再单独打开交互元素
public class RaycastCleaner : MonoBehaviour {
    public Graphic[] interactiveGraphics; // 真正需要交互的按钮

    void Awake() {
        // 先全部关闭
        foreach (var g in GetComponentsInChildren<Graphic>(true)) {
            g.raycastTarget = false;
        }
        // 再单独打开交互元素
        foreach (var g in interactiveGraphics) {
            g.raycastTarget = true;
        }
    }
}
```text

### 6.2 编辑器侧一键处理（推荐）

运行时处理能救急，但最干净的是在 Prefab 上直接关掉。写一个菜单脚本：

```csharp
#if UNITY_EDITOR
using UnityEditor;
using UnityEngine;
using UnityEngine.UI;

public static class RaycastTargetCleaner {
    [MenuItem("Tools/UI/关闭选中节点所有 Raycast Target")]
    public static void DisableRaycasts() {
        foreach (var go in Selection.gameObjects) {
            foreach (var g in go.GetComponentsInChildren<Graphic>(true)) {
                g.raycastTarget = false;
            }
        }
        EditorUtility.SetDirty(Selection.activeGameObject);
    }
}
#endif
```text

## 七、对象池与循环列表：海量列表的正解

### 7.1 为什么需要池

ScrollView 里 `Instantiate` + `Destroy` 每个 Item，会带来两个问题：

1. 首次 `Instantiate` 要构建整套 Graphic 网格，CPU 昂贵
2. `Destroy` 产生托管内存垃圾，触发 GC

### 7.2 通用 UI 对象池

```csharp
using System.Collections.Generic;
using UnityEngine;

public class UIPool<T> where T : Component {
    private readonly T prefab;
    private readonly Transform parent;
    private readonly Stack<T> pool = new Stack<T>();

    public UIPool(T prefab, Transform parent, int prewarm = 10) {
        this.prefab = prefab;
        this.parent = parent;
        for (int i = 0; i < prewarm; i++) {
            var item = Create();
            item.gameObject.SetActive(false);
            pool.Push(item);
        }
    }

    private T Create() => Object.Instantiate(prefab, parent);

    public T Get() {
        var item = pool.Count > 0 ? pool.Pop() : Create();
        item.gameObject.SetActive(true);
        return item;
    }

    public void Return(T item) {
        item.gameObject.SetActive(false);
        pool.Push(item);
    }
}
```text

### 7.3 循环列表的原理

当列表有数百上千条数据时，对象池也不够——你只应该实例化**可见的 10~20 个 Item**，滚动时复用它们渲染不同的数据行：

```text
可视区
┌─────────────┐
│ Item0 ← 数据行 37
│ Item1 ← 数据行 38
│ Item2 ← 数据行 39   ← 只有这 5 个 Item 真实存在
│ Item3 ← 数据行 40
│ Item4 ← 数据行 41
└─────────────┘
滚动时：往上滚，Item0 移到底部，改绑数据行 42
```text

GitHub 上的 `LoopScrollRect` 是成熟方案。核心思想：**Item 数量恒定，数据驱动内容，滚动时复用**。

### 7.4 自定义绘制：极致情况下的底牌

当标准组件无法满足时，继承 `Graphic` 自己造网格：

```csharp
public class SimpleProgressGraphic : Graphic {
    public float progress;

    protected override void OnPopulateMesh(VertexHelper vh) {
        vh.Clear();
        var rect = GetPixelAdjustedRect();
        float width = rect.width * Mathf.Clamp01(progress);
        // 手动添加 4 顶点 + 2 三角形，绕过标准 Image 的开销
        AddQuad(vh, new Rect(rect.x, rect.y, width, rect.height), color);
    }

    private void AddQuad(VertexHelper vh, Rect r, Color c) {
        int i = vh.currentVertCount;
        vh.AddVert(new Vector3(r.xMin, r.yMin), c, Vector2.zero);
        vh.AddVert(new Vector3(r.xMin, r.yMax), c, Vector2.up);
        vh.AddVert(new Vector3(r.xMax, r.yMax), c, Vector2.one);
        vh.AddVert(new Vector3(r.xMax, r.yMin), c, Vector2.right);
        vh.AddTriangle(i, i + 1, i + 2);
        vh.AddTriangle(i + 2, i + 3, i);
    }
}
```text

## 八、框架层面的两条纪律

### 8.1 Transform.Find 只能出现在初始化

```csharp
// 好：Awake 里 Find + 缓存
private TMP_Text hpText;

void Awake() {
    hpText = transform.Find("HPText").GetComponent<TMP_Text>();
}

// 坏：Update 里 Find
void Update() {
    transform.Find("HPText").GetComponent<TMP_Text>().text = "..."; // 灾难
}
```text

### 8.2 LateUpdate 统一赋值的前提

同一帧多个模块改同一个 Text 时，可推迟到 `LateUpdate` 统一赋值，但必须满足：
1. 配合脏值检查
2. 动态 Text 放在独立子 Canvas

**不要无脑把全部 Text 塞进 LateUpdate**——那等于把无效计算集中到帧末。

## 九、实战案例：排行榜从 120ms 到 15ms

### 9.1 场景

在线游戏排行榜：ScrollView 100 个 Item，每个含头像（Image）、玩家名（Text）、分数（Text）、段位图标（Image）。Profiler 显示 `Canvas.SendWillRenderCanvases` 单帧 **120ms**，滚动时帧率 **15 FPS**。

### 9.2 诊断四步

| 步骤 | 工具 | 发现 |
| :--- | :--- | :--- |
| 1 | Profiler → UI Details | `Batches: 420`，`Vertices: 85,000` |
| 2 | Frame Debugger | 每个头像都"different texture"——头像来自 100 个不同 Sprite，没打图集 |
| 3 | Profiler → CPU | `GridLayoutGroup.SetLayoutVertical` 每帧都在跑 |
| 4 | 代码审查 | Item 的 `OnEnable` 里实时 `GetComponent<Text>`，未缓存 |

### 9.3 修复五招

```csharp
// 1. 头像打图集：把 100 个头像 Sprite 放进一个 SpriteAtlas
//    （编辑器操作，DrawCall 从 420 → 15）

// 2. 禁用 Layout Group
void Start() {
    LayoutRebuilder.ForceRebuildLayoutImmediate(rectTransform);
    gridLayout.enabled = false;
}

// 3. 对象池 + Awake 缓存组件
public class RankItem : MonoBehaviour {
    public TMP_Text nameText;
    public TMP_Text scoreText;
    public Image icon;

    void Awake() {
        nameText = transform.Find("Name").GetComponent<TMP_Text>();
        scoreText = transform.Find("Score").GetComponent<TMP_Text>();
        icon = transform.Find("Icon").GetComponent<Image>();
    }
}

// 4. 批量关闭 Raycast Target（只留按钮）
// 5. 分数/排名加脏值检查
```text

### 9.4 验证结果

| 指标 | 优化前 | 优化后 |
| :--- | :--- | :--- |
| `SendWillRenderCanvases` | 120ms | 15ms |
| Batches | 420 | 18 |
| Vertices | 85,000 | 12,000 |
| 帧率 | 15 FPS | 58 FPS |
| GC Alloc/帧 | 6.2 MB | 0.3 KB |

## 十、优化 Checklist

每次 UI 优化，按此清单过一遍（可直接打印）：

1. **[ ] 分析**：真机 Profiler + UI Details，定位是 Rebuild（`SendWillRenderCanvases`）还是 Rebatch（`BuildBatch`）吃 CPU
2. **[ ] 图集**：同界面图片是否在同一个 Sprite Atlas
3. **[ ] Canvas 拆分**：静态 UI 与动态 UI 是否分开 Canvas
4. **[ ] 脏值检查**：所有动态 Text/Image 是否加了变化判断
5. **[ ] Raycast Target**：非交互元素是否已批量关闭
6. **[ ] Mask → RectMask2D**：所有矩形遮罩是否已替换
7. **[ ] Layout Group**：是否初始化后禁用、是否消除嵌套
8. **[ ] TextMeshPro**：文字是否已从旧版 Text 迁移，是否用 `SetText` 格式化
9. **[ ] 对象池**：ScrollView Item 是否用池管理，海量列表是否用循环列表
10. **[ ] 验证**：相同环境下再次 Profiling，对比关键指标

## 十一、三篇合起来怎么用

- **第 1 篇（底层机制）**：建立认知——为什么这些策略有效
- **第 2 篇（Rebuild/Rebatch）**：掌握诊断——用工具看清到底哪里卡
- **第 3 篇（本篇）**：直接执行——抄代码 + 过 Checklist

遇到 UI 卡顿时，正确打开顺序是：先按第 2 篇的方法定位（Rebuild 还是 Rebatch），再回第 3 篇找对应武器，原理忘了就翻第 1 篇。三篇构成"原理 → 诊断 → 实战"的完整闭环。
