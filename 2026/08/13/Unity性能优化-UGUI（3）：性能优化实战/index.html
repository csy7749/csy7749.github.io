Unity性能优化-UGUI（3）：性能优化实战

Created2026-08-13|Updated2026-08-18|Unity性能优化
|Post Views:

前两篇讲清了 UGUI 的底层机制和诊断方法，这一篇落地到可执行的代码。你会拿到一套”拿来即用”的优化武器库：脏值检查、CanvasGroup 显隐、Layout 禁用、TextMeshPro 迁移、Raycast 批量关闭、对象池与循环列表，最后用一个排行榜实战案例串起全部技巧，并给出可直接打印贴在工位上的 Checklist。

一、优化策略总览

按”投入产出比”从高到低排序，这就是本文的行进路线：

优先级 策略 一句话理由
★★★★★ 脏值检查 消除 80% 的无效 Rebuild，代价几乎为零
★★★★★ 关闭 Raycast Target 一行代码，EventSystem 压力骤降
★★★★☆ CanvasGroup 代替 SetActive 频繁显隐零重建
★★★★☆ 打 Sprite Atlas 消灭合批的最大敌人：纹理不一致
★★★★☆ 禁用 Layout Group 掐掉指数级递归计算
★★★☆☆ TextMeshPro 迁移 文字渲染全面降本
★★★☆☆ 对象池 + 循环列表 海量列表的唯一正解

三、CanvasGroup：频繁显隐的正确姿势

3.1 SetActive 的代价

SetActive(false/true) 会触发 Canvas 对 Dependencies 的全量重评估，进而 Rebuild + Rebatch。对于频繁切换的弹窗、Tab 页，这是持续的额外开销。

3.2 CanvasGroup.alpha 的零重建方案

三个属性配合使用，才能在”不可见”的同时”不可点、不挡射线”。只改 alpha 而不关 blocksRaycasts，元素虽然透明但依然会挡住后面的点击——这是常见翻车点。

注意：CanvasGroup.alpha=0 的元素仍在渲染管线里（Overdraw 仍在），所以它适合”频繁切换”，不适合”长期隐藏”。长期不用的界面还是应该 SetActive(false) 彻底移除。

四、Layout Group：初始化后立刻关掉

底线：无论如何，避免嵌套 Layout Group。VerticalLayoutGroup 里套 HorizontalLayoutGroup 的计算量会指数级放大，这是 UI 卡顿的经典元凶。

五、TextMeshPro 迁移：文字渲染的全面降本

5.1 为什么 TMP 更快

旧版 Text 用位图字体，每个字号一套纹理；TMP 用 SDF（Signed Distance Field），一套字形图集通吃所有字号，缩放不失真，且材质统一、顶点更省。

5.2 迁移时的性能要点

5.3 TMP 的几个性能坑

  • TMP 的 SetText(string) 每次仍然会分配——务必用 SetText(string, params object[]) 或 SetText(char[], ...)
  • 富文本 <sprite> 标签会额外生成 Sprite 网格，高频场景慎用
  • TMP_Text 的 autoSizeTextContainer 与 Best Fit 类似，每帧重算容器，尽量避免

六、Raycast Target：性价比最高的单行优化

每个 Image/Text 默认勾选 Raycast Target，导致 EventSystem 每次点击都要遍历 Canvas 下所有开启该选项的元素。纯展示的元素全部该关掉。

八、框架层面的两条纪律

8.1 Transform.Find 只能出现在初始化

8.2 LateUpdate 统一赋值的前提

同一帧多个模块改同一个 Text 时，可推迟到 LateUpdate 统一赋值，但必须满足：

  1. 配合脏值检查
  2. 动态 Text 放在独立子 Canvas

不要无脑把全部 Text 塞进 LateUpdate——那等于把无效计算集中到帧末。

九、实战案例：排行榜从 120ms 到 15ms

9.1 场景

在线游戏排行榜：ScrollView 100 个 Item，每个含头像（Image）、玩家名（Text）、分数（Text）、段位图标（Image）。Profiler 显示 Canvas.SendWillRenderCanvases 单帧 120ms，滚动时帧率 15 FPS。

9.2 诊断四步

2 Frame Debugger 每个头像都”different texture”——头像来自 100 个不同 Sprite，没打图集
3 Profiler → CPU GridLayoutGroup.SetLayoutVertical 每帧都在跑
4 代码审查 Item 的 OnEnable 里实时 GetComponent<Text>，未缓存

十、优化 Checklist

每次 UI 优化，按此清单过一遍（可直接打印）：

  1. [ ] 分析：真机 Profiler + UI Details，定位是 Rebuild（SendWillRenderCanvases）还是 Rebatch（BuildBatch）吃 CPU
  2. [ ] 图集：同界面图片是否在同一个 Sprite Atlas
  3. [ ] Canvas 拆分：静态 UI 与动态 UI 是否分开 Canvas
  4. [ ] 脏值检查：所有动态 Text/Image 是否加了变化判断
  5. [ ] Raycast Target：非交互元素是否已批量关闭
  6. [ ] Mask → RectMask2D：所有矩形遮罩是否已替换
  7. [ ] Layout Group：是否初始化后禁用、是否消除嵌套
  8. [ ] TextMeshPro：文字是否已从旧版 Text 迁移，是否用 SetText 格式化
  9. [ ] 对象池：ScrollView Item 是否用池管理，海量列表是否用循环列表
  10. [ ] 验证：相同环境下再次 Profiling，对比关键指标

十一、三篇合起来怎么用

  • 第 1 篇（底层机制）：建立认知——为什么这些策略有效
  • 第 2 篇（Rebuild/Rebatch）：掌握诊断——用工具看清到底哪里卡
  • 第 3 篇（本篇）：直接执行——抄代码 + 过 Checklist

遇到 UI 卡顿时，正确打开顺序是：先按第 2 篇的方法定位（Rebuild 还是 Rebatch），再回第 3 篇找对应武器，原理忘了就翻第 1 篇。三篇构成”原理 → 诊断 → 实战”的完整闭环。
