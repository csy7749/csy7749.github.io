游戏AI-GOAP（2）：框架深入

Created2026-08-08|Updated2026-08-17|游戏AIGOAP
|Post Views:

crashkonijn/GOAP 是目前 Unity 生态中最成熟的 GOAP 开源框架。这篇文章深入剖析它的架构设计——强类型的 Key 系统、Capability 配置模式、Local/Global 双层传感器、GraphBuilder+Resolver 的两阶段规划，以及多线程架构——看看一个工程化的 GOAP 实现是怎么把第一篇里的理论落到代码里的。

为什么选 crashkonijn/GOAP

Unity 生态中有好几个 GOAP 实现：adammyhre/Unity-GOAP 是教学向的最小实现，AkiKurisu/AkiGOAP 侧重可视化编辑器，mountain-goap 追求极简通用。而 crashkonijn/GOAP（以下简称 crashkonijn）是生产级的选择——多线程、强类型、Capability 模式配置，在性能和可维护性之间取得了很好的平衡[^1]。

它的设计哲学很明确：不是”给你一个 AI 模板拿去改”，而是”给你一套类型安全的 GOAP 基础设施，用它搭建你自己的 AI”。

整体架构

crashkonijn 的架构可以分为四个层次：

层次 组件 职责
配置层 CapabilityConfig / Goal / Action / Key 定义 AI 能做什么、想要什么
感知层 Sensor（Local / Global） 把游戏世界翻译成 GOAP 能读的状态
决策层 GraphBuilder + Resolver 从配置构建图，从图+状态中求解
执行层 AgentBehaviour / GoapActionProvider 驱动 Agent 移动、执行 Action

决策层和执行层是分离的：决策层不知道 Action 怎么执行，执行层不知道为什么要执行这个 Action。这让两端可以独立测试和替换[^1]。

Key 系统：强类型胜过字符串

这是 crashkonijn 与许多教学实现最大的不同。大多数 GOAP 教程用 Dictionary<string, int> 表示世界状态，类似这样：

// 字符串 Key —— 拼写错误不会被编译器发现
worldState["isHungry"] = 1;
worldState["hasWeapon"] = 0;
```text

crashkonijn 用**强类型 Key 类**替代字符串[^2]：

```csharp
// 每个 Key 是一个 C# 类，编译期保证类型安全
public class Hunger : WorldKeyBase { }
public class AppleCount : WorldKeyBase { }
public class HasWeapon : WorldKeyBase { }

// TargetKey 表示位置信息
public class ClosestApple : TargetKeyBase { }
public class WeaponCache : TargetKeyBase { }
```text

带来的好处：
- **编译期检查**：拼错 Key 名直接报编译错误，不会在运行时默默失败
- **IDE 支持**：自动补全、查找引用、重命名全部可用
- **避免 Key 冲突**：不同 Capability 的 Key 天然隔离

WorldKey 表示"值"（生命值、资源数量、布尔状态），TargetKey 表示"位置"（苹果树在哪、最近的敌人是谁）。Planner 在计算代价时会自动考虑 Agent 移动到 Target 的距离[^3]。

## Capability：可组合的 AI 模块

crashkonijn 不使用传统的"把所有 Action 丢到一个列表"的方式，而是引入了 **Capability** 概念[^2]：

```csharp
public class HungerCapabilityFactory : CapabilityFactoryBase
{
    public override ICapabilityConfig Create()
    {
        var builder = new CapabilityBuilder("HungerCapability");

        // 目标：饥饿值降到 20 以下
        builder.AddGoal<FixHungerGoal>()
            .AddCondition<Hunger>(Comparison.SmallerThan, 20);

        // 动作：吃苹果
        builder.AddAction<EatAppleAction>()
            .AddCondition<AppleCount>(Comparison.GreaterThanOrEqual, 1)
            .AddEffect<Hunger>(EffectType.Decrease)
            .SetTarget<AgentTarget>();

        // 动作：捡苹果
        builder.AddAction<PickupAppleAction>()
            .AddEffect<AppleCount>(EffectType.Increase)
            .SetTarget<ClosestApple>();

        // 传感器
        builder.AddWorldSensor<IsHungrySensor>().SetKey<Hunger>();
        builder.AddTargetSensor<ClosestAppleSensor>().SetTarget<ClosestApple>();

        return builder.Build();
    }
}
```text

一个 Capability 把一组相关的 Goal、Action、Sensor **打包成可复用的模块**。同一个 Agent 可以挂多个 Capability——比如同时有 HungerCapability（饿了找吃的）和 CombatCapability（看到敌人就战斗），每个都是独立配置的。

这种模式的威力在于：添加新行为不需要修改现有代码，新增一个 Capability 即可。

## Sensor：双层感知

传感器是 GOAP 连接游戏世界的接口。crashkonijn 的传感器按两个维度分类[^2]：

**按数据类型：**
- **WorldSensor**：提供数值型状态（Hunger=30、AppleCount=2）
- **TargetSensor**：提供位置型状态（ClosestApple 的 Vector3 坐标）

**按作用域：**
- **Local**：每个 Agent 独立感知，比如"我离最近的苹果多远"
- **Global**：所有 Agent 共享一份，比如"现在是白天还是黑夜"

```csharp
// Local WorldSensor —— 为每个 Agent 单独计算
[GoapId("IsHungrySensor-unique-id")]
public class IsHungrySensor : LocalWorldSensorBase
{
    public override SenseValue Sense(
        IActionReceiver agent, IComponentReference references)
    {
        var hunger = references.GetCachedComponent<HungerBehaviour>();
        return hunger.hunger > 80;  // 返回 bool，底层用 int 表示
    }
}

// Global WorldSensor —— 所有 Agent 共享
public class IsDaytimeSensor : GlobalWorldSensorBase
{
    public override SenseValue Sense()
    {
        return DayNightCycle.IsDaytime;
    }
}
```text

还有一个实用的组合器 **MultiSensor**，把多个传感器合并到一个类里。比如一个 AppleSensor 同时提供 ClosestApple（TargetKey）和 HasApple（WorldKey）：

```csharp
public class AppleSensor : MultiSensorBase
{
    public AppleSensor()
    {
        this.AddLocalTargetSensor<ClosestApple>((agent, references) =>
        {
            var closest = apples.Get().Closest(agent.Transform.position);
            return closest is null ? null : new TransformTarget(closest.transform);
        });

        this.AddLocalWorldSensor<HasApple>((agent, references) =>
        {
            var inventory = references.GetCachedComponent<InventoryBehaviour>();
            return inventory.Apples.Count > 0;
        });
    }
}
```text

传感器还支持 **Timer**，可以按固定间隔更新而不是每帧执行——对于不需要实时检测的状态（比如"附近有没有敌人"），能显著降低 CPU 开销[^2]。

## GraphBuilder + Resolver：两阶段规划

第一篇讲过 GOAP 的核心是 A* 反向搜索。crashkonijn 把这个过程拆成了两个阶段[^3]：

### 第一阶段：GraphBuilder（构建动作图）

GraphBuilder 遍历所有 Action，根据它们的 Conditions（前提）和 Effects（效果）构建一张**有向图**：
- 节点是世界状态
- 边是 Action
- 如果 Action A 的某个 Effect 满足了 Action B 的某个 Condition，A→B 就有一条边

关键优化：**图每个 AgentType 只构建一次**，缓存下来。因为 Action 的 Conditions 和 Effects 是静态的（编译时配置好的），不需要每帧重建。

### 第二阶段：Resolver（求解最优路径）

Resolver 用当前 WorldState（传感器实时数据）在缓存图上跑 A* 搜索：
- 从 Goal 出发，反向搜索
- 找到代价最低的 Action 序列
- 代价 = Action.BaseCost + 移动距离

这套设计让规划本身非常轻量——大部分工作（图构建）只在初始化时做一次[^3]。

## 多线程架构

crashkonijn 的规划跑在独立线程上，不和渲染帧耦合。这是它与其他 GOAP 库最大的性能差异：

- **主线程**：执行 Action（Perform）、移动、渲染
- **工作线程**：跑 Resolver 做 A* 搜索

当 Agent 进入 Idle 状态需要新计划时，Resolver 在后台线程求解，Agent 可以继续执行上一个计划（如果还有未完成的 Action）。求解完成后，新计划通过回调切回主线程执行[^1]。

这也解释了 F.E.A.R. 的老鼠问题——如果每个 Agent 都在主线程上同步做 A* 搜索，几十个 Agent 就能拖垮帧率。多线程方案让规划不阻塞渲染。

## Action 的完整生命周期

每个 Action 有一套清晰的生命周期方法[^2]：

| 方法 | 调用时机 | 职责 |
|------|----------|------|
| Created() | Action 实例化时 | 初始化，获取外部引用 |
| Start(agent, data) | 开始执行前 | 设置动画、播放音效 |
| Perform(agent, data, context) | 每帧调用 | 核心逻辑 |
| IsInRange(agent, distance, data, refs) | 每帧检查 | 判断是否到达目标范围 |
| ShouldStop(agent) | 每帧检查 | 是否需要中断 |
| IsCompleted(agent) | 每帧检查 | 是否执行完毕 |
| End(agent, data) | 结束后 | 清理、触发后续事件 |
| MayResolve(agent) | 暂停期间 | 是否允许 Planner 重新规划 |

还有个关键的控制方法 Perform 的返回值——ActionRunState，不是简单的 true/false，而是支持五种状态：

```csharp
ActionRunState.Continue;           // 继续执行
ActionRunState.ContinueOrResolve;  // 继续，但也允许重规划
ActionRunState.Stop;               // 停止（计划被打断）
ActionRunState.Completed;          // 完成，执行下一个 Action
ActionRunState.Wait(2.0f, false);  // 等待 2 秒（不重规划）
```text

Wait 状态很实用：比如攻击动作需要等动画播完，Perform 返回 Wait(1.5f, false)，Agent 会在 1.5 秒后再调用 Perform，期间不触发重规划。

## AgentBehaviour vs GoapActionProvider：决策与执行分离

crashkonijn 把 Agent 拆成了两个独立的组件[^4]：

- **AgentBehaviour**：执行层。负责移动（NavMesh）、执行 Action 的 Perform/Start/End。它不知道 Goal 是什么，只知道"现在要执行哪个 Action"。
- **GoapActionProvider**：决策层。管理 Goal 优先级、触发 Resolver 求解、把结果交给 AgentBehaviour。

它们之间通过接口通信：IActionProvider（提供下一个 Action）和 IActionReceiver（接收执行结果）。这种分离意味着——你可以把 GoapActionProvider 换成别的决策系统（比如行为树），AgentBehaviour 的代码不用改一行。

## 回顾

crashkonijn/GOAP 的设计精髓在于**类型安全 + 模块化 + 性能优先**：

- 强类型 Key 消除字符串拼写错误
- Capability 模式支持行为热插拔
- 双层传感器分离 Local/Global 感知
- GraphBuilder 缓存避免重复构图
- 多线程 Resolver 不阻塞渲染
- 决策与执行解耦，两端独立演化

这些设计不是凭空出现的——它们是对第一篇里提到的那些"实际使用中的问题"（状态表达、性能、可维护性）的工程化回答。
