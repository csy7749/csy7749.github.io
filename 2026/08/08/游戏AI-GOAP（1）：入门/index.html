游戏AI-GOAP（1）：入门

Created2026-08-08|Updated2026-08-08
|Post Views:

GOAP（Goal-Oriented Action Planning）是游戏 AI 中一种经典的决策架构——不靠手写状态机或行为树，而是让 NPC 自己组合动作来达成目标。这篇文章从 STRIPS 的起源聊起，梳理 GOAP 的核心组件、Planner 的 A* 搜索原理，以及 F.E.A.R. 里的实际应用和踩过的坑，作为这个系列的入门笔记。

GOAP 的来历

GOAP（Goal-Oriented Action Planning，目标导向型行动计划）的根在 1971 年——斯坦福研究院的 STRIPS（STanford Research Institute Problem Solver）规划系统[^1]。STRIPS 的核心思想很简单：把世界描述为一组状态，把动作描述为”前提条件 + 效果”的对，然后用反向搜索找出从当前状态到目标状态的动作序列。

2005 年，Monolith Productions 在 F.E.A.R. 中首次把 STRIPS 的思路搬进游戏[^2]。结果令人震惊——敌方士兵会主动找掩体、盲射、破窗、投掷手雷逼玩家走位、队友之间互相通信配合。这些行为不是脚本写死的，是 AI 自己规划的。F.E.A.R. 的 GOAP 实现至今仍被视为游戏 AI 的里程碑，主创 Jeff Orkin 也因此被广泛引用。

所以 GOAP 不是什么新东西——它是一个 50 年前的 AI 规划思路，在实时游戏环境中的工程化落地。

GOAP 解决什么问题

传统的有限状态机（FSM）在面对复杂行为时会迅速膨胀。一个 NPC 如果有 5 种行为，FSM 还能应付；如果有 20 种，状态之间的转换就会变成一张蜘蛛网。行为树（Behavior Tree）虽然比 FSM 更模块化，但本质上还是”开发者预设所有可能路径”的思路——树的深度和分支一多，维护成本同样指数级上升[^3]。

GOAP 的思路截然不同：不定义”在什么状态下做什么”，而是定义”每个动作需要什么条件、产生什么效果”。AI 自己组合动作。Jeff Orkin 的原话是”给 AI 一组可选动作，让它自己找出达成目标的路径”[^2]。

核心公式很简单，开发者只需要提供：

  • 动作库：一组可能的 Action，每个 Action 声明：
    • 前提条件（Conditions）：执行前必须满足的状态
    • 执行效果（Effects）：执行后会改变哪些状态
    • 代价（Cost）：执行这个动作的开销
  • 状态数据：分为两类——
    • 自身状态：Agent 自己的属性，比如 Hunger=30、HasWeapon=false
    • 世界状态：全局共享的信息，比如物体位置、昼夜时间、资源数量
  • 目标（Goal）：AI 需要达成的最终状态

核心组件

一个 GOAP 系统通常由四个核心组件构成：

组件 职责
Agent（代理） 主体，持有状态、目标、动作列表，驱动主循环
Action（动作） 可执行的行为单元，声明前置条件、效果、代价
Planner（规划器） 决策引擎，用 A* 搜索从当前状态到目标状态的最优路径
WorldState / Sensors 状态存储和感知层，维护自身状态和世界状态

Planner 的算法

Planner 的核心是 A* 搜索，这是几乎所有 GOAP 实现的标准选择（少数用 Dijkstra）[^1][^4]。

A* 在 GOAP 中的应用方式：

  • 节点 = 世界状态（不是空间坐标）
  • 边 = Action，边的权重 = Action 的 Cost
  • 启发函数：估算当前状态到目标状态的”距离”。这比空间 A* 复杂——因为状态空间的”距离”不是欧几里得距离，通常用未满足的目标条件数量作为启发值[^5]

搜索方向是反向链接（Backward Chaining / Regressive Search）：从目标状态出发，问”什么动作能产生这个效果？”，然后检查该动作的前提条件是否满足。不满足的条件变成新的子目标，继续往回推，直到所有条件都落在当前状态内[^3]。

比前向搜索高效的原因很简单：前向搜索会探索所有可能动作的分支，反向搜索只探索”对达成目标有用”的分支。

自身状态 vs 世界状态

GOAP 在规划时同时读取两类状态。Planner 对它们一视同仁——只要某个 Action 的前置条件涉及某个 Key，不管来自自身还是世界，满足就过。

区分它们的实际意义在传感器（Sensor）的作用域：

  • 自身状态：由挂载在 Agent 上的局部传感器维护。比如每个 Agent 单独感知自己的饥饿值。
  • 世界状态：由全局传感器集中管理，避免每个 Agent 重复计算。比如昼夜判断只需要一份。

实际框架（比如 crashkonijn/GOAP）会明确区分 LocalSensor 和 GlobalSensor[^6]。

主循环

整个决策流程是一个简洁的状态机：

  1. Agent 进入 Idle，从传感器获取当前自身状态和世界状态
  2. Planner 用 A* 搜索最优动作序列
  3. 切换到 PerformAction，依次执行
  4. 需要靠近目标时切到 MoveTo，到位后继续
  5. 全部完成，回到 Idle，等待下一个目标

注意：世界状态在持续变化。如果执行过程中世界发生了重大变化（比如敌人突然出现），Agent 会打断当前计划、重新规划。这和模型预测控制（MPC）的”执行一步 → 观测 → 重规划”循环是同一个思路[^3]。

一个例子：NPC 士兵

假设做一个 NPC 士兵，目标：KillEnemy（杀死敌人）。

  • 杀死敌人 → 需要武器（自身状态：HasWeapon=true）
  • 当前没武器 → 触发”寻找武器”动作
  • 有武器库（世界状态：WeaponCacheExists=true）→ 从武器库拿
  • 没武器库 → 寻路去捡
  • 拿到武器 → 需要找到敌人（世界状态：EnemyVisible=true）
  • 找到了 → 靠近敌人（世界状态：DistanceToEnemy < 5）
  • 可以徒步，也可以开车过去……

NPC 的决策同时依赖自身状态和世界状态，只定义动作的条件和效果，NPC 自己决定怎么组合。输出的行为动态、合理但难以预测——F.E.A.R. 里那些让玩家以为对面是真人的战术配合，就是这样涌现出来的[^2]。

F.E.A.R. 的一个有趣细节

F.E.A.R. 中有一个著名的性能 bug：开发团队花了多年才发现，某些关卡中 GOAP 规划器的额外性能开销来自——老鼠。关卡里的老鼠也是 GOAP Agent，每个老鼠都在不断重规划自己的目标，累积起来拖慢了整个规划系统。这个事后来被 Eric Jacopin 在 2014 年的一篇研究论文中详细分析过[^2]。

实际使用中的问题

  • 状态表达能力有限：大多数 GOAP 实现用 Dictionary<Key, int> 表示状态，数值型没问题，但”正在被攻击””处于眩晕”这类标签状态不好表达。
  • 目标饥饿问题：如果目标按固定优先级排列，AI 可能永远卡在第一个目标上，忽略其他需求。需要用基于效用（Utility）的动态优先级来打破[^4]。
  • 多目标并行困难：同时想要”不饿”+”不渴”，但没有一个 Action 能同时满足两个目标，需要 Planner 支持多轮规划。
  • 性能：大量 Agent 同时规划会拖累帧率。F.E.A.R. 的老鼠问题就是典型[^2]。解决方案是规划线程与渲染线程分离[^3]。
