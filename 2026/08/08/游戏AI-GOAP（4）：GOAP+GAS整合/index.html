游戏AI-GOAP（4）：GOAP + GAS 整合设计

Created2026-08-08|Updated2026-08-17|游戏AIGOAP
|Post Views:

GOAP 负责”做什么”，GAS（Gameplay Ability System）负责”怎么做”——前者是目标驱动的决策引擎，后者是能力驱动的执行框架。这篇文章探讨如何把两者整合成一个统一的 AI 架构：用 GAS 的属性和标签作为 GOAP 的世界状态，用 GAS 的能力作为 GOAP 的可执行 Action，让 AI 在”知道自己要什么”和”知道自己能做什么”之间建立闭环。

为什么整合

单独的 GOAP 有一个明显的短板：它只知道”要做这件事”，不知道”怎么做这件事”。GOAP 规划出 EatFood 这个 Action 之后，执行层怎么处理冷却时间？怎么管理资源消耗？怎么触发动画和音效？怎么处理 buff/debuff？这些全得自己写。

GAS 天然处理这些问题——能力（Ability）自带冷却、消耗、标签（Tag）、效果（GameplayEffect）和表现（Cue）[^1]。把 GOAP 的 Action 映射到 GAS 的 Ability，执行层的工作量大幅减少。

反过来，GAS 单独用也有局限：它只是一个”能力仓库”，没有规划能力。需要外部系统告诉它”现在该用哪个技能”。GOAP 的 Planner 正好填补这个空白。

所以整合的逻辑很自然：GOAP 做决策，GAS 做执行。

共享的基础设施

两个系统有一些天然可以合并的模块[^2]：

模块 GOAP 中的角色 GAS 中的角色 合并后
状态 WorldKey（Hunger, Health） Attribute（属性值） 统一的属性系统
标签 用 WorldKey 模拟（IsHungry, HasWeapon） GameplayTag（标记状态） 统一的标签系统
行为单元 Action（EatFood, Attack） Ability（技能实例） Ability = Action 的执行体
效果 Effect（Hunger -= 30） GameplayEffect（属性修改） GameplayEffect = Effect 的实现

合并后的 Agent 架构：

AIController（入口）
├── GOAPPlanner（决策层：选择目标、生成计划）
│   ├── Goal 数据（什么是"想要"）
│   └── 读取 Attributes + Tags（世界状态）
├── GASAbilitySystem（执行层：运行能力）
│   ├── Attributes（属性系统）
│   ├── Tags（状态标签）
│   ├── Abilities（能力执行体）
│   └── GameplayEffects（属性修改）
└── Debugger / Recorder（调试层）
```text

决策层和执行层彼此只通过 Attributes 和 Tags 通信——GOAPPlanner 不直接调用 Ability，GASAbilitySystem 不直接读取 Goal。这是整篇文章的核心理念：**用共享数据替代直接耦合**。

## 属性驱动规划

这是整合后最精妙的部分。标准 GOAP 的流程是[^3]：

```text
传感器读取当前状态 → Planner 用状态匹配 Goal → 生成计划 → 执行
```text

整合 GAS 后，流程变成：

```text
属性变化 → 触发 GameplayEffect → 添加/移除 Tag → GOAP 读取 Tag → 重新规划
```text

一个具体例子：假设有个 NPC 角色，它的配置如下：

```csharp
// 属性定义
Attributes:
  Hunger    (0-100)    // 饱腹值，越高越饿
  Thirst    (0-100)    // 口渴值
  Health    (0-100)    // 生命值

// 阈值触发的标签规则
Hunger > 70  → 添加 Tag: "Hungry"
Hunger < 20  → 移除 Tag: "Hungry"
Hunger > 90  → 添加 Tag: "Starving"
Health < 30  → 添加 Tag: "Wounded"

// GOAP 的 Goal
Goal: FixHunger
  条件: HasTag("Hungry") = false    // 不饿了就算完成

Goal: Survive
  条件: HasTag("Wounded") = false   // 脱离濒死状态

// GOAP 的 Action（每个映射到一个 GAS Ability）
Action: EatFood → Ability: Eat
  条件: HasTag("Hungry") = true, HasFood = true
  效果: Hunger -= 30, RemoveTag("Hungry")

Action: SearchFood → Ability: Gather
  条件: HasFood = false
  效果: HasFood = true

Action: HealSelf → Ability: Heal
  条件: HasTag("Wounded") = true, HasMedkit = true
  效果: Health += 40, RemoveTag("Wounded")
```text

运作流程：

1. 时间流逝，Hunger 从 30 涨到 71
2. GameplayEffect 检测到 Hunger > 70，给 Agent 加上 Tag "Hungry"
3. GOAP 下一帧做规划：读取 Tags，发现 HasTag("Hungry") = true
4. Planner 匹配到 Goal FixHunger，生成计划 [SearchFood, EatFood]
5. 计划传回 GAS：激活 Gather Ability，完成后激活 Eat Ability
6. Eat Ability 执行 GameplayEffect：Hunger -= 30
7. Hunger 降到 41，不再 > 70，移除 Tag "Hungry"
8. GOAP 检测到 FixHunger 目标已达成，回到 Idle

整个过程中，GOAP 和 GAS 没有直接互相调用——它们通过 **Attributes→Tags→WorldState** 这条数据链做到解耦。Attribute 变了，Tag 跟着变，GOAP 读到 Tag 变化就自动重规划。

## GAS 能力替代 GOAP 的效果和传感器

前面的设计已经暗示了一点：GAS 的能力（Ability）不光能执行 Action，还能替代 GOAP 的两大组件[^2]。

### 替代 Effect

GOAP 中的 Effect 本质上就是"修改世界状态的某个值"。GAS 的 GameplayEffect 天然擅长这个：

| GOAP Effect | GAS GameplayEffect |
|-------------|-------------------|
| Hunger -= 30 | Instant Effect：减少 Hunger 属性 |
| Health += 40 | Instant Effect：增加 Health 属性 |
| 持续燃烧伤害 | Duration Effect：每秒 Health -= 5，持续 10s |
| 加速 buff | Infinite Effect：MoveSpeed + 50%，直到被移除 |

GAS 的 Effect 比 GOAP 的 Effect 强得多——支持瞬时/持续/永久三种类型、支持叠加（Stacking）、支持条件触发、支持 Tag 联动。

### 替代 Sensor

这是一个更激进的想法：用 GAS 的能力替代 GOAP 的传感器。标准 Sensor 是"被动查询数据"，GAS Ability 可以是"主动检测条件并打 Tag"：

```csharp
// 传统 GOAP 传感器 —— 被 Planner 调用时返回
public class EnemyDetector : LocalWorldSensorBase
{
    public override SenseValue Sense(IActionReceiver agent, ...)
    {
        return Physics.OverlapSphere(agent.Position, 10f).Any(x => x.IsEnemy);
    }
}

// GAS 能力替代 —— 主动检测，打 Tag
public class EnemyDetectionAbility : GameplayAbility
{
    // 每 0.5s 检测一次周围敌人
    // 检测到 → 给自身添加 Tag "EnemyNearby"
    // 丢失目标 → 移除 Tag "EnemyNearby"
}
```text

好处是传感器逻辑可以复用 GAS 的冷却、消耗、条件限制——比如"只有清醒状态下才能感知敌人"、"感知能力需要消耗注意力值"。坏处是增加了复杂度——简单的数值查询用传统 Sensor 更轻量。

两个原则：
- **数值型状态**（Hunger、Health）→ 用属性系统 + 阈值触发 Tag
- **感知型状态**（EnemyNearby、ItemVisible）→ 用轻量 Sensor，除非需要冷却/消耗

## 目标驱动的能力激活

这是整合后的完整决策循环[^2]：

```text
┌─────────────────────────────────────────┐
│  GOAPPlanner                             │
│  ┌─────────┐  ┌──────────┐  ┌────────┐ │
│  │ Goals   │→│ Planner  │→│ Plan   │ │
│  └─────────┘  └──────────┘  └────────┘ │
│       ↑                          │       │
│  ┌────┴────┐              ┌──────┴────┐ │
│  │  Tags   │              │  Abilities│ │
│  └────┬────┘              └──────┬────┘ │
│       │                          │       │
├───────┼──────────────────────────┼───────┤
│  GASAbilitySystem                 │       │
│  ┌────┴────┐              ┌──────┴────┐ │
│  │Attributes│──Threshold──│GameplayEff│ │
│  └─────────┘              └───────────┘ │
└─────────────────────────────────────────┘
```text

流程：
1. Attributes 变化越过阈值 → GameplayEffect 更新 Tags
2. GOAPPlanner 读到 Tags 变化 → 重新评估 Goal 优先级
3. 选定 Goal → Planner 生成 Action 序列（每个 Action 对应一个 Ability）
4. 计划传给 GASAbilitySystem → 按顺序激活 Ability
5. Ability 执行产生 GameplayEffect → 修改 Attributes → 回到步骤 1

## 踩坑提醒

**不要把 Tag 膨胀成"另一种状态机"**。标签系统的初衷是标记布尔状态（饿了/受伤了/有敌人），但很容易演化成"用 Tag 的组合表达行为阶段"——比如 IsSearching + HasTarget + IsApproaching 组合来判断"正在追击"。这是行为树的逻辑，不该交给标签系统。

**属性阈值不要设太密**。Hunger 从 0 到 100 设了 5 个 Tag（Full, Satisfied, Neutral, Hungry, Starving），看起来精细，但每跨一个阈值就触发 GOAP 重规划——Agent 可能在两个阈值之间反复横跳（oscillation），导致行为抖动。加一个 hysteresis 窗口（比如降到 65 才移除"Hungry"而不是 70）能解决。

**Ability 的执行状态要同步回 GOAP**。不是所有的 Goal 都能被"属性变化"自动检测为完成。比如"杀死敌人"这个 Goal——GAS 执行完 Attack 之后，敌人死亡这件事需要通知 GOAP。不要在 Ability 里直接调 GOAP 的方法——通过 Tag（TargetDead）或事件系统通知。

## 回顾

GOAP + GAS 整合的核心是**用数据（Attributes + Tags）做中间层**，让决策和执行解耦：

- 属性变化 → 标签变化 → Planner 重评估
- 计划输出 → 能力激活 → 效果应用 → 属性变化（闭环）

这套架构让 AI 的行为链条完全自动化——你只需要配置"什么属性触发什么标签"和"什么标签对应什么 Goal"，剩下的规划、执行、重评估全部由系统完成。
