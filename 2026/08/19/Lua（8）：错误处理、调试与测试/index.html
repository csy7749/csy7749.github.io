Lua（8）：错误处理、调试与测试

Created2026-08-19|Updated2026-08-19|编程语言Lua
|Post Views:

游戏脚本最怕”一崩全黑”。Lua 的错误哲学是”错误是值，不是异常”：error 抛出任意值，pcall/xpcall 把它接住并返回。配合结构化错误对象和 traceback，才能做出”能定位、能上报、能恢复”的脚本层。这篇把错误处理、调试手段和单元测试一次讲清。

一、error 与 assert：显式的前置条件

assert 不满足就抛错：assert(条件, 消息)；error(消息, level) 手动抛：

error 的第二个参数 level 控制报错位置：默认 1（error 的调用处），2 是上层调用处；传 0 则不附加位置信息。给用户看的错误，尽量让 level 指向”调用方犯错的位置”。

二、pcall：保护调用

pcall 保护调用：pcall(fn, ...) 返回 (true, 结果...) 或 (false, 错误)，错误不会向上抛

pcall 适合”边界处兜底”（网络回调、配置加载、AI 决策），但注意：它只拦错误，不拦 os.exit、不拦宿主层崩溃，也不能当”隐藏 bug”的遮羞布——第 7 讲说过，load 系列返回错误值而不是抛错，调用方必须检查。

三、xpcall + debug.traceback：拿调用栈

xpcall 在出错时调用错误处理器：xpcall(fn, 错误处理器, ...)，最常用的是 debug.traceback

封装成统一入口是主程的必修课——所有 Lua 入口（热更回调、事件回调、定时器）都包一层 safe，崩溃时集中上报。

四、结构化错误：用 table 携带上下文

字符串错误信息只能”给人看”，程序没法按 code 处理。错误对象可以是任意值，用表能携带机器可读的字段：

规范建议：

  • 错误对象统一为 { code = 字符串, ... }，code 走枚举，message 走人读；
  • 边界统一转换：外部进来的错误（require 失败、网络数据）一律包成自己的 code；
  • 日志打印时提供”错误码 + 场景 + 上下文”三件套，别只记一行 message。

五、debug 库：查栈、取局部、挂钩子

线上排查靠 traceback，开发期靠 debug 库：

  • debug.traceback([thread [, message [, level]]])：把调用栈拼成字符串；
  • debug.getinfo(level, "Sl")：取源文件、当前行、函数名；
  • debug.sethook(fn, "cr")：挂调用/返回/行钩子，可做简易采样 profiler；
  • 5.1 的 setfenv/getfenv 已废弃，改用 _ENV（第 7 讲）。

注意 debug 库是”特权库”：沙箱里必须禁用，否则脚本能通过 debug.getupvalue 等绕开隔离。

七、单元测试：busted

工程建议：

  • 纯逻辑（算法、数值、配置解析）必须有单测；与宿主强耦合的部分用依赖注入把”宿主服务”换成桩；
  • CI 里跑 luac -p 语法检查 + busted 全量测试，脚本改动才有回归保障。

自查清单

  • 会用 assert/error，并理解 error 的 level 参数
  • 会用 pcall 兜底、xpcall + debug.traceback 取栈
  • 错误对象统一成 { code, message, ... }，边界处转换错误码
  • 知道 debug 库在沙箱里要禁用
  • 会写 busted 用例，并在 CI 里跑语法检查 + 单测
