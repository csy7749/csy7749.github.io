Lua（9）：性能优化与 LuaJIT

Created2026-08-19|Updated2026-08-19|编程语言Lua
|Post Views:

脚本性能问题 90% 出在写法，而不是语言本身。这一篇先给”先测量再优化”的方法，再讲 GC、常规优化清单，最后展开 LuaJIT 的 JIT 与 FFI——这是”会用”和”能调优”的分水岭。

一、先测量，再优化

没有数据就没有优化方向。用 os.clock 做微基准：

同一台机器上，.. 版本通常会比 table.concat 慢一个数量级以上——但结论要在自己的项目里验证，别照搬网上的数字。

二、GC 与对象生命周期

  • Lua 5.4 默认分代 GC（增量收集为辅），5.1~5.3 是增量 GC；LuaJIT 有自己的 GC 实现[^1]。
  • collectgarbage("count") 返回当前内存（KB），collectgarbage("collect") 手动触发。
  • GC 压力来自对象创建：table、闭包、字符串每创建一个都要被扫描。热路径的优化本质是”少建对象”。

三、常规优化清单（PUC Lua 与 LuaJIT 通用）

  1. local 化全局与库函数：访问局部变量比查全局环境快，循环里尤其明显。
  1. 少建表，复用表：高频函数里用”局部临时表反复清空”替代每次 local t = {}。

注意：清表用”置 nil”或 next(t) == nil 判断，别用 t = {}（那只是换引用，旧表还挂着等 GC）。

  1. 字符串拼接走 table.concat（见上文基准）。
  2. 避免无谓的数字↔字符串转换：tostring/tonumber 每次都有成本，热路径显式缓存结果。
  3. 别用 nil 当”占位”：它会让数组变稀疏、# 失效、遍历逻辑变复杂（第 4 讲）。
  4. 选择正确的数据结构：频繁”头部插入/删除”用双向链表思路而不是 table.remove(queue, 1)。

四、LuaJIT：JIT 与 trace

LuaJIT 把 Lua 5.1 代码编译成机器码：解释器先跑，识别热点循环后录制 trace（类型推导出稳定的执行路径），再编译成原生代码[^3]。

JIT 友好的代码特征：

  • 类型稳定：同一个变量始终是 number 或始终是 table，别一会儿数字一会儿字符串；
  • 循环体简单：大量动态创建函数、pairs 中修改表、vararg 滥用都会打断 trace；
  • 数字运算为主：纯数值热点能压到接近 C 的性能。

五、JIT 失效诊断

不是所有代码都能 JIT。诊断手段：

常见”编译中止”（NYI / exit）原因：

  • 调用了 JIT 未实现的库函数（部分 string、io、os 操作）；
  • 类型在循环里变化，trace 回退解释器；
  • coroutine 跨 trace 的复杂交互；
  • 大表遍历 + 遍历中修改表。

对策：先 -jv 看热点在哪、中止在哪，再决定是”改写法”还是”把这部分下沉到 C/C#”。别盲猜。

六、与 C# 互调的成本：批量化

xLua/ToLua 场景里，跨语言调用有固定开销（压栈、类型检查、P/Invoke 或生成代码）：

  • 每帧小调用（逐元素读写数组）是最大的浪费来源；
  • 设计批量接口：一次传整个表/数组，C# 侧循环处理，比 Lua 侧逐元素调 C# 快一个量级；
  • 用 LuaTable 缓存对象引用，别每次 CS.XXX.Find(...) 现查。

自查清单

  • 会写 os.clock 微基准，并坚持”先测量再优化”
  • 知道 5.4 分代 GC，会用弱表做缓存、collectgarbage("count") 观察内存
  • 掌握 6 条常规优化项（local 化、复用表、concat、少转换等）
  • 能用 luajit -jv 看热点与 trace 中止，区分”写法问题”与”NYI”
  • 设计跨语言接口时优先批量，避免每帧小调用
