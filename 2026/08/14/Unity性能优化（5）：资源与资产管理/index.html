Unity性能优化（5）：资源与资产管理

Created2026-08-14|Updated2026-08-18|Unity性能优化
|Post Views:

资源优化是”配置即性能”的典型——很多项目不改一行代码，只把纹理导入设置、音频格式、加载策略调一遍，就能砍掉一半内存和一半加载时间。本文按”导入 → 加载 → 卸载”三个阶段，逐个拆解纹理、网格、音频的导入设置，再对比 AssetBundle 与 Addressables 两种加载方案，最后给出一个首场景从 8 秒到 1.5 秒的实战案例。

一、资源三大阶段：导入 → 加载 → 卸载

一个资源的完整生命周期分三个阶段，每阶段的优化手段完全不同：

阶段 决定什么 优化手段
导入 资源在包里的格式、体积 Import Settings（本文 2~4 节）
加载 运行时进内存的速度和方式 AssetBundle / Addressables（本文第 5 节）
卸载 不用时能否正确释放 引用管理、UnloadUnusedAssets

最常见的坑：只关注加载（用了 Addressables 就以为万事大吉），却忽略了导入——一张 4096 的无压缩纹理，无论怎么加载，内存都是几百 MB。

所以正确的优化顺序是：先导入、再加载、最后卸载。

二、纹理优化：内存的绝对大头

纹理通常占游戏内存的 50% 以上，是第一优化对象。

2.1 Max Size：砍掉无意义的超大图

一张 4096 的 RGBA 纹理，内存占用约 64MB；降到 1024，只剩 4MB。很多纹理实际显示远小于 1024，砍尺寸是最划算的一刀。

2.2 POT vs NPOT

  • POT（Power of Two，2 的幂）：1024、512、256…… 大多数压缩格式和 MipMap 都要求 POT
  • NPOT：非 2 的幂，部分平台无法压缩、无法生成 MipMap

规则：纹理尽量用 2 的幂尺寸，否则压缩失效、内存膨胀。

2.3 压缩格式选择矩阵

格式 平台 内存占用 说明
ASTC 现代移动端 极低 首选，质量/压缩比最优
ETC2 移动端（旧） 低 兼容性好，支持 alpha
ETC 更旧移动端 低 不支持 alpha
DXT/BC 桌面 低 Windows/Mac
RGBA32（不压缩） 全平台 极高 除非有特殊需求，否则避免

规则：移动端首选 ASTC（现代设备）或 ETC2（兼容优先），绝不无脑用 RGBA32。

2.4 MipMap：按需开关

  • 3D 物体纹理：需要 MipMap（远处用低分辨率，避免锯齿和带宽浪费）
  • UI 纹理：不需要 MipMap（UI 永远近距离显示，开 MipMap 徒增 33% 内存）

2.5 Read/Write Enabled 的 2x 惩罚

勾选 Read/Write Enabled 后，Unity 会保留一份 CPU 可访问的纹理副本，内存占用翻倍。

绝大多数运行时只读的纹理，一律关闭。

2.6 Sprite Atlas：打包策略

图集不仅减少 DrawCall（见 UGUI 篇），还减少内存碎片。打包策略：

  • 按界面打包：同界面 UI 放一个图集（最适合 UI）
  • 按功能打包：同一功能模块的资源放一起
  • 避免：一张超大的全局图集（加载即全量进内存，反而不省）

三、网格与动画优化

3.1 Mesh Compression

开启网格压缩，顶点数据占用更小：

压缩级别越高，精度损失越大，但大多数场景 High 档的视觉差异可忽略。

3.2 顶点属性按需开关

网格的每个顶点属性都占内存，不需要的就关掉：

属性 用途 何时关
Tangents 法线贴图 不用法线贴图时关
UV2 光照贴图 不烘焙光照时关
Normals 光照 纯 UI/无光照模型关
Colors 顶点色 不用顶点色时关

3.3 BlendShape 的内存代价

每个 BlendShape 都会复制一份顶点数据。面部表情、口型动画用得上，但一个模型挂几十个 BlendShape，内存会成倍增长。按需精简。

3.4 Animation Clip 压缩

动画剪辑可开启 Keyframe Reduction（关键帧压缩）：

误差设得越大，压缩越狠，但动画越可能”漂移”，按视觉可接受度调。

3.5 Animator Controller 的 Layer 开销

每个 Animator Layer 都独立采样动画状态机。Layer 越多，CPU 开销越大。合并可合并的 Layer，减少无谓的状态机复杂度。

四、音频优化

4.1 加载类型三选一

类型 行为 适用
Decompress On Load 加载时解压成 PCM，运行时零解压 短音效（< 几秒）
Compressed In Memory 压缩存内存，播放时解压 中等长度
Streaming 边播边流式加载，不整段进内存 长音频（BGM、对白）

4.2 压缩格式与比特率

  • 音效：Vorbis/MP3，中低比特率（如 96~128kbps）
  • BGM：Streaming + 较低比特率，避免整段进内存
  • 原始未压缩 WAV：体积巨大，除非有特殊需求，否则导入时压缩

4.3 强制单声道

立体声比单声道多一倍的音频数据。音效一律强制单声道，只有需要声场定位的才保留立体声：

五、加载策略：AssetBundle vs Addressables

5.1 AssetBundle：手动但可控

AssetBundle 是传统方案，打包依赖、加载、卸载全手动：

  • 缺点：依赖关系手动维护、容易重复加载/卸载出错
  • 现状：老项目在用，新项目不建议手动造轮子

5.2 Addressables：引用计数 + 自动依赖

Addressables 是 Unity 官方的现代资源系统，核心优势：

  1. 引用计数：同一资源被多处引用，只在引用归零时才真正卸载
  2. 自动依赖：加载 A 时自动加载 A 依赖的 B
  3. 远程加载：资源可从 CDN/远程服务器拉取
  4. 分组策略：按功能分组，按需加载

5.3 加载 vs 预加载 vs 异步加载

方式 行为 适用
同步加载 阻塞，立即返回 启动必备资源
异步加载 不阻塞，完成后回调 进场景时加载
预加载 提前加载，用时不卡 即将用到的资源

原则：能异步就异步，能预加载就预加载，避免”用到时才同步加载”造成的卡顿。

5.4 Resources 文件夹的陷阱

Resources 文件夹里的资源会被全部打包进游戏、启动时建立索引，且无法热更新。它的三个坑：

  1. 索引常驻内存
  2. 无法做资源分级加载
  3. 无法远程更新

规则：新项目尽量不用 Resources，改用 Addressables。老项目里的 Resources 也应逐步迁移。

六、实战案例：首场景从 8 秒到 1.5 秒

6.1 症状

手游首场景加载 8 秒，玩家流失严重。Profiler 显示加载阶段纹理和音频占了大头。

6.2 诊断

  1. 纹理：多张 2048/4096 RGBA32 无压缩，无 MipMap 需求却开了 MipMap
  2. 音频：BGM 用 Decompress On Load，整段进内存
  3. 加载：全部资源塞 Resources 文件夹，启动时全量索引
  4. 无分级：热资源（登录界面）和冷资源（战斗资源）一起加载

6.4 验证

指标 优化前 优化后

七、资源优化 Checklist

  1. [ ] 纹理尺寸：大图已限 Max Size，无超 1024 的无 UI 纹理
  2. [ ] 纹理压缩：已用 ASTC/ETC2 等压缩格式，无 RGBA32
  3. [ ] MipMap：3D 开、UI 关
  4. [ ] Read/Write：无 CPU 读写需求的纹理已关闭
  5. [ ] 图集：UI 已按界面/功能打包 Sprite Atlas
  6. [ ] 网格：已开 Mesh Compression，无用顶点属性已关
  7. [ ] 动画：已开 Keyframe Reduction，Layer 已合并
  8. [ ] 音频：BGM Streaming、音效单声道、按需压缩
  9. [ ] 加载：已用 Addressables（或 AssetBundle），无 Resources
  10. [ ] 分级：热资源预加载、冷资源异步加载
  11. [ ] 卸载：Addressables.Release 成对调用，场景切换时 UnloadUnusedAssets
  12. [ ] 验证：复测加载时间、纹理/音频内存

八、结语

资源优化的回报是最”肉眼可见”的——内存从 600MB 降到 160MB，加载从 8 秒到 1.5 秒，都不需要改一行逻辑代码。核心就三句话：导入时砍体积（压缩/限尺寸），加载时分批按需（Addressables 分组），卸载时释放干净（引用计数）。把这三件事做成项目规范，资源问题基本就消灭在摇篮里了。
