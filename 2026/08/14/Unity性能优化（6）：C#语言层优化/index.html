Unity性能优化（6）：C# 语言层优化

Created2026-08-14|Updated2026-08-17|Unity性能优化
|Post Views:

前面五讲偏 Unity 引擎层，这一讲回归语言本身。很多分配和 CPU 问题，根源不在 Unity API，而在 C# 代码的写法：一个不该装箱的 struct、一条本该用 for 的 LINQ 链、一次 string 的 + 拼接。本文从值类型与引用类型讲起，覆盖集合选择、Span<T>、LINQ 代价、字符串处理和 unsafe，帮你把 C# 的每一个字节都算清楚。

一、值类型 vs 引用类型：先破除一个经典误解

1.1 struct 分配在栈？——看上下文

“struct 在栈上，class 在堆上”是流传最广、也最害人的一句话。真相是：分配位置取决于存放位置，不取决于类型。

public class Player {
    public Vector3 position;   // ① struct 作为类字段 → 分配在堆上（随 Player）
}

void Update() {
    Vector3 localPos;          // ② struct 作为局部变量 → 分配在栈上
    object boxed = localPos;   // ③ struct 被装箱 → 复制进堆上的 box
}
```text

### 1.2 struct 的陷阱：装箱

当值类型被当作 `object` 或接口使用时，会装箱——在堆上复制一份，并伴随分配：

```csharp
int hp = 100;
Debug.Log(hp);                 // ❌ Debug.Log(object) 装箱
IComparable c = hp;            // ❌ 值类型实现接口，装箱
ArrayList list = new ArrayList();
list.Add(hp);                  // ❌ ArrayList.Add(object) 装箱
```text

### 1.3 何时用 struct

满足这三个条件，用 struct 才能省分配：

- **小**（建议 < 16 字节，拷贝开销低于引用开销）
- **不可变**（避免意外的值拷贝）
- **短命**（局部使用，不长期驻留）

```csharp
// ✅ 好的 struct：小、只读、不会被装箱
public readonly struct PlayerInput {
    public readonly float horizontal;
    public readonly float vertical;
    public PlayerInput(float h, float v) {
        horizontal = h;
        vertical = v;
    }
}
```text

### 1.4 readonly struct 与 ref struct

- **`readonly struct`**：所有字段只读，编译器可避免防御性复制
- **`ref struct`**：只能存在于栈上，不能作为类字段、不能装箱、不能跨 `await`（`Span<T>` 就是典型的 `ref struct`）

### 1.5 典型错误：把 struct 当 class 用

```csharp
// ❌ 大 struct（几十字节）+ 频繁拷贝，反而比 class 更慢
public struct LargeData {
    public float a, b, c, d, e, f, g, h;  // 32 字节，拷贝开销已超引用
}

// ❌ 可变 struct 被装箱后修改，改的是副本不是本体
```text

struct 不是万能的，**用错地方比 class 更糟**。

## 二、集合选择：从分配和查找都要省

### 2.1 List\<T\> 的 Capacity 预分配

`List<T>` 内部是数组，元素超容量时会**扩容并复制整个数组**（分配新数组 + 拷贝旧数据）：

```csharp
// ❌ 默认容量 0/4，反复 Add 触发多次扩容复制
var list = new List<int>();
for (int i = 0; i < 1000; i++) list.Add(i);

// ✅ 预分配容量，一次到位
var list = new List<int>(1000);
for (int i = 0; i < 1000; i++) list.Add(i);
```text

### 2.2 Dictionary 的内部实现与碰撞

`Dictionary<TKey,TValue>` 用哈希桶存储，理想情况下查找是 O(1)。但**哈希碰撞会退化成 O(n)**。关键点：

- 自定义类型的 `GetHashCode` 要**分布均匀**，否则碰撞频繁
- 预分配容量同样重要（扩容会重新哈希所有键）

```csharp
// ✅ 预分配容量，避免扩容重哈希
var dict = new Dictionary<int, Enemy>(1000);
```text

### 2.3 HashSet vs List 查找

需要"判断是否存在"时：

```csharp
// ❌ List.Contains 是 O(n)，1000 个元素要遍历 1000 次
bool exists = list.Contains(target);

// ✅ HashSet.Contains 是 O(1)
bool exists = hashSet.Contains(target);
```text

高频"查重/去重"场景，`HashSet<T>` 比 `List<T>` 快几个数量级。

### 2.4 别再用 ArrayList / Hashtable

```csharp
// ❌ 遗留非泛型集合，装箱重灾区
ArrayList list = new ArrayList();
Hashtable table = new Hashtable();

// ✅ 泛型集合，零装箱
List<int> list = new List<int>();
Dictionary<int, string> table = new Dictionary<int, string>();
```text

### 2.5 .NET 新集合：ArrayPool\<T\>

需要频繁临时数组时，用池租借而非 new：

```csharp
using System.Buffers;

// ❌ 每次 new 一个临时数组
byte[] buffer = new byte[1024];

// ✅ 从池租借，用完归还
byte[] buffer = ArrayPool<byte>.Shared.Rent(1024);
try {
    // 使用 buffer...
} finally {
    ArrayPool<byte>.Shared.Return(buffer);  // 必须归还
}
```text

## 三、Span\<T\> 与 Memory\<T\>：零分配的切片

### 3.1 Span 是什么

`Span<T>` 是**栈上的类型安全指针**（`ref struct`），指向一段连续内存，不复制数据。它最大的价值是**切片和子串零分配**。

### 3.2 替代 Substring 的零分配方案

```csharp
string s = "Hello, Unity Performance";

// ❌ 每次 Substring 分配一个新 string
string sub = s.Substring(7, 5);   // "Unity"

// ✅ Span 切片，零分配
ReadOnlySpan<char> span = s.AsSpan(7, 5);
```text

配合 `string.Create` 或直接把 `Span` 传给接受 `ReadOnlySpan<char>` 的 API，全程零分配。

### 3.3 操作数组切片而不复制

```csharp
int[] numbers = { 1, 2, 3, 4, 5, 6, 7, 8 };

// ❌ 切片复制一份新数组
int[] middle = numbers[2..6];

// ✅ Span 切片，指向原数组，零复制
Span<int> middleSpan = numbers.AsSpan(2, 4);
```text

### 3.4 Span 的限制

- 不能作为类字段（它是 `ref struct`，不能逃离栈）
- 不能装箱
- 不能跨 `await`（async 方法里使用受限）

> 注：`Span<T>` 在 Unity 2021.2+（.NET Standard 2.1）可用，IL2CPP 后端已支持，但需引入 `System.Memory` 依赖。

## 四、LINQ 的代价

### 4.1 每个操作符都在分配

```csharp
// ❌ Where 分配委托 + 枚举器，ToList 再分配结果数组
var visible = enemies.Where(e => e.IsVisible).ToList();
```text

LINQ 的每个操作符（Where、Select、OrderBy）都分配枚举器对象，链越长分配越多。

### 4.2 高频路径用 for 替代

```csharp
// ✅ 初始化阶段用 LINQ（可读性优先）
var names = config.Select(c => c.name).ToList();

// ✅ 高频路径（Update/循环）用 for/foreach + if，零分配
visibleList.Clear();
for (int i = 0; i < enemies.Count; i++) {
    if (enemies[i].IsVisible) visibleList.Add(enemies[i]);
}
```text

### 4.3 判断标准

- **初始化、一次性执行**：LINQ 可接受，可读性优先
- **Update、循环内、高频事件**：一律 `for`/`foreach` + `if`

## 五、字符串与格式化

### 5.1 字符串不可变

字符串一旦创建就不可变，**每次拼接都分配新对象**：

```csharp
// ❌ 三个 + 三次分配
string s = "HP: " + hp + " / " + maxHp;
```text

### 5.2 StringBuilder 缓存 + Clear

```csharp
// ❌ 每次 new StringBuilder
var sb = new StringBuilder();
sb.Append(hp);

// ✅ 缓存一个，用 Clear 复用
private readonly StringBuilder sb = new StringBuilder(64);

void Update() {
    sb.Clear();
    sb.Append("HP: ").Append(hp).Append(" / ").Append(maxHp);
    label.text = sb.ToString();  // ToString 本身仍分配一次
}
```text

### 5.3 string.Format vs 插值

```csharp
string a = string.Format("HP: {0}", hp);
string b = $"HP: {hp}";   // 编译结果与 string.Format 等价
```text

两者编译后相同，**插值只是语法糖**，性能上没有区别。

### 5.4 string.Intern 的应用场景

重复出现的大量相同字符串（如枚举名、状态名）可以用 `string.Intern` 复用同一实例，减少重复分配：

```csharp
string status = string.Intern("Alive");  // 复用字符串池里的同一实例
```text

但**慎用**——它会让字符串常驻内存，滥用反而造成泄漏。

### 5.5 StringComparison.Ordinal

```csharp
// ❌ CurrentCulture 比较要做文化相关处理，慢
bool eq = a.Equals(b, StringComparison.CurrentCulture);

// ✅ 普通字符串比较用 Ordinal，快且行为确定
bool eq = a.Equals(b, StringComparison.Ordinal);
```text

## 六、unsafe 与指针：谨慎的底牌

当需要极致性能的大规模数组操作，或与 native 代码交互时，`unsafe` 指针可以避免边界检查和拷贝：

```csharp
unsafe void CopyFast(int[] src, int[] dst) {
    fixed (int* pSrc = src, pDst = dst) {
        for (int i = 0; i < src.Length; i++) {
            pDst[i] = pSrc[i];
        }
    }
}
```text

**但代价明确**：绕过安全机制、易出错、需要在项目设置开启 `Allow unsafe code`。**只有在 Profiler 确认是热点、且普通写法无法满足时，才考虑 unsafe。**

## 七、实战案例：伤害数字每帧 100KB GC

### 7.1 症状

战斗场景，每帧生成 200+ 个伤害数字，Profiler 显示 GC.Alloc 每帧 **100KB**，频繁触发 GC 卡顿。

### 7.2 诊断

定位到伤害数字生成逻辑，三个元凶：

```csharp
// 元凶1：字符串拼接
string text = damage + "";  // 每帧 200 次分配

// 元凶2：LINQ
var valid = damages.Where(d => d.active).ToList();  // 每帧分配

// 元凶3：new 临时数组
float[] arr = new float[damages.Length];  // 每帧分配
```text

### 7.3 修复

```csharp
// 修复1：StringBuilder 缓存 + TMP.SetText 格式化
private readonly StringBuilder sb = new StringBuilder(16);
sb.Clear();
sb.Append(damage);
damageText.SetText(sb);   // TMP 直接吃 StringBuilder，零额外分配

// 修复2：LINQ 换 for + 复用 List
validList.Clear();
for (int i = 0; i < damages.Count; i++) {
    if (damages[i].active) validList.Add(damages[i]);
}

// 修复3：临时数组换 ArrayPool / Span
```text

### 7.4 验证

| 指标 | 优化前 | 优化后 |
| :--- | :--- | :--- |
| GC.Alloc/帧 | 100KB | 2KB |
| GC 触发频率 | 每 2 秒 | 每 30 秒 |
| 战斗帧率 | 42 FPS | 60 FPS |

## 八、C# 优化 Checklist

1. **[ ] struct 审查**：无大 struct、无可变 struct、无不当装箱
2. **[ ] 装箱**：值类型未被当 object/接口传，无 ArrayList/Hashtable
3. **[ ] List 容量**：已知大小的 List 已预分配 Capacity
4. **[ ] 查找**：高频查重已用 HashSet，键值用 Dictionary
5. **[ ] 临时数组**：高频 new 数组已换 ArrayPool 或 Span
6. **[ ] 切片**：Substring/数组切片已用 Span 零分配
7. **[ ] LINQ**：Update/循环内无 LINQ，已换 for + if
8. **[ ] 字符串**：高频拼接已用 StringBuilder 缓存，比较用 Ordinal
9. **[ ] unsafe**：仅在确认热点且必要时使用
10. **[ ] 验证**：Profiler GC.Alloc 明显下降

## 九、结语

C# 优化的本质是**对每一次分配保持警惕**：struct 别装箱、集合别扩容、切片别复制、字符串别拼接、LINQ 别进循环。这些规则不复杂，难的是在高频路径上坚持执行。养成一个习惯：**写 Update 里的代码时，把每一行都当成"这行每帧跑 60 次"来审视**——很多优化，就在这个审视里自动完成了。
