Unity性能优化（6）：C# 语言层优化

Created2026-08-14|Updated2026-08-18|Unity性能优化
|Post Views:

前面五讲偏 Unity 引擎层，这一讲回归语言本身。很多分配和 CPU 问题，根源不在 Unity API，而在 C# 代码的写法：一个不该装箱的 struct、一条本该用 for 的 LINQ 链、一次 string 的 + 拼接。本文从值类型与引用类型讲起，覆盖集合选择、Span<T>、LINQ 代价、字符串处理和 unsafe，帮你把 C# 的每一个字节都算清楚。

一、值类型 vs 引用类型：先破除一个经典误解

1.1 struct 分配在栈？——看上下文

“struct 在栈上，class 在堆上”是流传最广、也最害人的一句话。真相是：分配位置取决于存放位置，不取决于类型。

1.2 struct 的陷阱：装箱

当值类型被当作 object 或接口使用时，会装箱——在堆上复制一份，并伴随分配：

1.3 何时用 struct

满足这三个条件，用 struct 才能省分配：

  • 小（建议 < 16 字节，拷贝开销低于引用开销）
  • 不可变（避免意外的值拷贝）
  • 短命（局部使用，不长期驻留）

1.4 readonly struct 与 ref struct

  • readonly struct：所有字段只读，编译器可避免防御性复制
  • ref struct：只能存在于栈上，不能作为类字段、不能装箱、不能跨 await（Span<T> 就是典型的 ref struct）

1.5 典型错误：把 struct 当 class 用

struct 不是万能的，用错地方比 class 更糟。

Dictionary<TKey,TValue> 用哈希桶存储，理想情况下查找是 O(1)。但哈希碰撞会退化成 O(n)。关键点：

  • 自定义类型的 GetHashCode 要分布均匀，否则碰撞频繁
  • 预分配容量同样重要（扩容会重新哈希所有键）

三、Span<T> 与 Memory<T>：零分配的切片

3.1 Span 是什么

Span<T> 是栈上的类型安全指针（ref struct），指向一段连续内存，不复制数据。它最大的价值是切片和子串零分配。

3.2 替代 Substring 的零分配方案

配合 string.Create 或直接把 Span 传给接受 ReadOnlySpan<char> 的 API，全程零分配。

3.3 操作数组切片而不复制

3.4 Span 的限制

  • 不能作为类字段（它是 ref struct，不能逃离栈）
  • 不能装箱
  • 不能跨 await（async 方法里使用受限）

注：Span<T> 在 Unity 2021.2+（.NET Standard 2.1）可用，IL2CPP 后端已支持，但需引入 System.Memory 依赖。

四、LINQ 的代价

4.1 每个操作符都在分配

LINQ 的每个操作符（Where、Select、OrderBy）都分配枚举器对象，链越长分配越多。

  • Update、循环内、高频事件：一律 for/foreach + if

八、C# 优化 Checklist

  1. [ ] struct 审查：无大 struct、无可变 struct、无不当装箱
  2. [ ] 装箱：值类型未被当 object/接口传，无 ArrayList/Hashtable
  3. [ ] List 容量：已知大小的 List 已预分配 Capacity
  4. [ ] 查找：高频查重已用 HashSet，键值用 Dictionary
  5. [ ] 临时数组：高频 new 数组已换 ArrayPool 或 Span
  6. [ ] 切片：Substring/数组切片已用 Span 零分配
  7. [ ] LINQ：Update/循环内无 LINQ，已换 for + if
  8. [ ] 字符串：高频拼接已用 StringBuilder 缓存，比较用 Ordinal
  9. [ ] unsafe：仅在确认热点且必要时使用
  10. [ ] 验证：Profiler GC.Alloc 明显下降

九、结语

C# 优化的本质是对每一次分配保持警惕：struct 别装箱、集合别扩容、切片别复制、字符串别拼接、LINQ 别进循环。这些规则不复杂，难的是在高频路径上坚持执行。养成一个习惯：写 Update 里的代码时，把每一行都当成”这行每帧跑 60 次”来审视——很多优化，就在这个审视里自动完成了。
