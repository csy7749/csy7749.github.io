Unity性能优化（2）：GPU 与渲染优化

Created2026-08-14|Updated2026-08-17|Unity性能优化
|Post Views:

解决了 CPU，就该看 GPU 了。很多项目 CPU 主线程并不忙，帧率却上不去——瓶颈在渲染端：DrawCall 太多、Shader 太重、Overdraw 太凶。本文从渲染管线讲起，教你判断 GPU 瓶颈，再重点拆解四种合批方案（静态/动态 Batching、SRP Batcher、GPU Instancing）的适用边界，最后覆盖 Shader、LOD、光照与后处理，配一个大世界 DrawCall 从 3000 降到 200 的实战案例。

一、渲染管线速览与 GPU 瓶颈判断

1.1 一条帧的渲染路径

CPU 侧                           GPU 侧
──────                           ──────
准备渲染状态（材质/纹理/参数）     顶点着色器（变换顶点）
  ↓                                ↓
提交 DrawCall                    光栅化（生成片元）
  ↓                                ↓
（等待 GPU 完成）                片元着色器（逐像素计算）
                                    ↓
                                 输出到帧缓冲 → 显示
```text

关键理解：**DrawCall 是 CPU 发给 GPU 的"渲染命令"**。CPU 负责"打包下单"，GPU 负责"加工渲染"。任何一端慢了，帧率都上不去。

### 1.2 判断 GPU 瓶颈

打开 Profiler 的 GPU Usage 模块（或 CPU Usage 对照）：

- **GPU Usage 很高、CPU 空闲** → GPU bound，优化渲染（本文）
- **`Gfx.WaitForPresent` 高** → 两者都在等显示器刷新，有余量
- **`Gfx.WaitForGfxCommandsFromMainThread` 高** → CPU 提交命令太慢，拖累了 GPU

口诀：**GPU 段高 = GPU 忙；WaitForPresent 高 = 都在等。**

### 1.3 移动端 vs PC 端的差异

| 维度   | PC              | 移动端                      |
| :--- | :-------------- | :----------------------- |
| 主要瓶颈 | 常是 CPU/DrawCall | 常是填充率（Fillrate）和带宽       |
| 敏感项  | DrawCall 数量     | Overdraw、Shader 复杂度、纹理带宽 |
| 精度   | float 随便用       | half 精度收益明显              |

所以移动端优化要额外关注：**减少 Overdraw、简化 Shader、压缩纹理**。

## 二、DrawCall 与 Batcher：合批的四种武器

### 2.1 DrawCall 为什么贵

每个 DrawCall 都要 CPU 做一套"状态准备"——设置材质、绑定纹理、上传 uniform 参数，再发给 GPU。**DrawCall 多了，CPU 光做这些准备工作就忙不过来**，GPU 反而在等。

所以优化的核心目标：**用更少的 DrawCall 画更多东西**，即"合批"（Batching）。

### 2.2 静态 Batching：一次合并，长期复用

把标记了 `Batching Static` 的**静态物体**（场景里不动的）合并成一个大的 mesh。

```csharp
// 标记方式：Inspector 右上角勾选 Static，或代码
gameObject.isStatic = true;
```text

- **优点**：大量静态小物体（石头、路标、建筑装饰）合并后 DrawCall 骤降
- **条件**：物体必须静态、材质相同
- **代价**：合并后的 mesh 要**额外占用一份内存**（原始 mesh 保留 + 合并 mesh）
- **适用**：场景固定不变、大量静态小物体的场景

### 2.3 动态 Batching：条件苛刻，别指望它

运行时把满足条件的小 mesh 动态合并。听起来美好，但条件极严：

- 顶点数 < 300（部分平台）
- 相同材质
- 不能用多 Pass 的 Shader
- 不能有骨骼、蒙皮等

**结论**：条件太苛刻，实际项目里大部分物体都不满足，**别把它当主要优化手段**。

### 2.4 SRP Batcher（重点）：不减少 DrawCall，但让每个 DrawCall 变快

这是 URP/HDRP 的核心优化，原理和传统合批**完全不同**。

传统渲染每个 DrawCall 都要 CPU 重新设置一遍材质属性；SRP Batcher 则把材质属性**持久化在 GPU 端的一块大 CBUFFER 里**，CPU 侧只需更新"per-object"的小数据（变换矩阵等），大幅降低每个 DrawCall 的 CPU 开销。

```text
传统：DrawCall → 设置材质A属性 → 设置纹理 → 绘制 → 设置材质B属性 → ...
SRP：  DrawCall → 更新 object 数据 → 绘制（材质属性早就在 GPU 上了）
```text

**注意**：SRP Batcher **不减少 DrawCall 数量**，它减少的是**每个 DrawCall 的准备成本**。所以它和静态 Batching 可以叠加——静态 Batching 减少数量，SRP Batcher 降低单次成本。

**启用条件**：
1. 项目用 URP 或 HDRP
2. Shader 兼容 SRP Batcher（材质属性声明在 `UnityPerMaterial` CBUFFER 里）

```hlsl
// 兼容 SRP Batcher 的写法：材质属性放进 UnityPerMaterial
CBUFFER_START(UnityPerMaterial)
    float4 _BaseColor;
    float _Glossiness;
CBUFFER_END
```text

在 URP 的 Render Pipeline Asset 里勾选 **SRP Batcher** 即可启用。

### 2.5 GPU Instancing：同一物体的千军万马

用**一次 DrawCall 绘制多个相同 mesh 的不同实例**（位置/缩放/颜色不同）。

- **条件**：相同 mesh + 相同材质
- **适用**：大量相同物体——草地、树木、子弹、粒子
- **开启**：材质勾选 `Enable GPU Instancing`

```hlsl
// Shader 里支持 instancing：用 UNITY_VERTEX_INPUT_INSTANCE_ID
UNITY_VERTEX_INPUT_INSTANCE_ID
```text

### 2.6 四种方案对比

| 方案 | 减少 DrawCall？ | 降低单次成本？ | 适用场景 | 内存代价 |
| :--- | :--- | :--- | :--- | :--- |
| 静态 Batching | ✅ | ❌ | 大量静态小物体 | 高（合并 mesh） |
| 动态 Batching | ✅ | ❌ | 极小物体（<300顶点） | 无 |
| SRP Batcher | ❌ | ✅ | URP/HDRP 通用 | 无 |
| GPU Instancing | ✅ | ✅ | 大量相同物体 | 低 |

**实战组合**：URP 项目默认开 SRP Batcher，再对静态场景物体做静态 Batching，对大量相同物体用 GPU Instancing。

## 三、Shader 优化

### 3.1 Shader Variant 爆炸

```hlsl
// ❌ multi_compile 会编译所有关键字组合，变体数量爆炸
#pragma multi_compile _ FOG_ON FOG_OFF
#pragma multi_compile _ NORMAL_MAP_ON NORMAL_MAP_OFF

// ✅ shader_feature 只编译实际用到的组合
#pragma shader_feature _ NORMAL_MAP_ON
```text

`multi_compile` 编译所有组合（2×2=4 个变体），`shader_feature` 只编译用到的。**能用 shader_feature 就不要 multi_compile**，否则构建时间和包体都会膨胀。

### 3.2 ShaderVariantCollection 预热

Shader 变体在**第一次用到时才编译**，运行时编译会造成卡顿。用 `ShaderVariantCollection` 把会用到的变体提前收集，构建时一并编译：

```text
Edit → Project Settings → Graphics → Shader Stripping
新建 ShaderVariantCollection，加入项目用到的 Shader 变体
```text

### 3.3 移动端慎用 discard / clip

```hlsl
// ❌ discard 会关闭 Early-Z，让隐藏像素也被完整计算
if (alpha < 0.5) discard;

// ✅ 尽量用 alpha test 或改用不透明渲染
```text

`discard`/`clip` 会破坏 GPU 的 Early-Z 优化，导致被遮挡的片元也被计算。移动端尤其敏感。

### 3.4 精度选择：half vs float

移动端 GPU（Mali/Adreno）的 `half` 精度运算比 `float` 快，且省带宽：

```hlsl
// ✅ 移动端优先 half（颜色、法线等不需要 full float 精度）
half4 frag(v2f i) : SV_Target {
    half3 normal = normalize(i.normal);
    half lighting = dot(normal, half3(0, 1, 0));
    return half4(lighting, lighting, lighting, 1);
}
```text

PC 端收益不大，但移动端能明显省功耗和带宽。

## 四、几何与可见性

### 4.1 LOD：远小近大

LOD Group 根据物体与相机的距离，切换不同精度的模型：

- **配置**：给模型准备 LOD0（高模）、LOD1（中模）、LOD2（低模）
- **收益**：远处物体面数骤降，GPU 顶点负担大幅下降
- **注意**：LOD 切换有过渡开销，层级不要设太密（3 级够用）

### 4.2 遮挡剔除：看不见就别画

遮挡剔除（Occlusion Culling）在**烘焙阶段**计算场景的空间遮挡关系，运行时隐藏被墙壁等完全遮挡的物体。

```text
Window → Rendering → Occlusion Culling → Bake
```text

- 只对**静态物体**有效
- 动态物体作为"被遮挡者"需要额外设置（Occludee Static）
- 大场景、室内场景收益极高

### 4.3 视锥剔除：Unity 自动做

相机视锥外的物体，Unity 会自动剔除、不渲染。**这是自动的，不要自己再实现一遍**。你只需确保物体的 bounds 设置正确（`Mesh.bounds`、`Renderer.bounds`），否则 Unity 可能误判。

## 五、光照与后处理

### 5.1 Forward vs Deferred

| | Forward（前向） | Deferred（延迟） |
| :--- | :--- | :--- |
| 多光源 | 每盏灯增加一次 Pass | 光源数量影响小 |
| MSAA | 支持 | 不支持 |
| 移动端 | ✅ 首选 | ❌ 带宽压力大 |

移动端几乎一律用 **Forward**。

### 5.2 烘焙光照

静态物体和静态光源的光照，**烘焙进光照贴图**，运行时零光照计算：

```text
Lighting 设置 → 静态物体标记 Static → 光源标 Baked → 烘焙
```text

动态物体用光照探针（Light Probe）接收烘焙的间接光。

### 5.3 阴影设置

阴影是 GPU 大户，按需收敛：

```csharp
Light light = GetComponent<Light>();
light.shadows = LightShadows.Soft;      // 或用 Hard / None
light.shadowStrength = 0.8f;
```text

- 减少投影阴影的光源数量
- 降低阴影分辨率、缩短阴影距离
- 减少阴影级联数（Cascades）

### 5.4 后处理的 GPU 代价

Post Processing 的 Bloom、SSAO、DOF 都是 GPU 重度开销：

- **Bloom** 是移动端最常用的后处理，但也是填充率杀手，慎用高分辨率
- **移动端建议**：只保留 Bloom + ToneMapping，其余关掉
- 后处理分辨率可适当降低

## 六、实战案例：大世界 DrawCall 从 3000 到 200

### 6.1 症状

开放世界场景，Frame Debugger 显示 DrawCall **3000+**，帧率 25 FPS。CPU 主线程不忙，GPU Usage 满。

### 6.2 诊断

1. 开 Frame Debugger，发现大量零散 DrawCall：树木、石头、草、建筑装饰各自独立提交
2. 大量静态物体未标记 Static
3. 同类物体（树木、草地）未用 GPU Instancing
4. Shader 变体过多，构建时编译了上千个变体

### 6.3 修复

```text
1. 静态物体标记 Static + 静态 Batching：DrawCall -1500
2. 树木/草地/石头用 GPU Instancing：DrawCall -800
3. 项目切 URP + 开 SRP Batcher：单 DrawCall CPU 成本 -60%
4. Shader multi_compile 改 shader_feature：变体数 -70%
5. 远处物体加 LOD + 烘焙遮挡剔除：GPU 顶点负担 -40%
```text

### 6.4 验证

| 指标 | 优化前 | 优化后 |
| :--- | :--- | :--- |
| DrawCall | 3000+ | 200 |
| 帧率 | 25 FPS | 55 FPS |
| GPU 顶点负担 | 高 | -40% |
| 构建时间 | 长 | -30% |

## 七、GPU 优化 Checklist

1. **[ ] 归属**：Profiler 确认 GPU bound（GPU Usage 高、CPU 空闲）
2. **[ ] 合批方案**：静态物体标 Static、大量同类物体用 Instancing、URP 开 SRP Batcher
3. **[ ] DrawCall 基线**：Frame Debugger 记录优化前 DrawCall 数
4. **[ ] Shader 变体**：multi_compile 已换 shader_feature，变体已收集预热
5. **[ ] discard/clip**：移动端 Shader 已避免
6. **[ ] 精度**：移动端 Shader 已用 half
7. **[ ] LOD**：模型已配 3 级 LOD
8. **[ ] 遮挡剔除**：静态场景已烘焙
9. **[ ] 光照**：静态光已烘焙、阴影已收敛
10. **[ ] 后处理**：移动端只留 Bloom/ToneMapping，分辨率已调
11. **[ ] 验证**：复测 DrawCall、GPU Usage、帧率

## 八、结语

GPU 优化的主线是**让 CPU 少打单、让 GPU 少算无用的像素**：合批解决"单太多"，LOD/剔除解决"画太多"，Shader 简化解决"算太重"。四种合批方案各有边界，别盲目全开——静态 Batching 吃内存，动态 Batching 条件苛刻，SRP Batcher 只降单次成本，Instancing 只适合相同物体。理解了边界，才能在 Frame Debugger 里做出正确的取舍。
